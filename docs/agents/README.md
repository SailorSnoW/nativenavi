# Working on the host: agent guide

These pages are for an agent working on this repository, which runs one game natively on Apple silicon Macs: The Legend of Zelda: Ocarina of Time for the Nintendo Switch 2 (profile `0400486024DEC000`, NVN2). The game's own aarch64 code runs natively, a rewriter patches only the instructions Apple's kernel cannot run, the host replaces Horizon system services, and NVN is reimplemented on Metal.

The repository is a hard fork of nxnative, which runs many Switch games, and the recipes here were found there on those games. Where a guide gives a number or an example from another game, it names the game: that is history, not a figure for this one, so measure before relying on it.

## Ground rules

- **Game files stay outside the repository.** The game's files and anything extracted from them stay in the game's build folder (`<NUP folder>/0400486024DEC000_build`, or the `--work-dir` given to `scripts/build_app.py`): unpacked files, rewritten modules, shader libraries, runs, dumps and analysis. Never in the repository, never in a commit. Ask before deleting anything in that folder that you did not write ([AGENTS.md](../../AGENTS.md)).
- **Measure, then change.** Each fix in this repository started from a concrete observation (a crash address and its decompilation, a census over all shaders, a memory profile). Write the evidence into the reference entry or the game's note, and link it from a short comment at the fix.
- **Find the root cause; don't just work around it.** A crash, hang or wrong picture is finished when its root cause is found and fixed there, not when it stops showing. Follow the bad value back to where it was written and the call back to the semantics the host gets wrong; a stub, skip, clamp, retry or timeout that only makes the symptom go away is a workaround, kept only when the root cause cannot be fixed and recorded as open ([AGENTS.md](../../AGENTS.md)).
- **One profile.** The game's constants live in its profile `dm/games/0400486024DEC000/` ([dm/games/README.md](../../dm/games/README.md)): program ID, known builds, modules, address-space partition, the shader tables and the app identity. The code reads the profile through `game_profile.h` (host) or `dm/games/game.py` (tools); the tools and Makefiles take this profile by default, and `DM_GAME` / `GAME` name another only for a derived profile (a version of the game the profile does not register). Behaviour that uses fixed addresses in the game's code is gated by the build ID (`dm_main_build()`), never left on for a build it was not found in.
- **One place per finding.** A fact about the game goes into its note; a mechanism of the host or the tools goes into its `docs/reference/<subsystem>.md` section as an entry (Symptom, Cause, Fix, Found on), then `python3 dm/tools/docs_symptoms.py` updates the symptom index. Link to a finding instead of repeating it.
- **Write code comments in English, and only where the code needs a clear, precise explanation**: never one per step, never a paraphrase of the code. Start log lines that mark something unimplemented or wrong with `[RED] `.
- **Test where it runs.** The Mac host (`dm/host/dmhost`) is the development loop, and the Mac app runs the same host. Say which Macs a change was run on, and name a path this Mac cannot exercise (hardware AV1 decoding needs an M3 or later) as untested.
