# Packing

The packing script (`scripts/build_app.py`, `scripts/pack_nup.py`): the NUP, the build folder, shader libraries, the RomFS image and the Mac app. Each entry: symptom, cause, fix, where it was found. The [symptom index](../agents/symptoms.md) lists every symptom.

## Game packages

### A NUP with complete standalone updates stops at "no base game"

- **Symptom:** `no base game, only update packages: pack the base game and its update into one NUP`, even when the update carries the complete game's files ([issue #1195](https://github.com/seedds/nxnative/issues/1195)).
- **Cause:** `pack_nup.scan` required a `base` record. NUP v1 permits a container without one when every update has the `standalone_update` flag (package flags bit 0, [SPEC §3.1.2](https://github.com/a55uka/nup/blob/meow/SPEC.md#312-package-kinds)). The reference packer writes one for a dump with no `base/` folder and, since its commit `92089de3`, for an empty `base/` too; before that an empty `base/` gave an empty base record, which got through the check. The issue was filed before that commit, so its NUP came from a dump with no `base/` folder or from another packer; the file itself was not seen.
- **Fix:** no base record and a base record with no files are one case: `scan` gives `None` for the base, and only the update versions present are offered. Both packing entry points select the newest update by default; requesting version 0 fails. The selected update must have `exefs/main`, `exefs/main.npdm` and its own RomFS; it cannot borrow another update's RomFS. Control data the update lacks comes from the record that holds application metadata: the empty base record, else the first package ([SPEC §5.1](https://github.com/a55uka/nup/blob/meow/SPEC.md#51-localized-records-types-0x0009--0x000a)). A base with files still supplies the RomFS for an update without one. Program-ID, DLC, content-size and SHA-256 checks apply as before. A version that cannot be packed stops at a `[RED]` line: the disk check reads its RomFS folder before extraction, so `cli()` catches `pack_nup.Error`.
- **Not known from the file:** whether the update is the whole game. The flag does not promise it (the spec says such an update needs a matching base elsewhere), and an update holding only changed files would pack and then fail at boot, after a full shader build. The scripts print that the update is taken as the whole game. Measured: both NUPs at hand have an update RomFS that holds every path of its base (Age of Imprisonment: 2,065 base files, 2,153 in the update, none missing; Yoshi and the Mysterious Book: 147 and 147, none missing).
- **Found on:** Mario Kart World. Reproduced with its base dump repackaged by the reference tool as a standalone-update fixture; this checks packaging, not the reported 1.8.0's contents or gameplay. Synthetic tests cover both entry points, both forms of no base, multiple versions, control data, DLC and incomplete updates.

### A damaged file in a NUP or a dump has no hash to fail

- **Symptom:** the game reloads one asset for ever: a background loader takes about a core and the process several (Ocarina of Time: 412% CPU on the Mac, `OptimizeChangeBanc` and `ParallelDecompThread` busy all session, one model and its texture opened about 22 times a second). Or, from the packing script: `vN: K file(s) whose bytes do not start as their names promise (a .zs file that is not a zstd stream), so the game files are damaged`, then the files.
- **Cause:** the game files themselves. A NUP's files are checked only against the container's own SHA-256 of each file, taken when the NUP was packed from a dump: whatever bytes the dump held are packed, and nothing says what they should have been. On one NUP of Ocarina of Time three `.zs` textures began with 12,288 zero bytes, so no zstd frame: the game could not decompress them, and its loader asked for them again on every pass ([PR #1530](https://github.com/seedds/nxnative/pull/1530)). The container's own SHA-256 of each file matched, so the bytes were like this when the NUP was packed. Another NUP of the same version holds all three as zstd streams, and none of its 102,185 `.zs` files fails the check.
- **Fix:** the packing script reads the first bytes of every file whose name promises a format (`romfs_image.FORMAT_HEADS`: `.zs` starts with a zstd frame or a skippable frame) once per extracted image (`check_formats`, after extraction; the result is kept in `RomFS.img.formats` beside the image until the image changes: Ocarina of Time 16 s from a USB SSD) and stops naming the damaged files: pack again from a good copy of the game. [`--allow-damaged`](../development.md#the-packing-script-in-detail) lists them and packs them as they are. The host serves a game's files as they are: substituting other files for damaged ones would hide the damage and change what the game draws.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md), a contributor's NUP of v131072.

### A NUP whose folder contains itself

- **Symptom:** `pack_nup.py`, or the packing script on a NUP, ends in a Python traceback (`RecursionError` in `tree_bytes`) instead of a `[RED]` line.
- **Cause:** `Nup` checked each folder's child range and each child index against the table sizes, but not that the folders form a tree. A table of contents whose hash matches can still name a folder, or one of its ancestors, as its own child; `scan` sums the base package's size by recursion and never ends, and `entries` (the RomFS image's walk) would loop.
- **Fix:** `Nup` walks the folder graph once, depth first without recursion, and refuses a folder that contains itself, naming it (`contains itself (damaged file)`), before any other walk sees the container.
- **Check:** `test_nsp_nup` Read.test_folder_cycle_refused: a folder made its own parent, then a cycle of two folders, each with the TOC hash fixed up, are refused, and the script exits 1 with no traceback. Without the check the container opens.
- **Found on:** a code audit; no damaged NUP of this kind is known.

### An app packed without control data says version 1.0

- **Symptom:** Finder shows `Version 1.0` for a Mac app whose game is at another version (this game's NUP holds update v131072, 1.1.1), and the game asks the host for its version (`nn::oe::GetDisplayVersion`) and gets `v131072`.
- **Cause:** the packer took the app's version from the game's NACP only, and a NUP (this game's) can carry none, so the bundle got its default. The profile's build row had `v131072` as its display version, which the host answers the game's version query with (`hle_sdk16.c`, `DM_GAME_DISPLAY_VERSIONS`, by main build ID).
- **Fix:** `scripts/build_app.py` `app_display_version`: the packed version's NACP first, then the numeric display version of the packed build's profile row, then the base game's NACP (which can describe an older release); with none, `1.0`. The profile registers `1.1.1` for its v131072 build (`main` build ID `e0f3ccfa…`, the one upstream registers as 1.1.1), which gives both the app and the host's answer.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md), upstream nxnative `742e959e` ([PR #2822](https://github.com/seedds/nxnative/pull/2822)), ported here by hand: upstream's packer is another script.
- **Check:** `dm/tools/tests/test_app_version.py` (the order of the sources, a row that is no number, and the profile's 1.1.1).

## Build tools

### Stopping a build left its tools running

- **Symptom:** after the packing script was stopped in Spyder (its interrupt), or by a front end's SIGTERM, the tool it was running went on: a shader build kept the CPU busy and wrote into the build folder that the next build reads, and the script could wait for it with no end. A regression run (`regress.py`) stopped during a shader build whose direct child ignored SIGTERM for 10 s left the build's workers running. A tool's child still writing after the tool's own exit was taken for a finished step.
- **Cause:** `run` (the packing script) started each tool in the script's own process group and on an interrupt stopped only that tool (`terminate`, then a wait without a limit); a terminal's Ctrl-C reaches the whole foreground group, but Spyder's interrupt reaches only its kernel, and nothing handled SIGTERM, so the tool's descendants were never told. `run_heavy` (`regress.py`) did start a group of its own, but its fallback after 10 s killed only the direct child, without reaping it, and a child left running after the job's own exit went unnoticed. `run` also read the tool's output until its end, so a descendant holding the output kept it waiting after the tool had exited.
- **Fix:** both run their tool through `dm/tools/proc_group.py`: the tool leads a session and process group of its own, and on an interrupt, a SIGTERM or an error (a log that cannot be written) the whole group gets the signal that stopped the caller (SIGINT for an interrupt, SIGTERM otherwise), resumed first when a pause (`run_heavy`'s measuring lock) left it stopped; what is left after 5 s is killed and the tool reaped. A process of the group still running 5 s after the tool's normal exit, holding its output or not, is stopped and fails the step as an exit code would (what it writes may be incomplete); the message names it. The tool's exit is seen while its output is read, so a holder of the output no longer stalls the step. The packing script's `cli` turns SIGTERM into an exit with code 143 (the [front end's contract](../frontends.md)), with the handler set only while it runs (Spyder's kernel gets its own back). A process that leaves the group itself (`setsid`) is out of reach of group supervision: it is neither signalled nor waited for (one still holding `run`'s output fails the step, unnamed). `patch_nso.py`'s pool of forked workers is outside this change: they stay in the rewrite's group, and the rewrite's SIGTERM handler (`sys.exit(143)`) ends the pool, which stops and reaps them. The module rewrites that `build_app.py` and `regress.py` start, `regress.py`'s game runs and `bench.py` still stop their direct child only: moving them to `proc_group` is a separate change. `dm/tools/tests/test_proc_group.py` runs real process trees (`fixtures/proc_tree.py`) through `run`, `run_heavy` and `cli`.
- **Found on:** no game; found in a review of the build scripts, with a repro (an interrupt raised in `run`'s progress callback, after which the tool's child kept writing).

### Closing the terminal left a build's tools running

- **Symptom:** after the terminal running the packing script or `regress.py` was closed, the tool the script was running (a shader build, a game under the harness) went on running with no parent, writing into the build folder; the script itself had gone without its cleanup.
- **Cause:** since [Stopping a build left its tools running](#stopping-a-build-left-its-tools-running), each tool leads a session and process group of its own, so the shell's SIGHUP on a closing terminal, sent to its job, reaches the script alone. Neither script handled SIGHUP, and its default action ended the script before the tool's group was stopped; before that change the tool was in the script's group and got the SIGHUP too. Reproduced with a script running `sleep 30` through `proc_group.Group`: a SIGHUP to the script's group ended the script and left the sleep running, where a plain child in the script's group went with it.
- **Fix:** the packing script's `cli` turns SIGHUP into `Stopped` as it does SIGTERM (the running tool's group stopped, the stage line ended, exit code 129; both handlers set only while `cli` runs and given back after), and `regress.py`'s main exits with 129 on SIGHUP as with 143 on SIGTERM, so the finally blocks stop the game or build's group. `test_proc_group` (`Cli.test_sighup_during_a_tool`) sends a real SIGHUP to the script while a tool's group runs and checks the group is gone and the tool got its SIGTERM.
- **Found on:** no game; found in the audit of the review's process-group change.

### Stopping a build while it replaced an output left that output half deleted

- **Symptom:** none seen on a game. An interrupt, a SIGTERM or a failed delete while the packing script replaced one of its outputs (the rewritten modules, the shader package) could leave that output half deleted at its real path, and a reuse check that looks for a few files could take it for a finished output on the next run.
- **Cause:** `swap_in` deleted the old output in place (`rmtree(dst)`) and only then renamed the staged one (`<dst>.partial`) in; its comment said the old one was untouched on failure. Its callers already write their completion stamps only after the swap, so the old output was stale whenever it was replaced: the loss was the half-deleted folder, not the old contents.
- **Fix:** `swap_in` renames the old output aside (`<dst>.old.partial`, a name the build ignores as it does every `.partial` folder), renames the new one in, and only then deletes the old one; a failure or an interrupt before the new one is in renames the old one back. The output is always the whole old one, the whole new one, or absent. This is recoverable, not atomic: a SIGKILL between the two renames leaves no output (the old one aside), which the next run rebuilds, and a delete stopped after the new one is in leaves the aside folder's remains until that output is replaced again (disk space only). A failed delete of the old output still fails the step, after the new one is in. `dm/tools/tests/test_nsp_swap_in.py` runs each case in a process of its own (`fixtures/swap_in_run.py`): failed and interrupted renames, interrupted and failed deletes, an earlier run's aside folder, a SIGKILL between the renames, each followed by a rerun.
- **Found on:** no game; found in a review of the build scripts. The half-deleted output was reproduced with the old `swap_in` (an interrupt during its delete); that a reuse check would have taken one is inferred, not reproduced.
- **Since:** the step 15 audit found three gaps, each reproduced against the script before it: a rerun after a SIGKILL between the two renames deleted the aside copy, the old output, before publishing again, so a rerun that then failed left no output; an interrupt between the rename aside and the second rename (outside the `try`) put nothing back; and a failure to rename the old one back raised that rename's own `OSError`, hiding the first failure and where the old output was. Now the rollback is judged by what is on the disk (the old output aside and nothing in place: it goes back), a failed putting back raises `BuildError` naming `<dst>.old.partial`, and an aside folder a run finds is put back when nothing is in place and deleted only when the new output went in. `test_nsp_swap_in`: a kill between the renames then a rerun that fails (the old output back in place), an interrupt right after the rename aside, and a putting back that fails (`BuildError`, nothing deleted, the next run publishes); all three fail on the script before.

### Building needed .NET, and finding its runtime kept failing

- **Symptom:** in nxnative, before running the packing script, a player had to install the .NET SDK 10, and builds then failed in ways that were about .NET, not the game: a translator that finds no runtime of its architecture ([GitHub issue #54](https://github.com/seedds/nxnative/issues/54), [#248](https://github.com/seedds/nxnative/issues/248), [The shader step stops with an empty `xlate_source`](#the-shader-step-stops-with-an-empty-xlate_source)), a Homebrew runtime the apphost cannot find, a dll tied to one architecture ([#803](https://github.com/seedds/nxnative/issues/803)). [GitHub issue #1853](https://github.com/seedds/nxnative/issues/1853) asked for the tools to be rewritten in Python or Objective-C.
- **Cause:** the shader translator, a C# tool, was framework-dependent: a committed apphost with its dlls, which needs a .NET 10 runtime of the architecture it starts as. It does not need .NET itself: Ryujinx's shader library compiles ahead of time. A rewrite would have replaced Ryujinx's translator with new code, changing every game's shaders on any difference. (nxnative's second C# tool, its NSP extractor, went the same way; this fork packs from a NUP with `scripts/pack_nup.py` and does not have it.)
- **Fix:** the translator is committed as a native universal executable (NativeAOT, arm64 and x86_64), `dm/gfx/tools/dmsh_xlate_bin/dmsh_xlate`, which `dm/tools/native_tools.sh` builds (the .NET SDK is needed only there). It embeds its sources and prints their digest with `--source-sha`: `tool_lock.py` refuses a translator not built from the sources in the repository, and the lock records the translator's own fingerprint in place of its dlls'. The packing script does not ask for `dotnet`; it starts the translator once before it unpacks anything (`check_translator`). `dm/tools/tests/test_native_tools.py` checks that the executable is universal, alone in its folder, built from its sources and the lock's. Measured before landing: the native translator wrote the same SPIR-V, reflection files and messages as the framework-dependent one for 2,058 shaders of Octopath Traveler II (Maxwell) and 672 of Splatoon Raiders (Ampere), byte for byte. The cost: each translator rebuild adds about 1.4 MB to the repository's history (the dlls about 0.3 MB), since the executable holds the runtime; the build is not byte-reproducible, so a rebuild only follows a source change.
- **Found on:** every game's build; reported in [GitHub issue #1853](https://github.com/seedds/nxnative/issues/1853).

### The committed translator crashes at address 0 on macOS 26

- **Symptom:** on macOS 26 the packing script stops before unpacking anything with `[RED] the shader translator does not run (exit code -11)`, and `dmsh_xlate --source-sha` exits 139: `EXC_BAD_ACCESS` at address 0 with pc 0, called from `dmsh_xlate +0x5adc`. On macOS 27, and under `arch -x86_64`, it runs.
- **Cause:** the arm64 slice committed with the [native translator](#building-needed-net-and-finding-its-runtime-kept-failing) imported `pipe2` weakly: its minimum macOS is 12.0, and `pipe2` is declared from the macOS 27 SDK on. The .NET runtime's `SystemNative_Pipe`, which opens the signal pipe at start, was compiled to call it without a check, so on a Mac without it the import binds to 0 and the call jumps there. Microsoft's NativeAOT runtime pack (10.0.14, built against the macOS 15.5 SDK) has no such call: a build with it on the same sources has no `pipe2` import. So that slice was linked with another `libSystem.Native.a`, one configured against the 27.2 SDK; which .NET gave it is open (a source-built one, such as Homebrew's formula, builds its host architecture's pack against the installed SDK, which would also explain the clean x86_64 slice).
- **Fix:** the translator is rebuilt with Microsoft's .NET SDK. `native_tools.sh` refuses a slice with a weak import before it joins the slices, and `test_native_tools.py` (`test_no_weak_imports`) reads the committed translator's symbol tables, so a function newer than the minimum macOS cannot be committed again from any Mac. Measured: over the translator jobs of a full Cuphead shader build, the new arm64 slice wrote the same files as the old one, byte for byte. Not run on macOS 26 here.
- **Found on:** every game's build on macOS 26 ([GitHub issue #2190](https://github.com/seedds/nxnative/issues/2190), [#2239](https://github.com/seedds/nxnative/issues/2239), [#2227](https://github.com/seedds/nxnative/issues/2227)).

### The shader step stops with an empty `xlate_source`

- **Symptom:** the game unpacks, then the shader step stops with `translation chain tools do not match the lock file: xlate_source: lock … / actual` and nothing after `actual`, which reads like a stale translator.
- **Cause:** the translator (`dmsh_xlate_bin/dmsh_xlate`) was a universal framework-dependent apphost. When it found no .NET 10 runtime for the slice it started as, it exited 131 with an empty stdout. A Python under Rosetta (an Intel Homebrew's) started it as x86_64, and it found only the arm64 .NET. An Intel .NET on Apple silicon failed the same way. `tools_now` (then in `dmsh_chain.py`) kept only the stdout of `dmsh_xlate --source-sha`, without its exit code or stderr, so the apphost's own message was lost.
- **Fix:** the translator is now native and needs no runtime ([native tools](#building-needed-net-and-finding-its-runtime-kept-failing)); the checks below stay, for a translator that does not start. The packing script checks the environment before unpacking anything: `check_native_python` stops under Rosetta (`sysctl.proc_translated`), and `check_prereqs` starts the translator once with `--source-sha` and stops with its first message line (`check_translator`). `tool_lock.py` records `--source-sha`'s failure instead of its empty stdout (`xlate_embedded`: `does not run (<first message line>)`), so `dmsh_build.py` run directly and `--update-lock` stop with the same message as the packing script, without the lock and rebuild lines. The tool checks used to be in `dmsh_chain.py`, which is part of the chain version and of every shader's cache key, so that fix rebuilt every library; they now live in `tool_lock.py`, outside both, and a change to them rebuilds nothing.
- **Found on:** NX2Apple builds ([LNPANDY/NX2Apple#31](https://github.com/LNPANDY/NX2Apple/issues/31), item 3; [PR #477](https://github.com/seedds/nxnative/pull/477), [PR #487](https://github.com/seedds/nxnative/pull/487)); reproduced with `arch -x86_64`. Applies to every game.

### The split shader tables differ from a game profile's

- **Symptom:** the shader split stops with `the split shader tables differ from game profile <id>'s`, on the game version the profile registers.
- **Cause:** the check compares the split's data rows with the profile's byte for byte, so it stops for either of two reasons: other game files, or a change to `shader_split.py` that reads the same files differently. A profile's tables can only be split again where its game files are, so continuous integration cannot catch the second reason.
- **Fix:** the error shows each differing table's row counts and its first row on each side. For a splitter change, check that the new rows are right, then copy the tables from `shader/pkg.partial/tables` in the build folder into the profile.
- **Duplicate selection (first four profiles refreshed, 2026-11-17, issues [#2916](https://github.com/seedds/nxnative/issues/2916) and [#2921](https://github.com/seedds/nxnative/issues/2921)):** `8d62601f` made `main` use the same checked first-copy selection as RomFS, replacing unchecked last-copy selection. The registered executables of Splatoon Raiders, Pokémon Scarlet, Tears of the Kingdom and Donkey Kong Bananza each regenerate 40 `main` rows: 22 source labels change and 14 more rows change only their package index. Their maps were refreshed with those 36 differing rows and the current source-column header; every registered key, stage and package and every non-`main` row is preserved. The strict table comparison and duplicate-content checks stay unchanged. Bananza's additional DLC shaders still use the existing DLC-only derived profile; they do not belong in its registered base/update map.
- **Representative contract:** first-copy selection covers both embedded shaders and decoded Unreal archives collected with `main`, as well as RomFS readers. Source labels determine package ordering and indices, so byte-equivalent duplicate selection can still change registered map rows. Verify shader identity by key, stage and package, compare complete duplicate controls/code, and preserve generated facts and pairs before refreshing a map. Keep RT metadata conflict rejection and the strict packing gate. `test_split_representatives` exercises complete synthetic BNSH/main, BNSH/RomFS and decoded-Unreal splits, first-copy payloads, labels, indices, pairs, base/update source precedence and deterministic output; restoring last-copy selection fails both main and Unreal cases.
- **Further rollout (2026-11-17 to 2026-11-19, issues [#2924](https://github.com/seedds/nxnative/issues/2924), [#2927](https://github.com/seedds/nxnative/issues/2927), [#2946](https://github.com/seedds/nxnative/issues/2946), [#2964](https://github.com/seedds/nxnative/issues/2964) and [#2950](https://github.com/seedds/nxnative/issues/2950)):** Odyssey, Breath of the Wild, Wonder, Mario Tennis Fever, Orbitals, Fire Emblem Fortune's Weave, Pokémon Legends: Z-A, Super Smash Bros. Ultimate, Mario Kart World and Final Fantasy XII The Zodiac Age have verified representative refreshes. Their notes in nxnative record the checks and limits; none of those profiles is in this fork.
- **Found on:** Splatoon Raiders ([issue #1263](https://github.com/seedds/nxnative/issues/1263)): [NVN2 task and mesh shaders](shaders.md#nvn2-task-and-mesh-shaders) moved one row from vertex to mesh. Donkey Kong Bananza, Pokemon Pokopia and Hyrule Warriors: Age of Imprisonment were checked and hold no such shader; Fire Emblem Fortune's Weave was not checked, as no dump was at hand.

### The shader package and the shader map come from different splits

- **Symptom:** `dmsh_build.py` stops with `[RED] <package> holds no record of shader <key>, which the shader map names: the package and the map come from different shader_split.py runs`, with `(its records carry no keys: it was split before they did)` for a package from before chain `3df44a5a4e0c`. Before that chain: wrong shaders wherever the game drew, such as a black screen with sound.
- **Cause:** `dmsh_build.py` `rec_of` read a shader's record by its row's index in the map alone. With a package (`shader/pkg/*.bin`) from one split and a map from a later one that dropped or added a row, every later row of that package was translated from another shader's bytes. The packing script's own split never mixes them: its reuse key covers `shader_split.py` and the profile's tables. A build whose split came from elsewhere could: NX2Apple's patches hand the split to another tool under the same key.
- **Fix:** general, in the package format. `shader_split.py` writes each record's key (its 8 bytes) at record +0x08, in header bytes that were zero; `dmsh_build.py` `record_index` indexes a package by those keys and `rec_of` finds a row's record by its key, so a row's index no longer matters and a package that does not hold a row's shader stops the build before the first job. The control section is searched from +0x38, after the header. The map keeps its index column, so the profiles' tables did not change. A package from before the change carries no keys: the packing script splits again by itself (its key covers `shader_split.py`), while a tool that hands `dmsh_build.py` an older package, such as `regress.py`'s use of a game's `<id>_build/shader/pkg`, needs that build run again first. `test_shader_package_keys` covers both sides.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) ([issue #1841](https://github.com/seedds/nxnative/issues/1841), diagnosed by its reporter). A build through NX2Apple 1.3.0 kept `ps_lib.bin` from an older split (4,711 records) beside a map from a split after 04df08d4 (4,707 rows), so the present pass's pixel shader `29e3c9dd92b8a571` was translated from a terrain shader's record and drew black.

### A reuse build spends a minute and a half on the c1 and uniform extent tables

- **Symptom:** a build that restores every shader from the compile cache still spends about a minute and a half after the last shader, with the progress line at 99%, before `dmsh_build.py` prints `c1_full.tsv: …` and `cb_extent.tsv: …`: 95 s for Ocarina of Time's 42,848 shaders on an M3 Max.
- **Cause:** `c1_guard.py` and `cb_extent.py` analysed every shader's MSL and reflection again after each full build (`dmsh_build.py` runs them, and `chain_tables` when a table names another library), though a shader restored from the cache has the same files, so the same answer.
- **Fix:** with `DMSH_TABLE_MEMO` set to a folder, each tool keeps a line per shader there (`c1_guard.memo`, `cb_extent.memo`): the SHA-256 of the files it read, then its answer. The next run takes the answer of every shader whose files hash the same and analyses the rest. The packing script sets it to its shader cache folder for the build and for `chain_tables`. The memo's first line is a fingerprint of `c1_guard.py`, `cb_extent.py`, `dmsh_abi.py` and the header it reads (`dm/gfx/nvn/dmsh_abi.h`: the binding kinds `cb_extent.py` filters on), so an edit to any of them starts it empty. It holds the last run's answers only (6.5 MB for Ocarina of Time). Without the variable nothing is hashed.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) v131072 on an M3 Max: both tables in 95.1 s without the memo, 96.8 s with an empty one and 6.5 s from a full one, byte-identical after the header in all three runs. `dm/tools/tests/test_nsp_chain.py` (`TableTools`: the same tables from the memo, its answer used, changed bytes analysed again, another version's memo not taken).

### Every second build signs the whole Mac app again

- **Symptom:** a build's last stage shows `Mac app · game files` without `(reused, signed)` and signs for three minutes, though the game files did not change and the build before it showed `game files (reused, signed)`; a build that changed nothing still shows `Mac app · pipeline archive` and signs for half a minute. Ocarina of Time (a 36 GB app) on an M3 Max: `Mac app` took 3:33 in the build after one where it took 1:11, and four packs that each changed one small file took 8 s, 220 s, 8 s and 220 s.
- **Cause:** three things kept `pack_app.py` from finding a data bundle as its last pack left it. A bundle cloned from the app being replaced has the change time of its files moved by macOS a second to a minute after the pack (seen on macOS 27.2 on APFS, as Spotlight takes in the new app; not in a `.noindex` folder, and not for the files that are clones of the build folder's), so the record a pack wrote after reusing a bundle never matched at the next pack, and reuse alternated. It moves the change times of the build folder's large files as well (the 10.7 GB library image, 6 and 19 minutes after its build), which the packer keys those inputs by, so a build that changed nothing made the shader libraries' bundle again. The prewarm pipelines in `pso/mac` were taken away by each `pso_offline.py` run (as archives of an architecture not asked for) and linked again by the packing script, and `pso_offline.py` wrote `prebuilt.tsv` and `archive.tsv` again with the same text: new times for files the packer keys by their times, so the pipeline archive bundle was made and signed by every build. And a pack that stopped (while it signed, the long step) had already deleted `<app>.key`, so the next pack signed every bundle though the app in place was unchanged.
- **Fix:** `<app>.key` also records a SHA-256 for each file of the data bundles (`seals`): the digest its bundle's signature holds (`CodeResources`, `files2`), which codesign wrote from the bytes it read, and for the few small files the signature does not name (the bundle's `Info.plist`, the signature's own) their own. A file whose change time alone differs from the record is read and compared with it (`as_recorded`): the same bytes are reused (and the app's record is written again with the new times), other bytes or a file with no recorded digest make the bundle anew as before. The large inputs are taken the same way (`as_packed`, the record's `sources`: the app's copy's digest for the RomFS image and the archive's files, which are clones, and the library image's own, read while its bundle is filled). The packing script leaves a prewarm file in `pso/mac` that is already this build's (the same link, or a copy of the same bytes), `pso_offline.py` leaves an asked architecture's prewarm files and a list whose text is unchanged, and a pack that fails sets its record aside as `<app>.key.replaced`, from which the next pack takes only the data bundles. The new data bundles are signed at once, each by its own codesign.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) v131072 on an M3 Max: the four packs took 8 to 9 s each; the `Mac app` stage of a build that changed nothing went from 0:39 to 0:01, and of a build after a chain change from 3:33 (4:02 the same day) to 1:00, the shader libraries and the pipeline archive signed together in 34 s (70 s one after the other, 38 s at once, the same signatures); with the change times of the RomFS image, the library image and the archive moved, the app is `reused (inputs unchanged)` after 22 s of reading them, where all three bundles were made again before; the app verifies (`codesign --verify --strict`), and its files are those of the app built before, but for the chain label, the host and the prewarm pipelines. `dm/tools/tests/test_nsp_mac_app.py` (`PackReuse`: a moved change time with the packed bytes and with other bytes, a stopped pack; `Sign`; `App`: codesign's own record of a large file; `Script`: the prewarm files left in place), `dm/tools/tests/test_pso_offline.py`.

### A build that changes nothing takes a minute and three quarters

- **Symptom:** a build whose every stage says `reused (inputs unchanged)` still takes 1:45 (Ocarina of Time on an M3 Max): 22 s between `unpack` and `rewrite`, 12 s in `Mac shaders · checking the inputs`, 26 s in `Pipeline archive`, 39 s in `Mac app`.
- **Cause:** each of them read the game or its libraries again to find them unchanged. The 22 s went to nxnative's guess of how a game's shaders are got, which read the head of every file of the RomFS several times over (19 s for 186,583 files); this fork has the one profile and no such step. The shader step's reuse path prunes the compile cache, and `prune_shaders` read every per-shader entry's size along with its name, which walks the blob table of an 11.5 GB file (13 s) though nothing was to go. `pso_offline.py` read every reflection and hashed every library its bases name (33,365 bases) before its key could say the archive was reused. The app was packed again for the reasons of [Every second build signs the whole Mac app again](#every-second-build-signs-the-whole-mac-app-again).
- **Fix:** `prune_shaders` reads names and times from the entry table and sizes only for what it removes. `pso_offline.py` keeps a key of what a run reads by name and time (`run.key` in its work folder: the library image's place, inode, size, modification and change times, the lists, the compiler, the options and the tools' code) with the state of its outputs, and a run with the same key and outputs returns before it reads a library; a library in a folder, or any difference, goes through `archive_key` as before. The inode and change time also catch [changed shader bytes whose modification time was preserved](#a-changed-shader-library-reuses-an-old-pipeline-archive).
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) v131072 on an M3 Max: 1:45 to 0:10, three builds in a row, the app `reused (inputs unchanged)`; the first build with the new tools took 1:10.

### After a chain change the steps behind the last shader take three minutes

- **Symptom:** a build after a chain change that left the MSL as it was (`Metal cache: mac 55482 reused, 0 compiled`) spends about a minute in `writing the library image` and a minute and a half in the c1 and uniform extent tables, and its app step half a minute in `shader libraries` (Ocarina of Time, 42,848 shaders: 0:56, 1:26 and 0:25 on an M3 Max).
- **Cause:** the tables' memo ([A reuse build spends a minute and a half on the c1 and uniform extent tables](#a-reuse-build-spends-a-minute-and-a-half-on-the-c1-and-uniform-extent-tables)) is keyed by each shader's files, and a reflection names its chain version, which neither tool reads: after a chain change every key missed. `dmsh_build.py` writes the image from its 300,000 staged outputs, read out of the compile cache one after the other on one SQLite connection, which gives a library's chain of pages at about 190 MB/s; the app's copy of the library (`shader_lib.subset`) read its 130,000 files one by one too.
- **Fix:** the memo's key takes a reflection without its chain version (`memo_reflection`). `shader_lib.write` calls the sources it is given as functions on eight threads, a few entries ahead of the writer, which takes them in order, and `shader_cache.Store.get` reads on a read-only connection of the calling thread's own when that thread is not the one that opened the store and is not inside a batch (it takes the store's lock to ask, so a batch under way in another thread is over first, as before); `subset` reads its files the same way, and `pso_offline.py` hashes the libraries on eight threads. The connections have a [reader-lifetime guard during recovery and close](#cache-recovery-races-a-parallel-shader-reader).
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) v131072 on an M3 Max: both tables in 106 s with an empty memo, 6.6 s from a full one and 13 to 19 s in the builds after a chain change (86 to 104 s before), their rows the same; the image in 40 to 49 s (56 to 70 s before; 7.4 GB from the cache in 22.3 s against 48.8 s alone), the app's copy in 15 s against 23 s, the same bytes each time; every file of the library is the one the unchanged tools built, but for the chain label. `dm/tools/tests/test_nsp_chain.py` (`test_memo_holds_across_a_chain_change`), `dm/tools/tests/test_shader_lib.py` (`Write`), `dm/tools/tests/test_shader_cache.py`.

### Cache recovery races a parallel shader reader

- **Symptom:** a shader build stops with an uncaught `KeyError` in `Store._reader` while the damaged compile cache is being recreated.
- **Cause:** the parallel reader checked and returned its registry entry outside the store lock, so recovery could clear that entry before the lookup. Connection creation also ran outside the lock, allowing a reader of the old file to be registered after recovery replaced it, and recovery could close a connection during an active `fetchall`.
- **Fix:** `shader_cache.Store._reader` creates, registers and reserves a connection under the store lock, then keeps its own query lock until `fetchall` finishes. Recovery and close retire readers under the same registry lock and wait for active queries before closing their connections. A failed query releases its reservation before returning to the primary connection, preserving the lock order; independent readers still execute in parallel.
- **Found on:** no game; reproduced with synthetic caches during the review of PR #2820. `test_shader_cache.Entries` pauses opening, fetching and a failed query during recovery, checks the recreated cache remains readable, and requires two independent queries to enter SQLite together.

### A changed shader library reuses an old pipeline archive

- **Symptom:** replacing a shader-library image with different bytes of the same size while preserving its modification time leaves the old pipeline archive reused without reading the changed libraries.
- **Cause:** `pso_offline.run_key` recorded only the image's path, size and modification time. That identity could remain unchanged after a timestamp-preserving write or replacement, bypassing the content-based `archive_key`.
- **Fix:** the fast key also records the inode and change time, as the image reader does (`romfs._resolve`), and its format is version 2. A changed identity goes through `archive_key`, which hashes the libraries' bytes; an unchanged image still takes the fast path.
- **Found on:** no game; reproduced with synthetic libraries during the review of PR #2820. `test_pso_offline.Build.test_a_changed_image_with_preserved_size_and_mtime_is_read_again` changes used metallib bytes inside a valid image, restores its modification time, and checks that the compiler is called again before subsequent unchanged runs are reused.

### The free-space check stops a build on a Mac that has the space

- **Symptom:** the packing script stops with `[RED] less than N GB free on the volume of <build folder>` before it unpacks the game, while Finder and the Storage settings show far more available. The Mac app step can stop with `the app needs … GB on the volume of …`, and `pso_offline.py` with `GB free on the volume of …, metal-tt needs about …` or `GB free before merging`.
- **Cause:** every check read `shutil.disk_usage` (`statvfs`), which counts only unallocated blocks. On APFS, space held by purgeable data (local Time Machine snapshots, caches the system deletes on demand) is not in it, though macOS frees that space while a write needs it.
- **Fix:** `dm/tools/vol_space.py` `free_bytes` returns macOS's `kCFURLVolumeAvailableCapacityForImportantUsageKey` for the path's volume (the capacity for writes a user asked for, queried through CoreFoundation), never less than `statvfs`'s figure, and `statvfs` alone where macOS gives none. It asks the nearest existing folder of a path not made yet. The packing script's `free_gb`, `pack_app.py`'s copy check and `pso_offline.py`'s checks before `metal-tt` and before the merge use it. Two reads keep `statvfs`: `tree_tar.pack_quiet`, housekeeping nobody asked for, which should make macOS purge nothing, and `pso_offline.py`'s diagnosis of a failed `metal-tt`, which reports what was really left. Tests: `dm/tools/tests/test_vol_space.py`.
- **Found on:** a user's APFS volume with a local Time Machine snapshot holding over 50 GB of deleted files ([PR #2257](https://github.com/seedds/nxnative/pull/2257)): `statvfs` showed 18.84 GiB free and the capacity for important usage 68.02 GiB. With the capacity, an [Ocarina of Time](../../dm/games/0400486024DEC000/README.md) v131072 `--platform mac-app` build wrote 57 GB of work and a 35.2 GB app there, with 24 GiB still unallocated at the end. Applies to every game built on a Mac.

## RomFS images

### A reboot packs a RomFS image again

- **Symptom:** the first build after restarting the Mac spends minutes in `unpack` (`[1/5] unpack v131072: 5%, 1.2/~24.4 GB`) although the game, the packer and the image are as they were: 8 minutes for a 24.4 GB image from a NUP on a network share.
- **Cause:** the stamp beside an image (`RomFS.img.inputs.json`) held `st_dev` in the image's identity, and macOS numbers a volume when it mounts it. Across one reboot the Data volume went from 16777234 to 16777232 while inode, size and both times stayed, so `reusable()` refused every game's image at once.
- **Fix:** `file_identity` leaves `st_dev` out, as the app packer's record already did. Inode, size, modification and change times still catch an image replaced or written over. An old stamp still misses the fast check, so the [NUP packer verifies the existing image](#an-old-nup-cache-stamp-makes-the-build-unpack-again) before repacking.
- **Found on:** Ocarina of Time (Switch 2, `0400486024DEC000`, packed from a NUP; PR #1299); the stamps of Star Fox and Mario Kart World show the same two numbers. `dm/tools/tests/test_romfs_image.py` remounts an image under another device number.

### An old NUP cache stamp makes the build unpack again

- **Symptom:** the next build spends minutes unpacking a NUP after a packer update even though its complete `RomFS.img` is still present.
- **Cause:** the stamp's digest holds the packers' source (`romfs_image.py` and `pack_nup.py`), and its identity has the fields `file_identity` gives; a change to either misses the fast check for every image, though neither says the image's bytes changed.
- **Fix:** on a stamp miss, `pack_nup.verified` compares the existing image with what the packer would write now: its size, its header and index as `romfs_image.layout` makes them (the bytes `write` writes, so a change of format still packs again), and each file's bytes against the SHA-256 in the NUP's table of contents. Only the image is read, not the NUP's file data. If the image is the same before and after the check, its stamp is renewed and later builds take the fast check; otherwise it is packed again. The build's unpack line ends in `reused (image checked)`.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md) v131072 (PR #1630): the 26.25 GB image took 21.6 s to check on an Apple M1 and 0.1 s to reuse on the next build, against minutes to unpack. `dm/tools/tests/test_nsp_nup.py` (`ImageReuse`) covers an old stamp, a damaged file, a wrong index, a cut-off image, an image changed during the check and an older layout.

### A commit switched and back, or another worktree, rebuilds every shader

- **Symptom:** a build after `git checkout` to another commit and back, or from another worktree of the same repository, with the translator's bytes as they were, translates every shader again: `building the whole shader map, 42,848 shaders` and 46 minutes for Ocarina of Time's Mac shaders, all from the compile cache, where `reused (inputs unchanged)` was expected.
- **Cause:** the shader step's reuse key (`build_shaders`) took the translator by where it was and when it was written: its folder `dm/gfx/tools/dmsh_xlate_bin` as path, size and modification time (`('stat', ...)` in `fingerprint`), from when the translator was a folder of .NET binaries, and its path (`str(xlate)`). Git writes a file again whenever a checkout moves between commits where it differs, and the translator differs between most chain versions, so going and coming back gave the same bytes a new time; another worktree has another path. Either missed the key, and the step removes its key and builds again.
- **Fix:** `scripts/build_app.py`: the key takes the translator by its bytes alone (`translator_key`: `('files', [xlate])`), as it takes the chain's other tools. It is one native executable that links only system libraries, 7.9 MB: 3 to 5 ms to hash. The other `('stat', ...)` inputs are extracted or provisional game files, too large to read for a key, and stay as they are. The key's form changed, so each game's first shader step after the fix translates again once.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game), its Mac app build after the checkout went to a newer `main` and back while the build ran ([PR #2496](https://github.com/seedds/nxnative/pull/2496)). `dm/tools/tests/test_nsp_chain.py` (`TranslatorKey`) takes `build_shaders`' key with the translator rewritten with the same bytes and a new time, at another checkout's path (key kept) and with other bytes (key changed).

### A stale `DM_ROMFS` path crashes the game soon after `nnMain`

- **Symptom:** a direct `dmhost` run logs `fs mount rom: → <path> (read-only)` for a path that does not exist, then crashes in the game's code a fraction of a second after `nnMain` (Echoes of Wisdom: `CRASH sig=11 addr=0x88` 0.3 s in). The host now stops at the mount instead with `FATAL the game files <path> (rom:) are missing: neither a folder nor a RomFS image`.
- **Cause:** an old run command still named the extraction's `RomFS` folder after a rebuild replaced it with `RomFS.img` (RomFS folder transfers). The read-only mount accepted any path, so every read failed and the game used the missing data. The Mac app's launcher checks its game files before it starts the host; direct runs had no such check.
- **Fix:** `mount_ex` (`dm/host/hle_fs.c`) stops on a read-only, non-save mount whose path is neither a folder nor a regular file, with the same `stat` that tells an image from a folder. The rom mount (`DM_ROMFS`, or `$DM_ROOT/romfs` when it is unset) is the only read-only mount the host makes. `dm/host/tests/t_fs.c` checks a missing path and a fifo in a forked child.
- **Found on:** Echoes of Wisdom 1.1.0 on the Mac ([issue #615](https://github.com/seedds/nxnative/issues/615), [PR #616](https://github.com/seedds/nxnative/pull/616)).

### Building creates a full RomFS tree before packing its image

- **Symptom:** packing a game's RomFS as one image still created thousands of resource files on the Mac first, and the build's scanners required the expanded folder.
- **Cause:** folder extraction followed by a separate image pack duplicates the work; ordinary filesystem APIs cannot address files inside an image.
- **Fix:** the image is written straight from the game's package: `scripts/pack_nup.py` (`pack_version`) streams each file of the NUP, checked against its SHA-256, into a temporary `DMROMFS1` image (`romfs_image.write`), which appends the sorted directory index, and publishes it by rename; nxnative's NSP extractor did the same from an NCA. ExeFS remains expanded; RomFS and each DLC remain one physical file. `dm/tools/romfs.py` gives the scanners read-only virtual paths, bounded seeks and archive mappings (Python 3.12+), without changing the process's standard filesystem APIs. The Mac app carries the image as `romfs.img`; its launcher validates it and the host mounts it in place (`dm/host/romfs_image.h`). Neither packing nor startup expands the resource files, and a `DM_ROMFS` that names a folder is still mounted as one. Full images for separate game versions cannot share unchanged individual files through APFS clones as folder extraction did.
- **Found on:** ANIMAL WELL, whose direct image is an empty root (56 bytes); Baba Is You (6,374 files in a 103,473,292-byte image, 131 shaders) and Raging Loop (all 1,473 source manifest entries match the image, and every registered shader remains in the scan), all three from NSPs in nxnative. `dm/tools/tests/test_romfs_read.py` and `test_romfs_image.py` read unaligned archive ranges and check the image's layout.

### The compile cache was unpacked for each build

- **Symptom:** a build that runs the shader step writes the compile cache's files back and removes them again, on Skyward Sword HD 24,131 files and 10,150 folders each time, Tears of the Kingdom over 900,000 entries. Removing old entries took up to half an hour on an external drive.
- **Cause:** the cache was a folder of a few files per shader, read and written by path, so a tar could only hold it between builds.
- **Fix:** `dm/tools/shader_cache.py` keeps it as one SQLite file, `cas.db`, whose entries go in and out by name, with nothing unpacked. Bytes are stored by their hash, since a library under its MSL's digest and its shader's digest was one APFS clone. `dmsh_build.py` and `dmsh_mtlcache.py` use it directly; a shader's entry is written in one transaction, so a stop leaves all of it or none. Several writers wait for each other: `dmsh_build.py`'s threads share a connection, and `regress.py`'s chain builds share their own per-game file, with [read-only reuse of the normal cache](#regression-shader-compilations-grow-the-normal-build-cache). Pruning is a query that gives its pages back. A damaged file costs the work it held and is made anew, and a full drive is one `[RED]` line. nxnative took a `cas/` folder or `cas.tar` from before this into the file at the next shader step; this fork starts from the file and has no such step.
- **Measured** on Skyward Sword HD: a 281 MB `cas.tar` became a 226 MB `cas.db`, restoring all 2,470 shaders from the cache took 6 s (9 to 13 s with the tar), and the build folder's `shader/` holds 8 files. It also ran on an exFAT volume, with three processes writing at once.
- **Found on:** Skyward Sword HD.

### Regression shader compilations grow the normal build cache

- **Symptom:** Ocarina of Time's `shader/cache/cas.db` occupies 40.8 GB: 30.4 GB of unique Mac and iOS Metal compilations, two complete generations of 42,848 per-shader records, variants and old staged outputs. Some results are useful for regression tests, but pruning old regression chain libraries does not reclaim their cache entries.
- **Cause:** `regress.py` directed baseline and candidate builders into the normal build's cache. Metal compilations and variants have no retention limit there; per-shader pruning also preserves entries written after the normal library's stamp.
- **Fix:** each game's regression runs share `<id>-work/regress/cas.db`. `shader_cache.py` reads matching immutable shader, variant and Metal entries from the normal cache through SQLite `mode=ro`, including committed WAL writes; local entries take precedence, and new outputs, staging and mutable bookkeeping go only into the regression cache. Missing or damaged fallback databases are ignored, never created or repaired. The harness runs a revision's builder with this checkout's `shader_cache.py` (`--run --readonly <shader/cache>`), so an older revision gets this cache reader without a change to its shader chain. Its default physical size budget is the larger of 8 GiB and four times the largest shader-library image in the normal build or retained regression chains; `--shader-cache-gb` sets a fixed per-game budget in GiB. Before and after a build, including a failed or reused build, cleanup removes oldest-written groups until the database fits and returns free pages without copying the database. Shader outputs, variants and split libraries leave as whole groups, identical blobs remain shared, and leftover staging is removed first. Builders hold a shared per-game lock; cleanup requires its exclusive lock, so active builds can temporarily exceed the budget. Existing results already mixed into the normal cache stay there: this change does not identify or delete them.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game).
- **Check:** `test_shader_cache.py` (read-only fallback, live WAL, forked workers, physical size, grouped eviction, failed builds, concurrent users and a writer without a live harness), `test_regress.py` (the builder's wiring, shared results across runs, automatic and explicit budgets, reused builds).

### Unused files had no one place in the build folder

- **Symptom:** Ocarina of Time's `run/pso_archive` held 13.9 GB in 99 files: 64 indexed by library file names (5.3 GB, about 33,700 pipelines, against a prewarm of under 10,000) and 35 with no index (8.4 GB) from the first week. What a build or a run no longer used was deleted in place by some steps, kept by others, and could be told apart from what was in use only by a tool.
- **Cause:** a pipeline's archive key covers its libraries' bytes (`arch_key`), so a chain change, a profile edit or an OS update leaves old pipelines no lookup reaches, and only compaction, which takes small files by tier, ever dropped any. The build's own retirements (old libraries, keys, compile caches) were deletions scattered over the build folder.
- **Fix:** one folder, `<id>_build/obsolete/`. The packing script moves what it retires there (`retire`: old chains' libraries and keys from `prune_stale_chains`, other chains' compile caches from `shader_cache.drop_generations`) into `<date time> build/` at their places in the build folder, a rename each. The host counts the pipelines taken from each archive file (`arch_lookup`, `ArchUse`), and once a start has asked for the prewarm lists' pipelines and every shader pair's pulling base (the prebuild's walk, after a chain change; or no pairs), moves the files none was taken from into `$DM_OBSOLETE/<date time> <archive folder>/` (`arch_sweep`, `arch_retire`; the Mac run command sets `DM_OBSOLETE`; the app, without it, removes them), as it already did with files indexed by library file names and files the system cannot open. Both walks are needed for every file, since a run file can hold pulling bases beside bases with a vertex layout. Not in the prebuild's bundle form, nor for files a compaction takes. A file with some live pipelines stays whole: dropping the rest means compacting it, which compiles every pipeline it keeps again (about 85 ms each on Ocarina of Time, 713-762 s for its 8,500 bases), so the sweep only counts them (`… indexed files kept, M of their K pipelines taken; F of them under a quarter used (X MB)`). Measured on Pokémon Legends: Arceus, its archive from chain 66eab9c9a6b4 under chain 19d183a2b462 (copied run folder, the prebuild tool on an M4 Pro): all 19,449 Metal compiles were byte-identical, so the prebuild took all 9,318 pair bases from the archive in 3.4 s and the line read `8 indexed files kept, 9172 of their 9339 pipelines taken; 0 of them under a quarter used (0.0 MB)`. A chain change mostly leaves the libraries' bytes as they were, so a file's pipelines live or die together, and usage-driven compaction would have freed nothing there: not built. A successful build empties the folder's entries of earlier builds and runs (`empty_obsolete`), keeps its own until the next one, and logs how much is left.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game).
- **Check:** `test_pso_archive.py` (`test_unused_file_moved_to_obsolete`: two files, a start that takes from one, the other moved with its index once both walks ran), `test_nsp_mac.py` (`test_prune_stale_chains_after_success`, `test_older_compile_caches_go_with_a_build`, `test_obsolete_emptied_by_the_next_successful_build`). On Ōkami HD's copied run folder, the prebuild tool with a current-chain library moved its archive file from an older chain (0.9 MB) to the obsolete folder and built 41 bases; the next run took all 41 from the archive and moved nothing.

### Old chains' compiles stayed in the one compile cache file

- **Symptom:** Ocarina of Time's `shader/cache/cas.db` grew to 52 GB, of which its current Mac library used 10.3 GB: about seven generations of Mac Metal compiles (31.4 GB), one of iOS (5.3 GB), three sets of 42,848 per-shader entries (one of them in use), the variants nothing reads since c8bfa161 (2.1 GB) and stopped builds' staging (1.0 GB). What a development build of another chain left could not be told apart or removed without a tool.
- **Cause:** every chain wrote into one file. The Metal compiles (`metallib/`) are keyed by the MSL, the convention and the compiler, not by the chain, so no prune could tell which were still wanted, and the packing script left them all; `shader/` entries newer than the library's list stayed as well.
- **Fix:** one file per chain version, `shader/cache/cas-<chain>.db` (`shader_cache.for_chain`). A build writes only its own file; another chain's per-shader entries never hit (their digests cover the chain), and a Metal compile it reads from an older file is copied into its own first. After a successful or reused build the packing script moves the other files whole into `obsolete/` (`shader_cache.drop_generations`, from `prune_shader_cache`; [Unused files had no one place in the build folder](#unused-files-had-no-one-place-in-the-build-folder)): older chains', and `cas.db`, the one file of every chain from before, which is the oldest generation. Nothing goes while the chain has no file of its own. `regress.py` reads the player's generations through `--readonly <shader/cache>`. A chain change copies the compiles it reuses instead of sharing them, a few GB for a large game, once.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game).
- **Check:** `test_shader_cache.py` (`Generations`: copying on read, dropping the older files after a build, a folder as the read-only cache), `test_nsp_mac.py` (`test_older_compile_caches_go_with_a_build`).

### A new compile cache on an exFAT drive is "a readonly database"

- **Symptom:** the first build of a game whose build folder is on an exFAT drive stops at its shader step, before any shader is compiled: `dmsh_build.py` fails opening `shader/cache/cas.db` with `sqlite3.OperationalError: attempt to write a readonly database` at `PRAGMA journal_mode=WAL` in `shader_cache.Store._open`, and the step ends with `[RED] own_compilers.py exit code 1`. Running the build again goes past it, as the failed run has left the file 16 KB long.
- **Cause:** SQLite notes a database file's inode when it opens it and refuses a write once its path names another inode (`SQLITE_READONLY_DBMOVED`, extended code 1032, which Python reports as a read-only database); it skips that check while the file is empty. macOS's exFAT driver (FSKit: `mount` shows `exfat, …, fskit`) gives an empty file a placeholder inode (18446744073709551598 on a disk image) and, once it has data, a lasting one. SQLite has guarded against this on Apple systems since 2017: on a volume whose type is `msdos` or `exfat`, it writes one byte (`S`) into an empty file when it opens it, before it notes the inode. On the reporter's external exFAT drive (macOS 26.6.2) the inode still changed at the first write after the open, `PRAGMA auto_vacuum` here, so the WAL pragma after it failed; plain SQLite showed it there too (on a new file, `CREATE TABLE` then `INSERT` failed at the `INSERT`). **Open:** why SQLite's guard missed there (its SQLite build, the drive, or macOS 26's driver). On an exFAT disk image under macOS 27.2, with Apple's SQLite 3.54.0 and 3.54.1 from Homebrew and the tool venv, the guard holds: a new file is 1 byte after the open and keeps its inode, and the cache passes with 400 writes, then 1,200 more from three processes at once.
- **Fix:** `dm/tools/shader_cache.py`: when `Store._open` gets `SQLITE_READONLY_DBMOVED` while it sets the file up, it opens the file again once and finishes, so that SQLite notes the inode the file now keeps. It costs nothing where the error does not come. A file that moves again fails as before. The page size, incremental vacuum and WAL stay as they were. The error's code needs Python 3.11 or newer; an older one fails as before.
- **Checked:** `test_shader_cache.py` (`Renumbered`) gets SQLite's real error by putting a copy of the file in its place after its first write: the store opens the file twice and keeps its settings through 200 writes, and fails as before when the file moves again; with `DM_EXFAT_DIR` naming a folder on an exFAT volume, the tests also run there. On the reporter's drive, an earlier form of the fix (a new file always opened again after its header) held 500 entries, then 1,200 more from three processes at once ([PR #2435](https://github.com/seedds/nxnative/pull/2435)).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game), its first Mac app build from a NUP onto an exFAT drive ([GitHub issue #2434](https://github.com/seedds/nxnative/issues/2434)). Applies to every game.

### Shader libraries take a file per shader variant

- **Symptom:** a game's shader libraries are slow to copy or delete: Skyward Sword HD's `b-<chain>/` held 12,064 files for 2,470 shaders, a third of its build folder's files, and each `regress.py` chain build held another set. A tar would not do: the host reads these files at every run.
- **Cause:** `dmsh_build.py` writes each shader's library, reflection, source and side libraries as separate files, and the host opened them by path.
- **Fix:** `dm/tools/shader_lib.py` packs the folder into one file beside its name, `b-<chain>.img`, in the RomFS image's format, flat, each file's data on 16 bytes. Nothing unpacks it: the host (`dm/gfx/nvn/msl_image.h`) keeps one descriptor and maps only a shader's pages, and the tools read it through `romfs.py`. `dmsh_build.py` still writes a folder, so the chain version does not change. The packing script packs at the end of the shader step, also on a reused step, so a folder from before this converts without a rebuild, and removes the old image only just before a build that replaces it. `regress.py` packs each chain build once it has read it. The Mac app carries the one file, without the sources and build reports, as `msl/b-<chain>.img` (`shader_lib.subset`). Each file comes from a folder beside the image first, so a partial `dmsh_build.py` run (given keys) goes over a packed library, and the next pack takes it in; a host running from a folder goes on when it is packed. Real files remain where a tool needs them: a compile's temporary files, and the libraries `metal-tt` reads, for the length of its run.
- **Measured** on Skyward Sword HD, on an external drive, warm cache: 10,017 files to one: copy 3.72 s to 0.18 s, delete 0.40 s to 0.02 s, 150 MB to 131 MB on disk. Reading all 2,470 shaders' reflection and libraries 100 ms to 28 ms. The map must be `MAP_SHARED`: on a file this size a private mapping costs about 80 µs, against 0.9 µs. A cold read has not been measured, as the cache cannot be emptied without an administrator.
- **Found on:** Skyward Sword HD.

### A Mac app packed with the library's image names it `b-<chain>.img.img`

- **Symptom:** the Mac app logs `[RED] shader library …/Contents/Resources/msl/b-<chain> (a folder or a .img file) does not exist` and then `failed to load shader`. Its `msl/` holds `b-<chain>.img.img`, and its `Info.plist` records `DMChain` as `<chain>.img`.
- **Cause:** `pack_app.py` accepts the library's folder path or image path. It used the input filename as the output stem and appended `.img` when it wrote the image. The packing script passes the folder path.
- **Fix:** use `shader_lib.name_of` for the output stem in the signed `ShaderLibraries` bundle and in its reuse key, The stem still takes the explicit `--msl-name` override and supplies `DMChain`. `test_nsp_mac_app.py` checks the signed layout and reuse across both input spellings.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game), a Mac app packed by hand from the build's `shader/cache/b-<chain>.img` ([PR #1790](https://github.com/seedds/nxnative/pull/1790)).

### A shader build leaves a file per shader output while it runs or after a stop

- **Symptom:** a game's build folder holds tens of thousands of small files while its shaders build, and keeps them when the build stops: Octopath Traveler 0's `_build`, stopped in its compile, held 68,230 files (38,376 in `tmp/dmsh_*`, 29,757 in `shader/cache/b-<chain>/`), against 105 once a build finished. Every later build made another `tmp/dmsh_*` beside the old one.
- **Cause:** `dmsh_build.py` wrote each shader's outputs into `b-<chain>/` and packed them into the image only at the end ([the entry above](#shader-libraries-take-a-file-per-shader-variant)); its cache check restored every cache hit into that folder before anything was translated; the translator wrote every missed shader's working files (`.bin`, `.spv`, `.res.json`, `.metal`) into one temporary folder before any was finished; and that folder went only when the build ended normally.
- **Fix:** `dm/gfx/tools/dmsh_build.py`. A finished shader's files go into the compile cache (`cas-<chain>.db`, under `stage/<output folder>/`) and leave the disk (`commit`); reads of another shader's outputs (a vertex shader's paired pixel MSL for `vs_pad`, the mesh step) take them from there (`output`). At the end the image is written from the staged outputs (`publish_library`, through `shader_lib.write`), with a partial build's image under it less the keys it built, and the folder and the staged entries go; when the image cannot be written, the staged outputs go back into the folder. Cache hits are restored when their shader is finished, not at the look. The shaders are translated and finished in batches of 4 × `J` (the next batch is translated while this one is finished), each in a folder of its own, and a shader's working files go as soon as it is finished. Each build's working folder holds its process ID; a later build removes a `dmsh_*` folder whose process is gone (one without the ID after a day). The packing script's progress comes from a small file the build rewrites (`DMSH_PROGRESS`), no longer from counting its files. The outputs are the same: chain `cfcc3a82c78b` against the new one, Minecraft Dungeons II's 61,655 library files and Octopath Traveler 0's 41,880 are byte for byte the same (reflection without its `chain` field), apart from `_b_cas.txt`, which lists the new chain's cache digests.
- **Measured** on an M4 Pro, every shader translated again (the chain changed), the Metal libraries from the cache: Octopath Traveler 0, 10,324 shaders, at most 405 files under `shader/` and `tmp/` (12 outside a build), 2:48 for the step (2:55 with batches of 4 × 128); Minecraft Dungeons II, 15,826 shaders, at most 3,279 with batches of 256 removed whole. Stopped with SIGKILL near the end of a compile: 40 files in `b-<chain>/` and 7 in `tmp/dmsh_*`; the next run cleared them and wrote the same library from the cache in 59 s. A partial build of 42 shaders for the Mac and the iPhone leaves one image each, also when run again over them.
- **Found on:** Minecraft Dungeons II and Octopath Traveler 0 builds, reported by the user.

### A full drive during a shader build drops finished outputs from the library

- **Symptom:** after a shader build on a nearly full drive (one `[RED] the shader compile cache … cannot be written` line), the library image lacks some outputs of a shader that built: the host finds no reflection or library for it.
- **Cause:** `commit` in `dmsh_build.py` removed each file from the disk as soon as its write into the stage had been made, inside the batch that held the shader's other files. SQLite answers a write that does not fit with `SQLITE_FULL` and may roll the whole transaction back, the writes before it too; `Store.put` turned the error into its `full` flag, and the files of those earlier writes were neither on disk nor staged, so `publish_library` left them out. A later write in the same batch ran outside any transaction and stayed, and a failed commit raised after every file was gone.
- **Fix:** `dm/tools/shader_cache.py`: a write or a commit that fails fails its whole batch, which is rolled back with `full` set, and no write is tried after that (one inside the ended transaction would land on its own). The outermost batch is tracked by the store, not by SQLite's transaction flag, which the failed write cleared. `commit` removes its files only once the batch has committed and `full` is still clear; otherwise every file stays on disk, where `publish_library` takes it. A forked worker's store (`Remote`) has `full` from the end of its batch. `dm/tools/tests/test_shader_cache.py` fills a store with a page limit inside a batch and fails a commit; `test_shader_toolchain_cache.py` stages a shader into a full store and publishes it.
- **Found on:** a code audit's reproduction with a page-limited SQLite file (2026-11-13); no build has been seen to lose an output.

### A work folder holds millions of small files

- **Symptom:** a game's `<id>-work` folder is too slow to count: Tears of the Kingdom's held 8,893,028 files and 509 GB, and its count ran past ten minutes.
- **Cause:** `regress.py` kept one whole shader build per chain version in `regress/chain` (45 there; Breath of the Wild held 57), and agents' investigations leave folders nothing reads again (`build` alone over 351,000 files).
- **Fix:** `prune_chains` in `scripts/regress.py` removes chain builds after each chain step, beyond the 3 used last, any used within 24 hours and those of the 3 newest stored baselines; a check that needs one builds it again. `tree_tar.pack_quiet` packs each other top-level folder untouched for 14 days, with 100 files or more, into `<name>.tar` at the end of a packing script or `regress.py` run. These tars keep extended attributes, so a RomFS folder's case-collision names survive, and `tar --xattrs -xf` restores them (plain `tar -xf` does not). A Python virtual environment stays a folder, as scripts run it by its path and nothing writes to it, which made it look untouched. It frees no space beyond the chain builds: a folder of APFS clones can take more as a tar, so each tar must fit with 20 GB to spare. A player's game folder has no work folder.
- **Found on:** Tears of the Kingdom.

### The zstd command given a path inside the image

- **Symptom:** the packing script stops at the shader split of a registered profile with `[RED] 13744 file(s) could not be read, their shaders are left out (first: AI/FileEntry/FileEntry.Product.100.byml.zs: CalledProcessError: Command ['zstd', '-d', '-c', '-q', '…/extract/v0/RomFS.img/AI/…'] returned non-zero exit status 1.)`.
- **Cause:** `shader_split.py`'s `unzs` read a `.zs` file through `romfs.open`, which reads inside the image, but then handed its path to the `zstd` command, which can only open real files (`Not a directory`).
- **Fix:** `unzs` feeds the command the bytes it read (`input=`). No other tool hands an external command a path inside the image. Test: `test_romfs_read.py` `test_zstd_file_inside_an_image`.
- **Found on:** Super Mario Bros. Wonder: every file of its RomFS is zstd-compressed, 13,744 left out in both versions; the first image-backed build after the folder extraction.

## Add-on content

### A registered build without the profile's DLC stops at the shader split

- **Symptom:** a game version the profile registers, packed with fewer DLC (or none, or other ones) than the profile was split with, stops at the shader split with `the split shader tables differ from game profile <id>'s`, though the packing script should derive a DLC-only profile for it (`the installed DLC shader content differs from the registered tables: using a shader-only derived profile`).
- **Cause:** `shader_split.py` writes one row per shader key, where the key was first found, and it scans in path order: `aoc/<index>/…` sorts before most game paths. A DLC that ships a copy of one of the game's shaders gave that shader a DLC row whenever the DLC was installed, and a game row when it was not. `dlc_only_shader_change` requires the game's rows (the rows outside `/aoc/`) to be the same on both sides, so a profile split with such a DLC built only with that DLC, and one split without it would not have built with it.
- **Fix:** general, in the split (`merge_keys`): a key found in both the game and a DLC is the game's row, whatever the scan order; otherwise the first copy is kept, and two different copies of one key are still red. The game's rows are then the same with or without any DLC, and the derivation rule stays strict in both directions. The profiles with DLC rows were split again with their DLC: PRAGMATA's 45 shared shaders moved to the game's rows (no other change); Mario + Rabbids Sparks of Hope (7 DLC) and FINAL FANTASY X/X-2 HD Remaster (2) came out the same; Xenoblade Chronicles 2, split here with more DLC than its profile, derived a DLC-only profile with no game row changed. `test_split_dlc_shared` (the merge: the game's copy in either order; fails without the change) and `test_nsp_incremental` `DlcOnlyShaders` (both directions with a shared shader; a profile under the old crediting is refused).
- **Found on:** PRAGMATA v196608 from a NUP with no DLC, against a profile split with `re_dlc_000.pak`, which holds 45 of the game's shaders ([issue #2439](https://github.com/seedds/nxnative/issues/2439), diagnosed by its reporter and a commenter, both splits checked on their data).

## Launcher metadata

### A game packed from a NUP or a dump shows "Ver. ?" for a build its profile registers

- **Symptom:** the game shows `?` where it shows its version (Super Mario Bros. Wonder's title screen: `Ver. ?`), and the build's lines name the version as `v327680 (?)`.
- **Cause:** a package with no control data (a NUP update, a dump) packed from a derived profile, here because the folder had no base game for the shader tables. `derive_profile` took the display version of the build row it writes from the package's `control.nacp` alone and wrote `?` without one, and the host answers `nn::oe::GetDisplayVersion` from that row by `main`'s build ID (`hle_sdk16.c`). The profile it derives from registered that very build, with its display version.
- **Fix:** `derive_profile` takes the package's control data first, then the display version the profile registers for this `main` build, and `?` only for a build no row names.
- **Found on:** Super Mario Bros. Wonder (1.2.1, v327680, an update-only NUP; `main` ff773e90…, the registered build): `Ver. ?` before, `Ver. 1.2.1` after, one Mac boot each to the title screen.

### No Game language row in an app packed from a NUP or a dump

- **Symptom:** the settings of a Mac app packed from a NUP have no Game language row, while `DM_LANG` in the environment changes the language. Reported on Donkey Kong Bananza ([NX2Apple#619](https://github.com/LNPANDY/NX2Apple/issues/619), [#659](https://github.com/LNPANDY/NX2Apple/issues/659); the reporters' packed files were not available).
- **Cause:** `settings.py` shows the row when the game's `control.nacp` lists more than one language, and two cases gave it none. A NUP update may carry no control data: the packing script's language check fell back to the base game's file, but the Mac settings got only the update's path. And there may be no NACP at all: the Yoshi and the Mysterious Book and Age of Imprisonment NUPs carry none in any package, and an FTP dump such as Bananza's has no control data.
- **Fix:** `languages_control` in `build_app.py` picks the file once (the packed version's, else the base game's), for the check and `mac_app`. With no list, `settings.py` offers every language with a note, as `game_language` and `DM_LANG` already accept any. Age of Imprisonment shows a language it lacks as English (Russian, Portuguese) and has more text languages than its voice folders suggest (Dutch, Simplified Chinese), so a game's list cannot be read from its folders.
- **Found on:** code reading and the NUP records of the two games above, with [PR #1182](https://github.com/seedds/nxnative/pull/1182); boots of Age of Imprisonment to its first settings screen. Not confirmed on Bananza by the reporters.

### A Mac front end's default settings change Metal execution paths

- **Symptom:** starting a Mac app through a front end with unchanged settings enables the encode thread, and can disable Metal 4 pipelines and the pipeline archive; starting the same app from Finder keeps the host's defaults.
- **Cause:** in nxnative the Mac's `launcher.json` reused iOS defaults from `settings.tsv`. `rec_on` in `nvn_rec.h` defaulted off on the Mac and on on iOS; `pso4_on` in `nvn_mtl.m` defaulted on on the Mac and followed the profile on iOS. The exported defaults instead enabled the encode thread everywhere and followed the profile for Metal 4 everywhere. A front end applying those values changed the Mac host's behavior without a player override.
- **Fix:** in nxnative a setting's default became a pair, `<ios>|<mac>`. This fork has the Mac only, so `dm/games/settings.tsv` carries the Mac's tested defaults directly (Metal 4 pipelines `1`, the encode thread the profile's `enc_thread`), which `dm/tools/tests/test_launcher_settings.py` checks; the host and shader chain are unchanged.
- **Found on:** synthetic metadata generation for Super Mario Bros. Wonder while reviewing [PR #352](https://github.com/seedds/nxnative/pull/352); checked against the native defaults, without a gameplay run.

### The Mac settings window stays on screen after Play

- **Symptom:** in a Mac app, the settings window stays on screen after **Play**, not responding (a spinning cursor over it), until the game ends.
- **Cause:** the window runs in the launcher's process (`dm/mac/Launcher.swift`). `finish` ordered the window out and stopped `NSApp.run`; then `launcher.c` started the host and blocked in `waitpid`, so the main thread never ran another run-loop pass. A window's order-out is committed only at the end of such a pass, and its default fade-out runs over several passes, so the window never left the screen. With the run loop kept running, the same order-out took effect at once.
- **Fix:** `finish` sets the window's `animationBehavior` to `.none` before the order-out, and `dm_mac_launcher` calls `CATransaction.flush()` after `run()` returns, before it hands back to `launcher.c`. Neither alone was enough. Check: a copy of the window with a timed Play and a `CGWindowListCopyWindowInfo` probe while the thread then blocks; the window was still listed 2 and 4 s after Play before the fix, and gone 3 times in 3 after it. `test_nsp_mac_app.py` passes.
- **Found on:** the Mac app of Breath of the Wild; applies to every Mac app.

## External drives

### The c1 guard stops on an AppleDouble file after the shader build

- **Symptom:** with the build folder on an exFAT or FAT drive, the shader step compiles every library and then stops in `c1_guard.py` with `UnicodeDecodeError: 'utf-8' codec can't decode byte …` (dmsh_build.py: `[RED] c1_guard.py failed`), reading a `._<key>_b.metal`.
- **Cause:** the same AppleDouble files as above, beside the shader build's outputs. `c1_guard.py` took every name ending in `.metal` for a shader's MSL and read the binary `._` file as text. `cb_extent.py` (every `_b.json`) skipped it only because it ignores what it cannot parse, and `dmsh_mtlcache.py` (every `_b.metal`) took `._<key>_b` for a shader, found no readable reflection for it and so filled the Metal cache from none of that folder's libraries.
- **Fix:** the three take only the names the shader build writes, `<16 hex key>_b….metal` / `.json` as `dmsh_build.py` (`OUT_KEY`) and `regress.py` already did: `c1_guard.py` `outputs` (which `cb_extent.py` uses too) and `dmsh_mtlcache.py` `OUTPUT`. None of them is part of the chain version. `dm/tools/tests/test_nsp_chain.py` runs both table tools on a folder with `._` files; the old `c1_guard.py` stops on it. On 13 Sentinels' 751 shaders both tables are unchanged.
- **Found on:** a user's iOS shader build on an external drive ([PR #555](https://github.com/seedds/nxnative/pull/555)). Applies to every NVN game.

### The Mac app step stops on AppleDouble files in its inputs, its copies and its signature

- **Symptom:** with the build folder or the app on an exFAT or FAT drive, the Mac app step stops in `pack_app.py`. The first form it takes is `no input file at <build>/shader/cache/<chain>/._<key>_b.metallib`, or `no rewriter fixups for <build>/<version>/._main.patched.bin` when the modules come first. When the inputs get past it, the copies stop with `chflags` or `Permission denied`, and the signing step stops with `codesign failed (1): code object is not signed at all` and `In subcomponent: …/Contents/MacOS/._nativenavi`, which reads like a broken launcher build.
- **Cause:** the same AppleDouble files as above. The module, shader, pipeline and font globs of `selected_inputs` took `._<name>` for a module or a library, and a `._x.patched.bin` has no `x.fixups.tsv` beside it. `shutil.copy2` of the host tried to set the copy's flags on a file system without extended attributes (`chflags: Operation not permitted`), and `cp -R` carried a folder's sidecars into the bundle, where `DMModuleFiles` listed them. `codesign` then read the `._nativenavi` beside the launcher as a nested code object that is not signed and refused the whole bundle. Signing also sets an attribute on what it signs, so the sidecar comes back after a successful signature.
- **Fix:** `dm/mac/pack_app.py` `detritus()` drops those names from `selected_inputs`, so neither the pack nor `DMModuleFiles` sees them. `copy()` passes `-X` where it copies and not where it clones (`cp` refuses the two together), and the host goes through `shutil.copy` instead of `copy2`, so a copy creates none of them. `strip_detritus()` runs before `codesign` reads the staged bundle, runs again after `xattr -cr` when `codesign` still refuses one, and runs once more after signing. On APFS nothing changes: no sidecar exists there, and the two passes are a stat walk. `dm/tools/tests/test_nsp_mac_app.py` puts a `._` file in every input folder and checks that it is not selected, does not reach the bundle, and is not in `DMModuleFiles`.
- **Found on:** the NX2Apple fork's users, packing Mac apps on an external drive ([LNPANDY/NX2Apple#486](https://github.com/LNPANDY/NX2Apple/issues/486)); reproduced on an exFAT disk image made with `hdiutil create -fs ExFAT`, where the same inputs pack, sign and pass `codesign --verify --strict` with the change and stop three ways without it. Applies to every game's Mac app.

### A second Mac app build stops with `[Errno 45]` when it replaces the old app

- **Symptom:** with the app on a Mac OS Extended, exFAT or FAT drive, the first build into a folder works and the next one that changes anything stops in `pack_app.py` `replace_app` with `OSError: [Errno 45] Operation not supported: '<app>'`. The old app stays in place.
- **Cause:** `replace_app` exchanges the new and the old app with `renamex_np(RENAME_SWAP)`, which only APFS offers: the others return `ENOTSUP`. A first build has no old app to exchange, so it takes a plain rename.
- **Fix:** on `ENOTSUP` or `EOPNOTSUPP`, `swap_by_moves` makes the state the swap leaves with three renames (the old app to `<app>.old`, the new one to `<app>`, the old one to `<app>.partial`), so the key write and its rollback do not change. A rename that fails undoes the ones before it. These volumes cannot make it atomic: a process killed between the first two renames leaves no app at `<app>`, with the old one at `<app>.old` until the next replacement clears it. APFS still swaps. Tests: `dm/tools/tests/test_nsp_mac_app.py` `test_volume_without_atomic_swap_replaces_by_moves`, `test_fallback_restores_the_old_app_when_a_move_fails` and `test_fallback_clears_an_old_app_a_killed_build_left_aside`.
- **Found on:** a user's rebuild onto an external Mac OS Extended (Journaled) drive ([LNPANDY/NX2Apple#595](https://github.com/LNPANDY/NX2Apple/issues/595), [PR #1190](https://github.com/seedds/nxnative/pull/1190)); reproduced on HFS+ and exFAT disk images made with `hdiutil create`, where the `PackReuse` tests stop with the real errno without the change and reach the fallback with it. Applies to every game's Mac app.

### External shader directories contain AppleDouble metadata

- **Symptom:** on an exFAT or FAT drive, shader splitting stops with `ValueError: not a version 2 shader code archive` or `[RED] /glslc_capture/._…: no GLSLC output`.
- **Cause:** `shader_split.py` selected captured `.glslc` programs and decoded `.ushaderbytecode` archives by extension alone. macOS AppleDouble sidecars retain that extension, but their `._<name>` files contain metadata rather than shader bytes.
- **Fix:** exclude `._` names when listing external shader directories. Other dot-prefixed names remain valid inputs, and malformed real inputs still fail their normal validation.
- **Found on:** an external-drive build reported in [issue #229's follow-up](https://github.com/seedds/nxnative/issues/229#issuecomment-6563450365). That commenter used a different, unnamed game; this fixes the sidecar failure, not the original Metroid Prime 4 port.

## Compressed inputs

### ZBIC-compressed NSO segments

- **Symptom:** the packing script or any module tool stops on `main`: `compressed with zstd (NSO flag bit 7), which this loader does not decode yet`; with the decoder but without its package, `ZBIC (zstd) segments need the zbic package (python3 -m pip install zbic)`.
- **Cause:** from system 22.0.0, an NSO may store its segments as **ZBIC**, NSO flag bit 7 for the whole module (the per-segment compression and check-hash bits keep their meaning). ZBIC is Nintendo's variant of zstd, not a container around standard frames: its frames start with the magic `ZBIC` and its FSE tables are written with binary interpolative coding, so neither `compression.zstd` nor the `zstd` command can read them.
- **Fix:** `dm/tools/nso.py` decodes such segments with the [`zbic`](https://pypi.org/project/zbic/) package (Kinnay's, zstd with Atmosphère's ZBIC changes), imported only for a flag-bit-7 module; every segment is still held to the header's size and SHA-256. zstd has no fixed ratio bound, so a ZBIC segment is held only to its own size, where an LZ4 one is also held to 255 bytes per stored byte. Install it with the other tools (README, step 1). The packing script checks for it before it extracts anything, as it does for its other modules, because it first reads a module at the rewrite, after the whole RomFS is unpacked.
- **Check:** Well Dweller's `main` decodes to 85,370,056 bytes with segments `0x39680d0 / 0x9f7e74 / 0x9b1930`, every SHA-256 matching; `dm/tools/tests/test_nso.py` checks that a flag-bit-7 module whose segments are not ZBIC is an Error naming ZBIC.
- **Found on:** Well Dweller (SDK 22.2.0).

## Versions with different modules

### A version without one of the profile's modules stops the host at boot

- **Symptom:** `FATAL open <folder>/subsdk1.fixups.tsv` right after the host starts, for a version that has no such module.
- **Cause:** a game's versions can differ in modules: Mario Kart World's base game has `main`, `subsdk0` (a Mono runtime) and `sdk`, its update 1.8.0 `main`, `subsdk0` (the movie player), `subsdk1` (a C library) and `sdk`. The host, the rewrite and the shader split all took the one `modules` list of the profile.
- **Fix:** `modules` lists all of them in load order, and each `build` row names its own (`game.py` `build_modules`; a row naming one `modules` lacks is an error). The host loads the modules of the row of `main`'s build, read from the rewriter's `main.fixups.tsv` (`main.c` `profile_modules`, from `DM_GAME_BUILD_MODULES`), and all of `modules` for a build with no row. `game.py modules <id> <folder>` prints the same list. The packing script rewrites, sizes `mem_used` from and splits the modules the packed version's ExeFS holds (`Game.modules_in`), and a derived profile's row names those (`derive_profile`).
- **Found on:** Mario Kart World: the base game boots with its three modules from a profile that lists four. Applies to every game. `test_game_profile.py` checks the rows and the list.

## Package identification

### A game file whose extension is in capitals is not found

- **Symptom:** the build stops with `no NUP (a .nup file) in <folder>` for a folder holding `Game.NUP`, on any Mac volume; renaming it to `.nup` makes the build go on.
- **Cause:** the script listed the folder with `Path.glob`, which compares case-sensitively on every POSIX system, a case-insensitive Mac volume included.
- **Fix:** `files_with_suffix` (`scripts/build_app.py`) lists a folder's files by their lowercased extension, and the scan for the game's NUP (`nup_file`) goes through it.
- **Found on:** NX2Apple, [LNPANDY/NX2Apple#554](https://github.com/LNPANDY/NX2Apple/issues/554) (Tears of the Kingdom, an NSP named `.NSP`). This fork's one input, the NUP, is found the same way.

### A derived profile leaves out a module that moved to another slot

- **Symptom:** a version a profile was not brought up on crashes at its first movie: `UNIMPL _ZN5movie9ExtractorC1ENS_13ContainerTypeE`, then `CRASH sig=11` ([issue #1211](https://github.com/seedds/nxnative/issues/1211)). The derived profile's `modules` has only `main sdk`.
- **Cause:** `derive_profile` could only take modules out of the profile's list, but a module's slot belongs to a build, not to a game: Absolum's movie module is `subsdk2` in 1.1.2, where `subsdk0` is NVIDIA's Vulkan driver, and `subsdk0` in 1.2.1.
- **Fix:** `derive_profile` adds what `main_modules` (`scripts/build_app.py`) finds: a module the list leaves out that exports something `main` imports, which no listed module and no host hook supplies, and never a GPU driver. The added module goes in the version's `build` row too, since the host loads what the row names. Checked on 9 games' real modules with their registered lists: nothing is added (Super Mario Galaxy 2's GLSLC and `nn::pcm`, which the host supplies, stay out), and each of the 7 subsdks taken out of a list comes back. A registered build keeps its row: the rule runs only when a profile is derived.
- **Found on:** Absolum 1.2.1, from the reporter's logs: with the module added by hand the game reached gameplay at 60 fps. No 1.2.1 files on this Mac: not run here.

### A derived profile loads only the modules its version ships

- **Symptom:** the packing script stops at its rewrite stage with `FileNotFoundError: … extract/v0/ExeFS/subsdk1` while packing a version the profile was not brought up on; the extraction has every other module.
- **Cause:** `derive_profile` in `scripts/build_app.py` gives the derived profile this version's `build` row, made only from the modules its ExeFS holds, but copied `modules` unchanged. A version that ships fewer modules than the registered one (an older base game before an update added a module) then names a module the rewrite and the host try to load.
- **Fix:** `derive_profile` keeps in `modules` only those the version's ExeFS holds, with a comment naming the ones left out; a version that ships them all keeps the line as it is, and `shader_only` derivations are unchanged. The host is built from the derived profile, so it loads the same list.
- **Found on:** Mario Kart World 1.0.0 (`0400C3F00006E000`, a base-game dump: `main`, `subsdk0` and `sdk`), packed from a profile for 1.8.0, whose `subsdk1` is the C library module the update added ([PR #1081](https://github.com/seedds/nxnative/pull/1081)). With it the rewrite, the shader split (11,561 shaders) and the Mac host built, and the game drew its first course on the Mac.
- **Check:** `test_nsp_incremental` (`test_a_module_the_version_does_not_ship_is_left_out`: the module left out with its comment and its build row, then kept once the version ships it).

## Damaged packages

### A build that allows damaged files splits and restores every shader again

- **Symptom:** every build with `--allow-damaged` runs the shader split and restores every shader from the compile cache, though nothing changed: about 56 s of split and 9½ minutes of shaders (42,848, about 75 a second) for Ocarina of Time on an M3 Max, each build.
- **Cause:** `split_shaders` gave a damaged copy no key (`key = None if ALLOW_DAMAGED`): a good copy that replaces a damaged one keeps every file's path and size, all that the RomFS input (`('tree', …)`) sees, so that key would have kept the damaged split. The shader step takes the package's key as its input, so it never reused its libraries either.
- **Fix:** a damaged copy is keyed as the same extraction: its RomFS by its files' times (`('stat', …)`, which an extraction writes again; inside `RomFS.img`, the image's) and by `check_formats`' list of damaged files (`RomFS.img.formats`). A build of the same extraction reuses the split and the shaders; a new extraction (a repaired copy) or another damage list splits again. An undamaged build's key is as before, and damaged and undamaged builds never take each other's split.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game), v131072 built with `--allow-damaged`, which a contributor kept on after replacing a NUP with three damaged textures ([A damaged file in a NUP or a dump has no hash to fail](#a-damaged-file-in-a-nup-or-a-dump-has-no-hash-to-fail)): the option alone, with no file damaged, took this path. `dm/tools/tests/test_nsp_incremental.py` (`SplitShaders.test_damaged_reuses_only_the_same_extraction`).
