# Services and SDK calls

SDK calls and system services the host answers (`dm/host/hle_*.c`). Each entry: symptom, cause, fix, the games it was found on. The [symptom index](../agents/symptoms.md) lists every symptom.

## Service connections

### SDK calls that open a system service through sm

- **Symptom:** `sm::Initialize` aborts right after `ConnectToNamedPort` (SVC 0x1F) and `SendSyncRequest` (0x21); abort inside `nn::sm::Initialize`, the log showing `SVC 0x1f` (ConnectToNamedPort, port name `sm:`) and `SVC 0x21` answered by placeholders, then an `nn::diag` abort; abort with no message at start-up in a service call the host has no hook for (`Break` from `sdk+…` with an `nn::diag` backtrace).
- **Cause:** an SDK path reached a system service the host doesn't replace: the SDK's IPC to the service fails and it calls `AbortImpl`. Often it is an SDK call the host does not hook, for example a newer overload of a hooked call.
- **Fix:** hook the public SDK entry point named in the backtrace (`HLE_FORCE` in the relevant `hle_*.c`). Symbolize the abort backtrace against the SDK's exports to find the caller (resolve the frames with `sdis.py --sym` on the decompressed module) and hook that name. List the game's imports of that service the host does not hook ([Listing a game's unhooked imports before they are met](#listing-a-games-unhooked-imports-before-they-are-met)) and add the ones that talk to a service; library helpers that only fill the game's own buffers need nothing. Look at how the game uses the result before choosing an answer.
- **Found on:** Super Mario Galaxy (SDK 18), on an SDK 18 overload of a call the host hooked in its older form; Super Mario Odyssey (SDK 7), on four calls in a row.
- **Note:** the same abort from other services: the shop service accessor's requests ([Shop service accessors](#shop-service-accessors)), `oe::FinishStartupLogo` ([The startup logo](#the-startup-logo)), `hid::VibrationNode::Update` ([Vibration values flushed by the SDK's vibration graph](#vibration-values-flushed-by-the-sdks-vibration-graph)), `audio::GetAudioDeviceOutputVolume` ([Audio device output volume and names](audio.md#audio-device-output-volume-and-names)), and the rest of this file.

### Listing a game's unhooked imports before they are met

Most service calls can be found before they crash, before the first boot or the next one: the calls that would abort in `sm::Initialize` (or read a null service object) are in the import list.

- **Procedure:** list `main`'s `nn::` imports (its undefined imports) that no host hook names, by namespace: the survey's import table (`nso_syms.py`), then `main`'s undefined `nn::` symbols that no hook (`HLE` / `HLE_FORCE`) names, and read each one's SDK code. This gives the calls a game will make before they are met. The import list itself says where to look: diff the undefined symbols against the closest title the host already runs (and every other game's imports), drop what the host hooks, and the rest are the candidates. To find which `sdk` function aborted, map the backtrace offsets to the nearest exported symbol (The Legend of Zelda: Tears of the Kingdom 1.4.3). For an update of the game, diff the undefined dynamic symbols of the two `main` modules before the first run, and read the call sites before choosing answers (Super Mario Bros. Wonder 1.2.1 added 28 imports).
- **What needs nothing:** most `nn::os` / `nn::mem` imports run natively in `sdk`. Calls that are pure computations need nothing, nor do socket calls behind a `Socket()` that already fails offline, nor library helpers that only fill the game's own structures.
- **Hook names:** hooks are `HLE`, `HLE_FORCE`, `SKF`, `SSF` and `SSC` across `dm/host` and `dm/gfx`. `strings` misses names the symbol table stores as the tail of a longer one, so list them with `nso_syms.dynsyms`.
- **The survey table's blind spots:** it counts only names given to `HLE` / `HLE_FORCE` directly: hooks made through macros (`SKF`, `SSF` and `SSC` in `hle_net.c`) show as missing. It once listed every vi call as unhooked: `nso_syms.py host_hooks` read only `dm/host`, and the vi hooks are in `dm/gfx` (it reads `dm/gfx` and `dm/gfx/nvn` now; found on Absolum).
- **Found on:** Pokémon Sword (SDK 7: the import list against the hooks and every other game's imports named all 33 calls beforehand), Monster Hunter Rise (SDK 11), Pokémon Legends: Z-A (SDK 19.3.11: 86 candidates, most of which only fill the game's own structures) and a dozen other games brought up by nxnative. The hooks added for them that this game does not reference were removed with the fork.

### Game-linked HIPC clients of system services

- **Symptom:** abort in `sm::Initialize` under `sf::hipc::InitializeHipcServiceResolution`, right after the first frames; since that fix, `[RED] sf: the game connects to service <name> itself, which the host does not serve`, then an abort with `Result=0xe15` (`caps:su` in Super Smash Bros. Ultimate's single-player mode, `notif:a` when Fit Boxing 3 opens its Settings).
- **Cause:** `main` or `sdk` links its own clients of system services (`nn::sf::hipc`), which connect through `sm` and talk HIPC through `svcSendSyncRequest`; the host has neither, and a failed connect aborts.
- **Fix:** `hle_sf.c` takes over the SDK's HIPC client entry points (`InitializeHipcServiceResolution`, `ConnectToHipcService`, `SendSyncRequest`, `CloseClientSessionHandle` and the control requests `QueryPointerBufferSize`, `ConvertSessionToDomain`, `DuplicateSession(Ex)`). A service in its fixed list (`sf_served`: `notif:a`, `caps:su`, `caps:u`) gets a host session, and every request on it succeeds with zeroed output and no objects or handles. Any other name is refused with the red line and `0xe15`, as `sm` refuses a service nobody registered. `DM_SF_TRACE=1` dumps each request. No service has answers of its own: a service that needs them is added to this file with its answers, not to the list.
- **Capture services:** Super Smash Bros. Ultimate links clients of `caps:su` and `caps:u` (screenshots and clips) and aborts with `Result=0xe15` when `sm` refuses them at the start of its single-player mode. The host has no album: a list reads as empty and a save does nothing.
- **Reminder alarms:** `nn::notification`'s alarm calls (`ListAlarmSettings`, `RegisterAlarmSetting`, `UpdateAlarmSetting`, `DeleteAlarmSetting`, `LoadApplicationParameter`), which most SDKs link, connect to `notif:a` on their first call and abort on any failure: Fit Boxing 3 2.0.0 (SDK 21.4.4) lists them when its Settings open. The client sends only commands 1000 (Initialize, with the process ID), 500, 510, 520, 530 and 540 (SDK 21: `sdk+0x58ac80`..`0x58ad10` in Splatoon Raiders 1.1's `sdk`); the notification event comes from `am`, not from this service. The host schedules no alarms, so `notif:a` is served: a list is empty and leaves the caller's array as it is, a registration succeeds with ID 0 and never fires, a parameter loads 0 bytes.
- **Check:** `make -C dm/host/tests build/t_sf`, then `dm/host/tests/build/t_sf`: requests on `caps:u`, `caps:su` (with a process ID, arguments and an input buffer) and `notif:a` (as a domain) succeed with zeroed output and leave the input buffer untouched, a duplicate answers as its session does, and a name outside the list is refused.
- **Found on:** Super Smash Bros. Ultimate (capture services); Fit Boxing 3 2.0.0 (`notif:a`, PR #1974); first on Animal Crossing: New Horizons (SDK 20.5.4), whose `olsc:u` client this fork no longer serves.

## File system and save data

### Directory handle allocation failure

- **Symptom:** the host crashes in `h_fs_OpenDirectory` when its folder-backed directory handle allocation fails.
- **Cause:** `opendir` succeeded, but the following `calloc` of `dirh_t` was dereferenced without a null check. Returning early without cleanup would also leak the already-open `DIR`.
- **Fix:** close the directory on allocation failure, preserve `errno` across cleanup, and return the existing filesystem failure through `err_res` before publishing a handle. The caller's output stays untouched, as on the other failed-open paths. `t_fs_directory.c` injects allocation failure in the real handler, checks the descriptor is closed and the output unchanged, then exercises successful open, count, read and close.
- **Found on:** the [GCC audit in issue #313](https://github.com/seedds/nxnative/issues/313#issuecomment-6523656102), reproduced with a synthetic directory and allocation fault injection; no game-specific failure was reported.

### A mount in the SDK's own table stays until the SDK releases it

- **Symptom:** `game called nn::diag abort: Result 0x7802` (`MountNameAlreadyExists`) when a game mounts a RAM disk under a name it has just unmounted.
- **Cause:** the host's mount table is permanent and `nn::fs::Unmount` did nothing. `nn::fs::MountRamDisk` has no host version, so it runs in `sdk` and registers in the SDK's own table, and the no-op left that entry there while the game freed the disk's buffer.
- **Fix:** `h_fs_Unmount` leaves a host mount alone and sends any other name to the SDK: its `IsMounted`, then its `Unmount` if it holds the name (the SDK's `Unmount` aborts on a name it does not hold). `guest_sym` gives the module's own definitions, not the host's take-overs. A name in neither table stays a no-op. `t_fs.c` covers each case.
- **Note:** the file calls on such a mount now reach the SDK too: [File calls on a mount in the SDK's own table](#file-calls-on-a-mount-in-the-sdks-own-table).
- **Found on:** Paper Mario: The Thousand-Year Door ([GitHub issue #1012](https://github.com/seedds/nxnative/issues/1012)).

### File calls on a mount in the SDK's own table

- **Symptom:** `game called nn::diag abort: Result 0x202` (path not found) right after `fs path not found: <name>:/...` lines (`DM_FS=1`) for a mount name no `fs mount` line ever named.
- **Cause:** `nn::fs::MountRamDisk` runs in `sdk` and registers in the SDK's own mount table ([A mount in the SDK's own table stays until the SDK releases it](#a-mount-in-the-sdks-own-table-stays-until-the-sdk-releases-it)), while every file call the host takes over looked in the host's table only. Nintendo Switch Sports Resort mounts its VoiceText speech data as the RAM disk `vtapi`, copies `VoiceText/` from `content:` into it at boot and aborted on its first `GetEntryType` (`main+0x414dbc`).
- **Fix:** a path whose mount name the host does not hold but the SDK's `IsMounted` does goes to the SDK's own call (`sdk_path_call` in `hle_fs.c`; `guest_sym` gives the module's definition, not the host's take-over), with no host lock held. The file and directory handles that call opens are listed (`sdk_handle_add`, up to 256 open at once; past that the open is closed in the SDK and fails), and the calls that take a handle go to the SDK when it is listed; a close forgets the handle before the SDK frees it. `IsPathMounted` answers from both tables. A rename between the SDK's mount and another fails without reaching either. A path on a host mount never asks the SDK. `t_fs.c` (⑩) covers routing, handle tracking and isolation.
- **Note:** Paper Mario: The Thousand-Year Door's file cache (the RAM disk `cache`) takes this path as well: its `CreateFile` on `cache:/<hash>` was "path not found" and the game skipped the cache (its note); not checked on that game.
- **Found on:** Nintendo Switch Sports Resort (`04008E001F098000`).

### File handles with low bits set, and backslash paths

- **Symptom:** a 10-byte read of the wrong RomFS file, then a null pointer at boot; files named `rom:\StartupUI.pak` are not found.
- **Cause:** on Horizon a `FileHandle` is a pointer to the SDK's `FileAccessor`, a heap object, so its low bits are clear, and a game's file device may mask them off (`handle & ~7`) before `ReadFile`. The host's RomFS-image handle kept the entry index in its low bits, so entry 7 was read as entry 0. Separately, Horizon's file system accessor turns every backslash in a path into a slash before it normalizes the path (`FileSystemAccessor::SetUpPath`, on every mount except the PC host's); the host treated a backslash as part of a name.
- **Fix:** the guest gets the host's handle shifted left by 4, 16-byte aligned like an AArch64 heap block (`FH_OUT` / `FH_IN`). Each guest path resolver (`img_path`, `host_path_ex`, `set_guest_name`, `dir_snapshot`) turns backslashes into slashes first, so overlays, `..` and guest names see the same path (`hle_fs.c`; `dm/host/tests/t_fs.c`).
- **Found on:** Metroid Prime 4: Beyond (SDK 19; bring-up in [issue #229](https://github.com/seedds/nxnative/issues/229), from [PR #513](https://github.com/seedds/nxnative/pull/513)); not in the games table yet.

### An unhooked `fs::ReadFile` overload falls through to the SDK's own

- **Symptom:** a fault inside `sdk` at boot, right after the save data is mounted: `ldr w8, [x0, #0x24]` with `x0` holding a host file handle (SD GUNDAM G GENERATION CROSS RAYS: `sdk+0x62a78`, `x0 = 0x4000000000000390`), while `GetFileSize` on the same handle answered just before.
- **Cause:** the game imports `nn::fs::ReadFile(FileHandle, s64, void*, size_t, const ReadOption&)`, the overload with read options and no bytes-read output, which the host did not hook, so the call bound to the SDK's own. That one reads the handle as a `FileAccessor*`, and the host's handle is an image-entry id ([as above](#file-handles-with-low-bits-set-and-backslash-paths)). The general case: [SDK calls that open a system service through sm](#sdk-calls-that-open-a-system-service-through-sm); the import list finds such overloads beforehand ([Listing a game's unhooked imports before they are met](#listing-a-games-unhooked-imports-before-they-are-met)).
- **Fix:** a hook with the contract of the overload without read options (`h_fs_ReadFileExactOpt` calls `h_fs_ReadFileExact`): the options are ignored and a short read is a failure, as on Horizon, since the caller has no byte count to see it by (`hle_fs.c`; `dm/host/tests/t_fs.c`).
- **Found on:** SD GUNDAM G GENERATION CROSS RAYS (`010055700CEA8000`, SDK 9.4.1, from [PR #947](https://github.com/seedds/nxnative/pull/947)): the fault was all that stood between the boot and its frame loop; not in the games table yet.

### C library path checks ask the file system's limits

- **Symptom:** Addressables never start (no `StreamingAssets/aa/settings.json` in the `DM_FS=1` output at all), then a null asset crash (`main+0x31100ec`).
- **Cause:** Unity 2022's C# file API reaches the SDK's C library, not `nn::fs`: `File.Exists` → `SystemNative_Stat` → `stat` = `open` + `fstat` + `close` (`sdk+0x948b0`). nnmusl's path check (`sdk+0x904e0`, then the converter `sdk+0x8ef50`) asks `nn::fs::IsPathMounted`, `GetPathLengthMax`, `GetUtf16PathLengthMax`, `GetEntryNameLengthMax` and `GetUtf16EntryNameLengthMax` before it calls `nn::fs::GetEntryType` / `OpenFile`, and the SDK's own versions read the empty mount table (`IsPathMounted` false; the next one aborted with Result 0x35f202).
- **Fix:** the host answers them from its mount table, with Horizon's 0x300-byte limits and no UTF-16 limit (`hle_fs.c`). The path .NET builds is `/rom:/…`; nnmusl's converter turns it back into `rom:/…`.
- **Found on:** Ace Attorney Investigations Collection (1.0.0.2, SDK 17.5.3, Unity 2022.3 IL2CPP).
- **Note:** armyja's fork (GitHub issue #18) patched the managed stat wrappers by address instead; these hooks need no per-build table.

### Paths with `.` and `..` components

- **Symptom:** an Atk task aborts in a `switch` default (`UnexpectedDefaultImpl`, then `AbortImpl`) while a stream sound loads.
- **Cause:** the stream path was `rom:/system/snd/../../sounds/streams/…`, and the host answered "not found" for any `..` component. Horizon's path normalizer resolves `.` and `..` lexically and fails only above the mount root.
- **Fix:** `host_path_ex` now does the same (`norm_rest` in `hle_fs.c`).
- **Found on:** Metroid Dread (`main+0x1225a8c`).

### RomFS lookups on large directories

- **Symptom:** a long black screen at boot with nothing in the log (Engage: about 17 s on the Mac, 32 s on an iPhone); sampling the process (`sample <pid> 3`) shows `getxattr` under `path_component` at the top of stack.
- **Cause:** the game is walking RomFS, and every path component scanned its whole parent directory. That scan maps the game's case-sensitive names onto APFS, so it calls `getxattr` on each entry, and Engage has directories of 38,000 files. The rest of the time was the listing itself: `ReadDirectory` called `stat`, `getxattr` and a failing `fopen("<file>.holes")` for every entry.
- **Fix:** read-only mounts now use a per-directory name index built at the first lookup (`dir_index_get` in `hle_fs.c`), which also speeds up every file Wwise opens during play. In listings, now only `.dm-case-*` names (the only ones that carry the xattr) read it, directories take their type from `d_type`, and files use `fstatat` / `openat` relative to the directory.
- **Found on:** Fire Emblem Engage: with the name index the first frame came at 5.7 s on the Mac; with the listing fix too it comes at 1.8 s on the Mac (9.9 s → expected about 3 s on an iPhone), and the opening movie starts at 7 s instead of 49 s.

### ReadFile into write-protected texture pool pages

- **Symptom:** `[RED] fs ReadFile into … failed at +0 (EFAULT): VM region … protection 1`, now and then.
- **Cause:** the destination was texture pool memory, which the dirty-page tracker write-protects after each upload (`nvn_dirty.c`). `ReadFile` lifts the protection first (`dm_guest_write_prepare`), but the graphics layer can protect the pages again before `pread` writes them, and a system call gets EFAULT where a plain write would fault into the tracker's handler; at 60 fps uploads come twice as often.
- **Fix:** on EFAULT the host now prepares the rest of the buffer again (unprotect, mark dirty, so the texture is uploaded again) and reads on, up to eight times (`h_fs_ReadFile`; the first case is logged, `[fs] ReadFile … prepared again`).
- **Found on:** Monster Train 2 at 60 fps: two runs in three as the route map loads, never at 30 fps.
- **Check:** four runs at 60 fps: one retry, no failed read.

### File-not-found noise from optional paths

- **Symptom:** `fs … not found` lines with `DM_FS=1`.
- **Cause:** games probe many optional paths (debug parameters, other-language voice files).
- **Note:** only a missing file followed by a failure matters.
- **Found on:** every game (general).

### Directory delete and rename calls

- **Symptom:** a missing `fs::DeleteDirectory`; undefined `nn::fs::` imports with no hook, found from the import list ([Listing a game's unhooked imports before they are met](#listing-a-games-unhooked-imports-before-they-are-met)) before they were met.
- **Fix:** hooked: `fs::DeleteDirectory` (an empty directory), `fs::DeleteDirectoryRecursively` and `fs::RenameDirectory` (the same rename as `RenameFile`, `rename_any`) (`hle_fs.c`).
- **Found on:** Metroid Dread (SDK 11: `fs::DeleteDirectory` was missing); The Great Ace Attorney Chronicles (SDK 10.4.1: `RenameDirectory`).

### Save-write failures stay with their backing transaction

- **Symptom:** a failed write in one independent save can make another save's next `Commit` fail and discard its successful changes; the damaged save may then commit its truncated working file.
- **Cause:** the host used one process-wide failure marker, consumed by whichever save committed first.
- **Fix:** each canonical backing save owns its failure state. Open file handles retain that transaction identity, aliases share it, and each commit waits for in-flight writes or size changes to its backing save before consuming or restoring its failure marker (`hle_fs.c`). Concurrent first writes initialize the shared failure-injection settings with `pthread_once`.
- **Check:** `t_fs_commit` injects write failures after truncation in either of two independent saves, verifies that the other save commits its changes, and checks failure propagation through aliases, rename failure handling, and a failed recovery clone. It blocks writes and size changes through an alias while another save commits, then verifies that `Commit` waits for the affected I/O and refuses its failure. `make -C dm/host/tests fs-tsan` also checks concurrent first writes and failed file I/O concurrent with mounting another alias.
- **Found on:** the [two-save host regression](../../dm/host/tests/t_fs_commit.c). Mario Kart 8 Deluxe uses independent device and account saves.

### A failed save path operation still allowed the save to commit

- **Symptom:** after an unexpected host error while creating, opening for writing, deleting or renaming a save entry, `Commit` could publish the other changes in the working directory without the failed change.
- **Cause:** writes and size changes through file handles marked the backing transaction failed, but path lookup and most path mutations did not. A recursive delete also continued after a child failed, letting the next directory read replace its error.
- **Fix:** unexpected mutation failures mark the transaction by its exact guest mount name, even when lookup failed before a physical path existed. Aliases share the backing transaction's marker; read-only and non-save mounts do not mark it. Ordinary missing, existing, type, not-empty and invalid-name results (what Horizon answers too) remain unmarked; a rename whose name metadata and rollback both fail marks it whatever the first error, since the entry stays at the new path. Recursive deletion checks the child result as well as the saved directory-read error before returning, restoring that error after closing the directory; deletion calls `rmdir` only after every child succeeded. This also keeps the analyzer from treating a failed child followed by a successful `rmdir` as a failure with undefined `errno`. The existing commit refusal restores the committed version and notifies the front end; the next complete save can succeed.
- **Found on:** the [synthetic save-mutation regression](../../dm/host/tests/t_fs_mutation.c), following the filesystem lead in [issue #1692](https://github.com/seedds/nxnative/issues/1692) for [Ocarina of Time](../../dm/games/0400486024DEC000/README.md). The cause of that game's area-transition crash and subsequent black screen remains unconfirmed; this correction does not establish that connection or repair an already damaged save.

### `DeleteFile` on a directory refused the save's next commit

- **Symptom:** `fs unlink <path> failed errno=1` in the log, then `[RED] save commit refused: ... errno=1` at the game's next `Commit`: that commit's changes are discarded (the committed version stays, the front end is told), and every commit after another such call is refused too. The game's `DeleteFile` call returned a generic failure.
- **Cause:** a directory is not a file to Horizon's save data, which keeps files and directories in separate tables: `DeleteFile` on a directory finds no file, answers `PathNotFound` and changes nothing (as LibHac's save file system answers; `OpenFile` on a directory here already answers `PathNotFound`). `h_fs_DeleteFile` called `unlink(2)` on the path, which on Apple systems fails with `EPERM` for a directory (Linux gives `EISDIR`). `EPERM` is not one of the guest errors in `fs_guest_error`, so the [save path rule](#a-failed-save-path-operation-still-allowed-the-save-to-commit) took it for the host's error and refused the commit.
- **Fix:** general, `h_fs_DeleteFile` in `hle_fs.c`: when `unlink` fails with `EPERM` or `EISDIR` and `lstat` shows a directory, the call answers `PathNotFound` (logged under `DM_FS=1`) and the transaction is not marked. Any other `unlink` failure, `EPERM` on a file among them, still refuses the commit.
- **Check:** `t_fs_mutation` deletes a real directory as a file in a transactional save with no fault injected: the call answers `PathNotFound`, the directory and its child stay, and the save commits. An `EPERM` injected into the `unlink` of a file still refuses the commit.
- **Found on:** upstream nxnative `5b5504ab` ([PR #3329](https://github.com/seedds/nxnative/pull/3329)), from the bring-up report for The Binding of Isaac: Repentance in [issue #2144](https://github.com/seedds/nxnative/issues/2144), whose log has one `fs unlink ... save.work failed errno=1` (on a build from before the save path rule). Whether the deleted path was a directory is not shown in the issue.

### A save folder that cannot clone directories

- **Symptom:** `[RED] save transaction: cloning the work directory failed (…, errno=45)` when the save folder (`DM_SAVE`) is on an external drive, then a read-only save mount and every save write failing (South Park: `profile.sys`); now the line reads `the save folder's filesystem cannot clone directories (save transactions need APFS …)`.
- **Cause:** a save transaction clones the committed folder into its work folder with `clonefile` and publishes a commit with `renamex_np(RENAME_SWAP)`. Both need APFS: on HFS+ and exFAT disk images both fail with `ENOTSUP` (45), and neither format advertises `VOL_CAP_INT_CLONE` or `VOL_CAP_INT_RENAME_SWAP`, so copying the files instead of cloning them would still leave no atomic commit. The host already failed safely (the committed save mounted read-only, `front_save_failed` called); the line did not say why. The Mac app's own save folder is on APFS (`~/Library/Application Support/NativeNavi/<title ID>/save`); only a `DM_SAVE` set by hand or a development run's work folder can be elsewhere.
- **Fix:** `hle_fs.c` names the cause when `clonefile` returns `ENOTSUP`: set `DM_SAVE` to a folder on an APFS volume (the RomFS and shader libraries may stay on the other drive). Recursive deletes (`rm_tree`, `DeleteDirectoryRecursively`) now take each entry's type from `lstat`, not `d_type` (which a filesystem may report as unknown), unlink a symlink without entering it, and refuse a symlink given as the tree itself; a commit whose leftover `.new` cannot be cleared is refused with its own red line instead of failing in the clone.
- **Check:** `dm/host/tests/t_fs.c` (⑧) makes `clonefile` fail with `ENOTSUP` (read-only mount, one front-end notice, committed save unchanged, writable again once cloning works) and deletes save folders holding a symlink to a folder outside the save (the target keeps its files).
- **Found on:** South Park: The Fractured But Whole 1.05, whose port is [PR #662](https://github.com/seedds/nxnative/pull/662) (not yet in the games table): a development Mac run with its save folder on a Journaled HFS+ external drive.

### A rename between two mounts

- **Symptom:** `RenameFile("save:/a", "rom:/a")` succeeded and wrote into the read-only RomFS folder; a rename between two writable mounts, or between two names of one host save, moved the file.
- **Cause:** `rename_entry` in `hle_fs.c` checked that the source's mount is writable and resolved the destination without looking at its mount. Horizon's `fs::RenameFile` and `fs::RenameDirectory` find each path's file system by its mount name and refuse two before touching either (Atmosphère's `fs_user_filesystem.cpp`: the two accessors must be one, else `ResultRenameToOtherFileSystem`, module 2 description 6034); only a rename between the SDK's own mount and the host's was refused, with `RES_FAIL`.
- **Fix:** `rename_any` compares the two mount names (the part before `:`, as `FindFileSystem` takes it) and answers `0x2F2402` for two, before the SDK or the host is asked; one mount's rename goes on as before, and a read-only source is refused by its own check. Two mount names of one host save (one folder and one transaction) are two mounts on Horizon too, so a rename between them is refused as well. `make -C dm/host/tests run` (`t_fs`, ⑦b) renames into a read-only mount, into another writable one and between two names of one save, and checks both paths afterwards.
- **Found on:** a code audit's reproduction (2026-11-13); no game has been seen to rename between mounts.

### A folder that cannot be read is listed short

- **Symptom:** after a read error on a folder (`EIO`, an external drive going to sleep), files of a read-only mount are not found for the rest of the run; a recursive delete succeeds with files left; a listing or count is short with no error.
- **Cause:** `readdir` returns NULL both at a folder's end and on a failure, and only `errno` tells them apart. Every loop in `hle_fs.c` took NULL for the end: the name index of a read-only folder (`dir_index_get`) was kept for the whole run without the names after the failure, the path walk answered "not found", and the recursive delete, the listing (`ReadDirectory`), the count and the overlay snapshot went on with what they had.
- **Fix:** `dir_next` in `hle_fs.c` gives the next entry without `.` and `..`, and NULL with `errno` 0 at the end or set on a failure; the name index, the path walk, the recursive delete, `ReadDirectory`, `GetDirectoryEntryCount` and the overlay snapshot (`OpenDirectory`) use it and fail on a failure. A name index that could not be read is not kept, so the next lookup reads the folder again. `make -C dm/host/tests fs-directory` (`t_fs_directory`) fails a folder's reading at once and after one entry in each of them.
- **Found on:** a code audit's reproduction with an injected `EIO` (2026-11-13); no game log has shown it.

### Opening a large folder with an overlay set takes seconds

- **Symptom:** with `DM_ROMFS_OVERLAY` set, `OpenDirectory` on a RomFS folder of tens of thousands of entries takes seconds, during which every other path call waits for the path lock.
- **Cause:** the overlay snapshot (`dir_snapshot` in `hle_fs.c`) compared each name it gathered with every name gathered before it, the base folder's own too, to drop a name a layer repeats: n(n−1)/2 comparisons, 722 million for 38,000 names.
- **Fix:** the snapshot gathers every layer's names, then `names_first` sorts them once without case, so that the folders' names that differ only in case take one spelling (the image's first of that case, else the base folder's, else the first folder's: the rule of [the mods folder](#mods-made-for-emulators-do-nothing-or-only-half-of-them-does)), and sorts (name, position) once to keep each name's first, in the order gathered, so the listing is the same as before (the last overlay folder first, then the base, an image base in its table order). Measured on an M4 Pro, a read-only folder of 4-byte files under an empty overlay folder: 10,000 entries 0.19 s → 0.03 s, 38,000 entries 3.23 s → 0.20 s; what is left grows linearly (each name's layer is looked up for its type and size). `t_fs_directory` checks a name in several layers, names differing in case (one name, spelled as the base has it) and the layers' order; `t_fs` the spelling of an image base.
- **Found on:** a code audit's synthetic measurement (2026-11-13). No game runs with an overlay by default.

### Temporary storage survives a reset or a quit

- **Symptom:** the temporary storage folder (`$DM_TEMP`, what `MountTemporaryStorage` maps) kept its files across a reset (⌘R / `DM_CTL` `reset`) and across a quit of the app, while a Switch's fsp-srv deletes an application's temporary storage when the software closes.
- **Cause:** the host drops the mount at a reset (`dm_fs_reset`) but only closed its files; nothing emptied the backing folder, and no exit path did either.
- **Fix:** `dm_fs_temp_empty` in `hle_fs.c` removes the folder's entries (the folder stays, the next mount recreates it). It runs in `dm_fs_reset` (a reset is a close and a start again), in `exit_end` (the SIGTERM graceful exit and the reset's process-relaunch fallback end in `_exit`, which runs no `atexit`), and from an `atexit` registered by a constructor (the player's ⌘Q / window close is `exit(0)`). Verified headless: a marker file and a subfolder placed in `temp/` are gone after a reset, with `fs: temporary storage … emptied (2 entries)` in the log.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#reset) (2026-11-27).

### Opening a large RomFS image directory allocates a full snapshot per handle

- **Symptom:** `OpenDirectory` on a large `DMROMFS1` RomFS image directory allocates 784 bytes (`sizeof(DirectoryEntry)`) per child up front (28.4 MiB for a 38,000-entry directory) and calls `die` if the allocation fails, even when the next `ReadDirectory` asks for one entry.
- **Cause:** `h_fs_OpenDirectory` (`hle_fs.c`) copied the image directory's whole child range into a heap snapshot (`h->snap`) as the overlay path does, although the image's index already holds the children as one contiguous run of `img_ent` (`a` the first, `b` the count), mapped for the whole run.
- **Fix:** `dirh_t` keeps the mount's `romfs_img` and a cursor (first, count, position) for an image directory. `OpenDirectory` allocates only the handle (1,096 bytes) and answers `err_res` instead of `die` when it cannot; `ReadDirectory` fills and zeroes only the entries asked for, filtered by the open mode; `GetDirectoryEntryCount` answers the count at once when both types are asked for, else counts the run's matching entries, without moving the cursor. The overlay snapshot (`dir_snapshot`) and the reset's handle list (`dir_track`) are unchanged. Upstream measured on an M4 Pro, a synthetic 38,000-entry image directory: first open 5.908 → 0.033 ms, 28.4 MiB → 1,096 bytes a handle. `t_fs` and `t_fs_directory` check batched filtered reads, zeroed padding, a count that leaves the cursor, one allocation a handle, a failed allocation and the overlay path kept apart.
- **Found on:** upstream nxnative `5e55efad`, a code audit's synthetic measurement (2026-11-25) prompted by Fire Emblem Engage's 38,000-file RomFS folders; no game was seen to fail. Ocarina of Time opens two small `Foliage` folders at boot, so it gains nothing measurable; taken for the error return in place of `die`.

## Add-on content

### Add-on content from `DM_AOC_DIR`

- **Symptom:** DLC the player owns is not unlocked.
- **Fix:** the host reports add-on content from `DM_AOC_DIR`: one entry per DLC index (title ID − base − 0x1000), a numbered folder or `<index>.img`. `build_app.py` writes the NUP's DLC there (`<build folder>/aoc/<index>.img`, `extract_aoc`), the Mac app holds it as `Resources/aoc`, and the launcher sets `DM_AOC_DIR`. `aoc::CountAddOnContent` / `ListAddOnContent` report those indices (`hle_misc.c`); without `DM_AOC_DIR`, or with `DM_AOC_OWNED=0`, they report none. The fork removed the mount (`fs::MountAddOnContent` has no hook): the host counts and lists add-on content, and a game that mounts one reaches the SDK's own call.
- **Found on:** Fire Emblem Engage: its two DLC packages each hold one empty marker file (`e0`, `h0`), and the content is already in update 2.0.0.

### Owned add-on content lists beyond 64 entries

- **Symptom:** some owned DLC is missing, and `aoc: reporting` stops at 64 add-on contents.
- **Cause:** `hle_misc.c` stored only 64 indices and stopped reading `DM_AOC_DIR` when that array filled, before sorting. The omitted indices depended on directory order; its 256-byte log buffer also truncated longer lists.
- **Fix:** the shared array holds 2000 indices, covering the scanner's existing accepted range (1..2000), and a static buffer holds the complete index log without increasing guest-stack use. Folder and `.img` discovery, sorting, deduplication, pagination and `DM_AOC_OWNED=0` retain their behavior. This applies to every game using the add-on content hooks.
- **Open:** the existing 1..2000 acceptance range is retained; it is not established here as Horizon's full legal range. More than 2000 accepted folder/image entries can still fill the array before deduplication, even when their unique indices fit.
- **Found on:** Super Smash Bros. Ultimate (13.0.5, 99 DLC licences; PR #441).

### Add-on content queries on a small guest stack

- **Symptom:** SIGBUS in `__vfprintf` under `aoc_load`, from `h_aoc_Count` (a store to `0x…67ff0`, right below a page of the guest thread's stack).
- **Cause:** the first add-on content query lists `DM_AOC_DIR` and logs, a few KB of stack, and the game asks from a thread with little left.
- **Fix:** `aoc::CountAddOnContent` and `ListAddOnContent` run on the big host stack (`hle_misc.c`; since 2026-11-13 every take-over does: [Host calls on small guest stacks](memory.md#host-calls-on-small-guest-stacks)).
- **Found on:** Digimon Story Cyber Sleuth: Complete Edition (SDK 6.4.0; one boot).

## Input

### Controller disconnect between style and player lookup

- **Symptom:** clang reports a negative shift in `fill` or `vib_targets` (`hle_hid.c`).
- **Cause:** a style check looked up the connected player, then input or vibration routing looked it up again. A disconnect between the reads made the second result -1, used in `1u << player`.
- **Fix:** look up the player once and derive the style from that same result before constructing the player mask.
- **Found on:** clang static analysis ([issue #424](https://github.com/seedds/nxnative/issues/424)); no gameplay failure reported.

### History reads fill every requested entry

- **Symptom:** buttons and menus work, the sticks do nothing in play (Super Mario Odyssey: its first hint, "Look Around", waited forever).
- **Cause:** games read whole histories and ignore the returned count. Odyssey reads all 16 entries of `GetNpadStates`; the host filled only the newest. It polls every controller slot each frame, which moves the shared sampling number on by about 16, so the stick samples it combined were mostly empty, while buttons and the stick's direction bits (which menus use) still came through.
- **Fix:** the host now fills every requested `GetNpadStates` entry with the current state under consecutive sampling numbers (`hle_hid.c`). `DM_KEYS` takes `RLeft` / `RUp` / `RRight` / `RDown` for the right stick.
- **Found on:** Super Mario Odyssey.
- **Note:** Odyssey's six-axis history is read the same way ([Six-axis sensors](#six-axis-sensors)).

### Six-axis sensors

- **Symptom:** motion moves never happen; shaking does nothing (Super Mario Odyssey: cap throws by shaking).
- **Cause:** the host handed out six-axis handles but reported no sensor.
- **Fix:** it now reports one per connected controller: two for handheld or dual Joy-Cons, one otherwise, with the style, npad id and device in the handle. At rest the sensor lies flat: acceleration (0, 0, −1) G, no rotation, identity direction. Samples are 5 ms apart on the guest clock and numbered by time, so a history read returns the samples at those times. `DM_BTN_SHAKE` (`dm_input.h`: Space on the keyboard, `DM_KEYS` `Shake`) plays a side-to-side shake in whole cycles.
- **Found on:** Super Mario Odyssey: it reads all 16 history entries per sensor and ignores the count, like its npad history ([History reads fill every requested entry](#history-reads-fill-every-requested-entry)).
- **Note:** find a game's swing detector by probing the accelerometer value it reads (`DM_PROBE=main:626248@x8+10` in Odyssey 1.4.1).

### A stick's rest drift reads as input on GameController pads

- **Symptom:** a controller at rest drifts a few percent and the game moves (camera, cursor): the sticks feel more sensitive than on a console. Reported on Ocarina of Time's Mac app (macOS 27.2) with a DualSense over Bluetooth.
- **Cause:** pads read through GameController (`pad_read` in `front_mac.m`) were handed over raw: the axis was only clamped, with no dead zone, while raw HID pads got a round 12 % one (`pad_hid_stick`) and Switch 2 controllers their calibration's (`s2_cal_apply`).
- **Fix:** `DM_PAD_DEADZONE` sets one round dead zone for every controller's sticks, the deflection rescaled past the edge so there is no jump (`dm_stick_apply` in `dm_input.h`, used by `pad_hid_stick` and `pad_read`); `0`, the default, keeps each path's own. The settings window offers it as **Stick dead zone** (`settings.tsv`, `meta test=sticks`) and draws both sticks with the zone under the row (`dm/mac/LauncherSticks.swift`), applying the same math, to see when input is emitted.
- **Found on:** Ocarina of Time on a Mac (macOS 27.2), a DualSense over Bluetooth, with the launcher's defaults.
- **Check:** `t_pad_hid` covers the override, the rescale and the fallback to the built-in dead zone.

### Switch 2 controllers over Bluetooth LE

- **Symptom:** a Joy-Con 2 or Pro Controller 2 does not appear in the Mac's Bluetooth menu, or as a GameController or HID device; the game sees no controller.
- **Cause:** these controllers are Bluetooth LE devices with Nintendo's own GATT service, not HID gamepads (Apple's controller driver list on macOS 27.2 has no Switch 2 products), and a Joy-Con 2 forgets a connection the moment it drops: one that is let go stays silent until Sync is held again, unless it is bonded to the host.
- **Fix:** `switch2_proto.h` (pure C: the advertisement and what the host does with it, command framing, bonding, the input report, stick calibration, the motion maps) and `pad_switch2_apple.m` (the Mac front end's CoreBluetooth central, behind the off-by-default `DM_SW2`). A controller held in Sync advertises no host: the host bonds it with the console's `0x15` commands (this Mac's Bluetooth address, then two keys, which may be fresh random ones), and from then on a button press makes it advertise toward this Mac and the host connects. A controller advertising another host is never written to. After connecting, the host runs the handshake (identity read, stick calibration, player lights, features) and takes the 63-byte reports; a player light write once a second keeps the link up.
- **Report layout (a left and a right Joy-Con 2, macOS 27):** the controller's own clock in milliseconds at offset 0 (four bytes; +30 a report on a Mac, +60 or +90 when one was lost), buttons at offset 4 (the same bits as the Pro Controller 2; the right Joy-Con's rail buttons are `0x10` / `0x20`, the left's `0x100000` / `0x200000`), the left Joy-Con's stick in the first stick field and the right one's in the second, both calibrated from the first slot (`0x130A8`); accelerometer at `0x30`, gyro at `0x36`. A Joy-Con held upright reports raw x right, y forward, z up, and its gyro channels are right-handed rotations about the same axes, which is the Switch frame, so its map is the identity for rotation and the negated reading for gravity. The gyro scale is 0.0607 degrees per second per count, measured: 14 tilts from lying on an edge to standing against a wall (90 degrees by the accelerometer) integrated to 1.153 times as much at the Switch family's nominal 0.070, on both Joy-Cons. Each sample is timed by the controller's clock, not by when its notification arrived (they come in bursts, and a lost report leaves a gap only the clock shows). At rest the gyro reads up to about 1.5 degrees per second off, a fixed offset per controller: it is there from the first sample, the one learned for that controller before (kept under its serial number) or, for a right Joy-Con 2, its factory offset (16 bytes at `0x13040`: a temperature and the offset in radians per second, which matches its rest offset); about a second of nearly constant samples refines it.
- **Rumble:** each controller lists its own vibration channel (the right Joy-Con 2's `FA19B0FB-CD1F-46A7-84A1-BBB09E00C149`, the left one's `289326CB-A471-485D-A8F4-240C14F18241`). The report is a zero byte and a 16-byte block per actuator: `0x40 | samples << 4 | sequence`, then up to three five-byte samples, played in turn. A sample is two bands, low then high, each a 10-bit frequency code and a 10-bit amplitude. The frequency code is logarithmic, 96 steps an octave, with 333 at 110 Hz (about 9.9 Hz to 16 kHz); the amplitude is linear, 1023 at full; both bands together are limited to 0.98. Hertz and amplitude are rounded as the console rounds them: truncate, then the nearer of that code and the next. Checked against the Switch 2's own encoder on 200,000 random values: no byte differed. An earlier reading (hertz as the code, a single sample per block) played effects 3 to 5 times too low in pitch and dropped two samples of three. A game sets its vibration about every 5 ms, and each value plays once in its own 5 ms sample, three to a packet every 15 ms (`switch2_proto.h`, Rumble timing), as the console plays them: a one-step pulse stays one sample long. Before that, a value played until the next packet, so short pulses lasted two to three times as long; replayed against a recording of Nintendo Switch 2 Welcome Tour's rumble exhibits, their energy came to 1.8 to 2.2 times the console's, and now matches it. The game's two full-key motors reach the pad through `haptics_apple.m` (`dm_haptics_apple_set_sink`, with Rumble strength and cutoff applied): each Joy-Con of a pair plays its side, a Joy-Con alone the stronger of the two, a Pro Controller 2 one per grip (rumble checked in Echoes of Wisdom). The console also corrects the amplitude by frequency with tables of its own per controller model; that is not done here.
- **Bonding (a left and a right Joy-Con 2):** each bonded with fresh random keys, then woke toward the Mac on a button press and reconnected with no Sync. The answer to the first key was the same bytes on both Joy-Cons and with any key; the answer to the second changes with the key.
- **Permission:** macOS asks once for each game app, at the first scan. A rebuilt app with the same bundle ID asked again (a fresh ad-hoc signature); a second start of the same app did not.
- **Found on:** a left and a right Joy-Con 2 on an M1 Pro Mac, macOS 27.2: Metroid Dread (both woke and played as one pair, pairing by Sync during the game, the Home quit prompt; a Joy-Con paired back to a Switch 2 woke for it and was left alone, `woke for another host`, until Sync paired it with the Mac again) and Super Mario Odyssey (motion: the cap throw by shaking, from the pair's right Joy-Con; rumble on both Joy-Cons).
- **Note:** protocol credit: the community's reverse engineering of these controllers ([Finally the Controller Works](https://github.com/Peterksharma/switch2mac), ndeadly/switch2_controller_research, trevlars/switch2-controllers-linux, Nadeflore/switch2-controllers); the code was written from those notes. A Pro Controller 2 (an M4 Pro Mac, Super Mario Bros. Wonder 1.2.0, [issue #1267](https://github.com/seedds/nxnative/issues/1267)) paired by Sync on the first try and sends the Joy-Con 2's report layout (GR `0x1000000`, GL `0x2000000`, C `0x4000`), with full stick travel from its factory calibration and Home's quit prompt; its rumble channel came from the notes and is now checked in Echoes of Wisdom, and its gyro scale is the Joy-Con 2's, not measured on it. Its motion map is measured: [A Pro Controller 2's motion turned a quarter turn](#a-pro-controller-2s-motion-turned-a-quarter-turn). This Mac's own address comes from `IOBluetoothHostController`, read once the app may use Bluetooth; when it cannot be read, controllers are used without bonding (`DM_SW2_HOST` names it).

### A Switch 2 controller's stick at rest reads as in use

- **Symptom:** a game that turns a feature off while a stick is in use keeps it off after the stick is let go, some of the time. Breath of the Wild with a Pro Controller 2: motion aiming did nothing on about half the aims, and from the first use of the right stick on.
- **Cause:** each stick axis had a dead zone of 40 raw counts and no scale past it. A Pro Controller 2's right stick comes to rest 0 to 60 counts off its calibrated centre, so after a release it read 0 or a constant 3 to 5 % (41 counts was already 3.4 % of a 1200-count travel). Breath of the Wild decides at the start of an aim whether the right stick is in use.
- **Fix:** `s2_cal_apply` (`switch2_proto.h`) uses a round dead zone, and past it scales the deflection back to start at 0, as `pad_hid_stick` does, so there is no jump at the edge and a small diagonal movement keeps both axes. Its size is the stick's own. Each stick's factory block, which the host now reads whole (0x31 bytes at `0x13080` / `0x130C0`), holds 0x28 bytes of model constants before its calibration. These match Switch 1's "stick parameters", whose third value is the dead zone the console applies. The third value here is 160 counts on a Pro Controller 2 (10 % of its nominal travel, the last pair, 1583) and 147 on a Joy-Con 2 (12.6 % of 1167), read from dumps in ndeadly/switch2_controller_research and GP2040-CE. A value outside 3 to 25 % of the stick's travel, or a blank block, falls back to 10 %. The log names the dead zone at connect (`[sw2] ... dead zone`).
- **Open:** that the third value is the dead zone is inferred from the Switch 1 layout and the two models' values, not read from the Switch 2's hid code. The right stick's user calibration is read at `0x1FC062` (ndeadly's layout, past the 2-byte magic); SDL reads it at `0x1FC082`. This matters only after a stick calibration on a console.
- **Found on:** The Legend of Zelda: Breath of the Wild, a Pro Controller 2 on a Mac, 1.9.0 ([issue #2245](https://github.com/seedds/nxnative/issues/2245)).

### A Pro Controller 2's motion turned a quarter turn

- **Symptom:** with a Pro Controller 2, tilting the controller forward turns the game's view sideways, as a roll.
- **Cause:** the Pro Controller 2 took the Pro Controller 1's motion map. Its raw frame is the Joy-Con 2 pair's: flat and still its accelerometer read `-164, -584, 4193` (z up), and held with its top tipped up `-73, 3227, 2597` (+0.79 G on y, forward). The old map turned that tilt into about 50 degrees of roll.
- **Fix:** `s2_map_pro` is the pair's map (`switch2_proto.h`). y and z are measured, which fixes x in a right-handed frame, and the gyro shares the accelerometer's axes (one ICM-42670-P chip). `t_switch2` checks both recorded poses.
- **Found on:** The Legend of Zelda: Breath of the Wild, a Pro Controller 2 on a Mac, 1.9.0 ([issue #2245](https://github.com/seedds/nxnative/issues/2245)).

### Xbox One controllers from other makers over USB

- **Symptom:** a wired Xbox One controller that is not Microsoft's, such as a PDP Wired Controller for Xbox One (`0e6f:02a8`), is listed on USB (System Information) but its light stays off, GameController does not list it and the game sees no controller. The same pad works on Linux.
- **Cause:** macOS's Xbox driver (`XboxGamepad.dext`) matches Microsoft's pads by vendor and product ID only (`045e:028e`, `02ea`, `0b00`, `0b12`), so another vendor's pad stays unconfigured. A GIP pad (the Gaming Input Protocol, USB class `FF` / `47` / `D0`) sends nothing until the host powers it on, and some vendors' pads want more packets first (PDP: its light and authentication). Linux's xpad sends them (`xboxone_init_packets`).
- **Fix:** `pad_gip.h` (pure: the init packets per vendor, the input report, the Xbox button's report and its acknowledgement) and `pad_gip_mac.h` (IOUSBHost from user space, no driver or entitlement): a device of GIP's class with no driver 1.5 s after it appears is configured once without interface matching (if not already configured), its GIP interface (`FF` / `47` / `D0`, with an interrupt IN and OUT pipe) opened, the init packets sent and its interrupt IN pipe read into a reusable DMA buffer. A device with macOS's Xbox driver on it (its `XboxUSBDevice` `IOUserService` or `AppleUserHIDDevice` interface service) is left to GameController. The configuration outlives the process, so interfaces with only user clients on them count as free, or the second run would never find the pad. `front_mac.m` makes it a player from its connection, as a GameController controller; its Xbox button is Home. `+[IOUSBHostDevice createMatchingDictionary…]` gives a driver personality's keys, which `IOServiceAddMatchingNotification` found no device by: the host matches by `IOPropertyMatch`.
- **Fix, later (upstream nxnative `ef0b5be3`):** an input report shorter than the payload it declares, or declaring under 14 bytes, is ignored, and each trigger is read as its 10 bits. `gip_remove` holds a request count across `[intf destroy]`, which may complete the pending reads at once: the last completion freed the pad, and `gip_remove` then wrote to it and could free it again.
- **Limits:** no rumble or player light yet. Not run: unplugging during a game, another vendor's GIP pad, an Xbox One pad of Microsoft's beside it.
- **Found on:** upstream (upstream nxnative `b78d7e8e`, PR #2666): Mario Kart 8 Deluxe (v1507328) with a PDP Wired Controller over USB on a MacBook Pro M1, macOS 27.2: its light came on, every button, both sticks over their range, both triggers and the Xbox button read, a second run found the pad still configured from the first, and the game logged `(USB) connected: player 1`. Not on a pad here.
- **Check:** `t_pad_gip` (`dm/host/tests`): the init packets per vendor, a PDP pad's first report at rest, Turtle Beach REACT-R (`10f5:7024`) 36-byte reports, each button by position, the triggers' 25% threshold, the sticks' range, the Xbox button and its acknowledgement, the announce and reset; `t_pad_gip_mac` covers attach, claim filtering, detach races and slot ownership.

### Wired Xbox 360 controllers from other makers over USB

- **Symptom:** a wired Xbox 360 controller that is not Microsoft's, such as a PDP Xbox 360 pad (`0e6f:0301`), is no player on a Mac: GameController does not list it and the log has no controller line for it.
- **Cause:** macOS's Xbox driver (`XboxGamepad.dext`) matches only Microsoft's wired Xbox 360 product ID (`045e:028e`), leaving third-party wired Xbox 360 pads unconfigured and invisible to both GameController and HID (`pad_hid_mac.h`). They are vendor-specific USB devices (`ff/ff/ff`) with an `ff/5d/01` controller interface (XUSB).
- **Fix:** `pad_xusb.h` (pure: 20-byte `00 14` report validation, buttons by position, 25% trigger threshold, `pad_hid.h` stick dead zone, decoded-state deduplication) shares the `IOUSBHost` user-space transport in `pad_gip_mac.h`: a `ff/ff/ff` device with no driver 1.5 s after it appears whose configuration holds an `ff/5d/01` interface is configured once without interface matching (if unconfigured), its `ff/5d/01` interface opened and its interrupt IN pipe read into a reusable DMA buffer. Devices with `XboxGamepad.dext` attached (such as Microsoft's `045e:028e`) and non-pad `ff/ff/ff` devices (such as Xbox 360 wireless receivers `ff/5d/81`) are skipped. `front_mac.m` assigns slots, focus release/reread, `DM_PAD_MERGE` and `DM_PAD_PRESS_TO_JOIN` through the shared `g_gippads` hooks. `DM_XUSB=0` turns this off and `DM_XUSB_LOG=1` logs decoded state changes.
- **Limits:** a pad can be read by one process only. Not supported yet: the Xbox 360 wireless receiver (`ff/5d/81`), Guide button, rumble and player lights.
- **Check:** `t_pad_xusb` (pure decoder, filters and deduplication) and `t_pad_gip_mac` (synthetic `IOUSBHost` attach, claim skip, wireless receiver skip, detach races and slot ownership).
- **Found on:** upstream (upstream nxnative `ef0b5be3`, [PR #2436](https://github.com/seedds/nxnative/pull/2436)): Mario Kart 8 Deluxe 4.0.1 on macOS 27.2 (Apple M5), with a PDP Xbox 360 pad (`0e6f:0301`) beside a Turtle Beach REACT-R (`10f5:7024`); upstream's hardware retest on this shared `IOUSBHost` path is pending. Not on a pad here.

### Joy-Cons as dual or single npads

- **Symptom:** a pair of Joy-Cons is one Pro-style controller: the game cannot see a dual controller with two sensors, one Joy-Con cannot be a sideways player with its rail buttons; a game that wants two players from one pair (its controller screen) gets one.
- **Cause:** every controller was a full-key (or handheld) npad: `style_for_player` knew only those two styles, the styles the game supports were recorded but never consulted, `fill` kept the low 16 button bits (no SL / SR), the vibration handles knew types 3 and 4 only, and a pair was never split.
- **Fix:** a front end that reads Joy-Cons one by one reports them to the npad layer (`dm_joy_attach`, `dm_joy_set`, `dm_motion_set_joy` in `dm_input.h`, no controller-specific names); nothing changes until one does. Docked, a pad that holds both Joy-Cons is one JoyDual npad (both Joy-Cons' buttons, rail buttons included, each stick on its side, a six-axis handle per Joy-Con) when the game supports JoyDual; when the pair is split (single assignment, `joy_assign`), the left Joy-Con stays on the npad (JoyLeft) and the right one takes the lowest free supported npad (JoyRight); one Joy-Con alone is JoyLeft or JoyRight. The controller applet splits a pair when the game wants more players than there are controllers (`ctrl_support`); the SDK's own assignment calls (`SetNpadJoyAssignmentModeSingle` / `Dual`) are not taken over: the game's modules import none. A game that supports no Joy-Con style gets the pad's merged state as a whole controller: full-key, or JoyDual when the game supports JoyDual but not full-key ([A controller in a style the game does not support](#a-controller-in-a-style-the-game-does-not-support)). Vibration handles exist for the Joy-Con styles (type 5, 6, 7) and reach the motor of their Joy-Con, on whichever npad it is. Handheld mode: player 1's Joy-Cons count as attached to the console (the Handheld npad) and are not split; a player 2 Joy-Con pair is as docked.

### A controller in a style the game does not support

- **Symptom:** docked, the game opens the controller applet again every frame and never leaves the screen behind it. The log repeats `oe library applet: controller support`, `hid controller applet: 1 to 1 players wanted, 1 connected` and focus 2, then 1, thousands of times (7,162 in 3 minutes), after `hid supported controller styles 0x6`.
- **Cause:** the host showed every whole controller (the keyboard, a Pro-like pad, a Joy-Con pair the game supports no Joy-Con style for) as full-key on No1..No8, whatever styles the game supports. The hid service connects a controller only in a supported style, so a game may take any connected npad as one of its own. Nintendo Switch Sports Resort sets Handheld | JoyDual (0x6) for its Tennis lobby (`main+0xa9e940`); its player check (`main+0x58d0f0`) found no usable player 1 on a full-key No1, so its caller (`main+0x3f9d120`) opened `ShowControllerSupport` again, and the applet's answer (one player, No1) could not change that.
- **Fix:** on No1..No8, a whole controller is shown as a JoyDual pair when the game supports JoyDual but not full-key (`pad_style`, `hle_hid.c`): JoyDual is the only other style with all its buttons and both sticks. Its JoyDual state, two six-axis sensors, type 5 vibration handles and the applet's selected npad follow; full-key handles taken earlier still reach its motors. This holds in both modes: in handheld mode players 2..8 (No2..No8) are shown as JoyDual too, and only player 1's Handheld npad stays Handheld. A game that supports full-key, or neither style, is unchanged.
- **Found on:** Nintendo Switch Sports Resort (`04008E001F098000`, v65536), on the Mac with the keyboard and `DM_KEYS`: after the fix the applet is not opened once in 220 s, and Play leads to its one-controller screen ("press the button") and into a doubles Tennis match at its serve prompt.
- **Check:** `t_hid` (`t_unsupported_style`).

### Live controller motion

- **Symptom:** motion controls do nothing with a controller that has a gyroscope (Breath of the Wild: aiming with its Motion Controls option on); the six-axis sensor always lies flat.
- **Cause:** the host's six-axis sensor had no source of motion: flat at rest, apart from the `DM_BTN_SHAKE` shake ([Six-axis sensors](#six-axis-sensors)).
- **Fix:** a controller with a gyroscope drives its player's sensor (`GCMotion`, `motion_apple.h` → `dm_motion_set`, `hle_hid.c`). The orientation is integrated from the gyro with tilt correction toward the measured gravity (`motion_fusion.h`), in `SixAxisSensorState`'s units (G, revolutions/s, revolutions). After 300 ms without a sample the source expires; without another source the sensor lies flat again. A shake still adds on top. The switches are in [development.md, How it works](../development.md#how-it-works) (Input).
- **Source routing (resolved, review of PR #351):** sharing one integrator let two sources' callbacks mix orientations, and checking only `hasRotationRate` let zero-only controller reports count as motion. Each source (a player's GameController stream, its HID stream, each Joy-Con's own) now has its own orientation and timestamp: fresh GameController data is preferred, then fresh HID data, and the Apple adapter waits for actual data before publishing. One-player games merge motion from the same controller slots as buttons. Motion settings initialize once with `pthread_once`; per-source locks also protect diagnostic timestamps. `t_hid` covers routing, expiry and concurrent startup under ThreadSanitizer; `t_motion_apple` covers activation, zero-only reports and detachment.
- **A gyroscope advertised but not there (PR #1877):** the GameSir X5 Lite has no gyroscope, but GameController advertises rotation data for it ([NX2Apple issue #971](https://github.com/LNPANDY/NX2Apple/issues/971), on an iPhone): the log contains 26 identical printed controller reports, including a nonzero rotation rate. The Apple adapter (`motion_apple.h`) accepted any report that was not all zeroes, which kept that controller fresh and preferred over every other source of the player.
- **Controller liveness heuristic (platform workaround):** each attachment withholds controller samples until a raw rotation component differs exactly from its first report; acceleration alone does not qualify it. Once qualified, all later reports, including constant or zero values, pass until detachment. This compensates for incorrect platform/device capability reporting without a controller-model or game rule. Motion or sensor noise is expected to vary a working gyro, but constant output does not prove a sensor is missing, and varying fabricated output could pass. `t_motion_apple` covers constant zero/nonzero rotation, nonzero acceleration, qualification, later zero samples and reset on reattachment. **Pending:** a retest with a GameSir attached and reconnected, and a genuine gyro controller's takeover. The original log rounds rotation to three decimal places in revolutions/s, so it does not establish the exact raw equality this heuristic needs.
- **Upright initialization (resolved, review of PR #351):** the heading reference was parallel to gravity when a sensor started upright, so projection produced a zero vector and silently left the orientation flat. A nonparallel reference now primes the orientation on the first sample; `t_motion` covers all six axis-aligned starting poses.
- **Found on:** The Legend of Zelda: Breath of the Wild (1.9.0): motion aiming on a Mac with a DualSense.
- **History (resolved):** history entries and Switch 2 IMU answers used to repeat the newest sample, so the SDK's sensor fusion saw a staircase instead of a 200 Hz stream. Each live stream now keeps its last 128 samples stamped on the guest clock (`live_motion.ring`, `hle_hid.c`); every 5 ms tick takes the sample at its own time, interpolated between its neighbours (the direction as a normalized blend of the two rotations), the newest sample held past its time. The ring holds host times, turned into guest time with the clock's lag when read, so a freeze or `DM_DETCLOCK` keeps them in order. An answer ends at the clock's tick and never below the last one answered for that handle (`answer_tick`, a high-water mark per handle), so the sampling numbers never go back and keep up with the clock: ending at the newest sample's tick (the first version) took them back when a first sample came late or a player's GameController and HID streams took turns, and stalled them for a game polling faster than its controller. `t_hid.c` feeds 100, 125, 200 and 833 Hz with jittered sample times and checks consecutive ticks, the clock's tick at the end, the signal at each tick and the six-axis history, and keeps the numbers monotone through a late first sample, two streams with different latencies, fast polling, a stale source, a freeze and equal or out-of-order stamps; `t_hid_tsan` runs a writer against a reader.
- **Playout delay:** a source sends a sample every 15 to 30 ms (a DualSense about 67 a second, a Joy-Con 2 33) while a Switch 2 game reads 5 ms ticks up to the present, so read at the present most ticks lie past the newest sample and can only hold it (76 to 79% of a Joy-Con 2's ticks in one session, in runs of 4 to 9). The IMU samples now play each live stream back late by about one sample interval (`DM_IMU_DELAY`, default `auto`: the 90th percentile of how long after a sample the next one arrives, over the last 32, capped at 40 ms; `motion_lag`, `motion_fusion.h`), a change of delay slewed at 5% of the guest time so the data never goes back or jumps, none on a frozen or `DM_DETCLOCK` clock. In the host's tests at 33 Hz (a Joy-Con 2's clock, arrivals up to 4 ms late) and 67 Hz (jittered arrivals), no tick of the steady state held a sample, against 75% and 52% read at the present. The six-axis states (`GetSixAxisSensorStates`) keep no delay by default (`DM_SIX_DELAY=0`): a Switch 1 game reads the newest state each frame, aiming or steering, and a delay would only add latency.
- **Joy-Cons shown as a pair:** a game that supports JoyDual but no single Joy-Con style is shown a single Joy-Con as a pair ([A controller in a style the game does not support](#a-controller-in-a-style-the-game-does-not-support)); both of its handles read that Joy-Con's own stream, in the upright frame a pair's sensor has, not the pad's merged stream (a sideways Joy-Con's frame, a quarter turn away). A real L + R pair gives each handle its own half, also in another player's slot of a one-player game; a pair that loses a half leaves that half's handle flat instead of switching it to the other Joy-Con mid-game, and a Joy-Con that has reported its own motion and goes quiet while attached gives its handle the flat sensor, not the merged stream.
- **Joy-Con 2 sample times:** the front end times a sample by the controller's clock plus an anchor, about the least latency seen (`s2_clock_sample`, `switch2_proto.h`): the anchor rises 1 ms a second, so a controller clock running slow no longer drifts its samples toward 60 ms behind their arrival, and falls only on two reports in a row that came earlier than it predicts, to the later of the two, so one unusually quick report does not move it; a sample keeps at least half a report's step after the last where its arrival allows. `DM_SW2_VERBOSE` also logs the report bytes the parser does not read (0x2A..0x2D read like a microsecond counter, maybe the sensor's own timestamp: unconfirmed).
- **Diagnostics:** `DM_IMU_LOG=<n>` logs every n-th raw sample per stream as the host receives it and every n-th `GetNpadImuSamples` answer.
- **Note:** yaw drifts as on the console, with no recenter.

### Non-finite motion samples

- **Symptom:** a non-finite accelerometer or gyro sample corrupts the six-axis fields; later valid samples do not restore the previous fusion state.
- **Cause:** `motion_update` published raw NaN/Infinity and integrated it into persistent angle/orientation. Finite but extreme rates can also overflow the float rotation norm or accumulated angle.
- **Fix:** reject a non-finite sensor sample before priming or changing any state. A non-finite time step skips integration, and a non-finite gain disables tilt correction. Do not commit an overflowing rotation step or angle; normal finite samples keep the same arithmetic and coordinate conventions.
- **Found on:** synthetic `t_motion` samples, not a reproduced game or controller fault. Tests cover each sensor axis before/after priming, subsequent valid input, invalid timing/gain, finite overflow, all 48 signed frame maps and small-angle accumulation. No device or gameplay result is claimed for this change.

### Switch Pro Controller advertises motion but sends zeroes

- **Symptom:** a Pro Controller's buttons work on the Mac, but its gyro pointer never moves; `GCMotion` callbacks arrive with acceleration and rotation all zero.
- **Cause:** the macOS driver can expose empty motion through GameController while its underlying Nintendo HID `0x30` reports contain IMU data ([PR #296](https://github.com/seedds/nxnative/pull/296)). The OS driver lies outside this repository; the passive HID adapter is a workaround for that platform defect.
- **Fix:** `motion_pro_mac.h` listens nonexclusively to vendor `057E`, product `2009`, without sending commands or changing the driver's configuration. `motion_pro.h` converts the three signed little-endian samples to G and rad/s in the Switch frame; their nominal 5 ms spacing reaches the shared integrator through `dm_motion_set_hid`. An all-zero IMU block (the sensor off, also mid-session) is dropped, so a dead stream expires after 300 ms instead of feeding `(0, 0, 0)` G (upstream nxnative `186374d9`, issue #3364). Each HID device owns its buffer and decoder. HID and GameController orientations stay separate; usable GameController data wins, otherwise fresh HID data supplies that player's controller motion. Removal, focus loss or ambiguous routing clears only the HID source; 300 ms of silence expires it. `DM_MOTION_HID=0` disables the reader; `DM_MOTION=0` disables all motion.
- **Routing limit:** GameController exposes no public per-controller HID identity. Raw motion is enabled only with one physical Pro and one GameController Pro, using that controller's existing player slot (including `DM_KBD_PLAYER=own` / `DM_PAD_MERGE`). Multiple Pros keep their GameController paths; raw data is never assigned to the first controller by guesswork. Each model the reader knows (a table in `motion_pro_mac.h`, with the [DualShock 4](#dualshock-4-over-bluetooth-advertises-motion-but-sends-zeroes)) is paired on its own, so another model connected beside the Pro does not make it ambiguous; under `DM_PAD_MERGE`, where two models share player 1, the first live model in the table keeps it. Every motion report rechecks routing, so a continuously streaming pad takes over when the preferred model has been silent for one second, even without a removal callback; the preferred model takes the player back on its first report. `t_motion_pro_mac` covers both transitions. Synthetic GameController HID devices are excluded with Apple's `GCSyntheticDevice` property.
- **Open:** passive reading cannot obtain factory calibration without issuing SPI commands alongside the OS driver (identical pads read from their reports do issue that read, and it works: [Identical controllers that GameController lists as one](#identical-controllers-that-gamecontroller-lists-as-one)). Nominal scales are 4096 counts/G and 70 mdps/count ([protocol research](https://github.com/dekuNukem/Nintendo_Switch_Reverse_Engineering/blob/master/imu_sensor_notes.md)); the rest offset is learned and taken off with `motion_rest` (`motion_fusion.h`, as for GameController's motion: two agreeing still seconds within 2 deg/s, ramped in over 0.75 s, so a slow turn is not taken for an offset; upstream nxnative `327f4bcd`, issue #3364). Sample order follows that research and [Linux hid-nintendo](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-nintendo.c); SDL reverses it. Confirm order, sensitivity, drift and reconnects on hardware before calling the reworked reader device-tested. `t_motion_pro`, `t_motion_pro_mac` and `t_hid` cover decoding, the rest offset, timestamps, ownership, removal, ambiguity and source fallback with synthetic inputs.
- **Found on:** Super Mario Galaxy, docked pointer on a Pro Controller.

### Switch Pro Controller stick stays zero in GameController

- **Symptom:** on the Mac, a third-party Switch Pro-compatible controller (`057e:2009`, `Switch Pro Controller`) has working buttons and motion, but one or both thumbsticks stay at `(0, 0)` in GameController, both in `GCExtendedGamepad` and in `GCController.input.unmappedInput`.
- **Cause:** the pad sends valid 12-bit stick values in its report `0x30`, and Apple's Switch Pro driver gives exact zero for them (probably rejecting the pad's calibration). The driver lies outside this repository: the passive stick reader is a workaround for it.
- **Fix:** `motion_pro_mac.h` decodes both sticks from the `0x30` reports it already receives, read nonexclusively with no output report (`pad_pro.h`, its own rest and reach). `pad_read` marks a stick live when `GCExtendedGamepad` moves it; GameController's `unmappedInput` is asked only when a stick not yet live has stayed past half tilt in the raw reports for 150 ms, or while a stick is latched, and no stick work is done once both are live (upstream nxnative `186374d9`, issue #3364). A stick that both GameController interfaces still read as exact zero at that point latches onto those reports and logs it once; buttons, vibration, Home, motion and a working stick stay with GameController. front_mac.m is told only when a latched stick's value changes, the stick lets go 300 ms after the reports stop, and it goes back to GameController for good once GameController moves it. Independent of `DM_MOTION` / `DM_MOTION_HID`; `DM_PRO_STICKS=0` turns it off. As for motion, only one Pro Controller pairs ([above](#switch-pro-controller-advertises-motion-but-sends-zeroes)): two unbind it.
- **Check:** `t_motion_pro_mac`: one and two dead sticks, a short flick, no GameController query on idle reports or before the 150 ms mark or once both sticks are live, a remapped stick, repeated packets, GameController moving late, focus loss, the 300 ms expiry, a short report, two pads, motion off, `DM_PRO_STICKS=0`.
- **Found on:** upstream (upstream nxnative `be3b8bf8`; issue #2655 and PR #382): Splatoon Raiders with a USB BETOP T6 For NS on macOS 26.7.3 (left stick zero while report `0x30` spans 4 to 4091), and a Bluetooth Pro-compatible pad on macOS 27.0.1 in Pokémon Scarlet (both sticks). Not on a pad here: this Mac's player uses a DualSense, which this path never matches.

### DualShock 4 over Bluetooth advertises motion but sends zeroes

- **Symptom:** a DualShock 4 over Bluetooth is logged `with motion (gyro)` and the game reads the six-axis sensor every frame, but motion aiming does nothing; over USB it works ([issue #1770](https://github.com/seedds/nxnative/issues/1770)). With `DM_MOTION_LOG=1` no `[hid] motion player 1` line appears.
- **Cause:** as with the [Pro Controller](#switch-pro-controller-advertises-motion-but-sends-zeroes), GameController's `GCMotion` for the pad sends only zeroes over Bluetooth, which `dm_motion_attach` rightly ignores, while the pad's own Bluetooth input report `0x11` carries the sensor. Over USB the pad sends report `0x01` and `GCMotion` works. The OS driver lies outside this repository.
- **Fix:** the DualShock 4 is a row of the passive reader's model table (`motion_pro_mac.h`): vendor `054C`, products `05C4` (v1) and `09CC` (v2), report `0x11`, paired with GameController's `DualShock 4` controller. `ds4_motion_decode` (`motion_pro.h`) reads six signed little-endian words from byte 15 (USB's report `0x01` fields two bytes later, as Linux hid-playstation and SDL read them): rotation x, y, z, then acceleration, at the nominal 8192 counts/G and 2000 deg/s over 32767, into the Switch frame with the axis signs measured on a pad (MacNativeGames PR #1306). One sample per report, stamped on arrival; a stream that falls silent for 300 ms must show data again. A pad over USB never sends `0x11`, so its entry never counts and GameController's motion stays. The routing is the Pro Controller's, per model: one DualShock 4 that sends `0x11` and one GameController DualShock 4, whatever other models are connected.
- **Open:** the factory calibration (a feature report the OS driver owns) is not read; the rest offset is learned and taken off by `ds4_motion_decode` as for the [Pro Controller](#switch-pro-controller-advertises-motion-but-sends-zeroes) (upstream nxnative `327f4bcd`), not yet checked on a pad. `09CC` is matched by the same report and not yet tested on a pad. With one pad over USB and another over Bluetooth, GameController lists two and the Bluetooth one keeps its zero `GCMotion`. A controller that presents itself as a DualShock 4 (a GameSir Cyclone uses `054C:05C4`) and sends `0x11` with zeroes never becomes a source. `t_motion_pro` covers decoding and the rest offset (a gap of 100 ms breaks a window, 300 ms of silence forgets the offset), `t_motion_pro_mac` a DualShock 4 paired beside a Pro Controller.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md), slingshot aiming with a DualShock 4 v1 (`05C4`) on macOS 27.2 (M2 Pro); reported on Tears of the Kingdom with a v2 (`09CC`).

### 8BitDo Ultimate 2 Wireless over Bluetooth has no motion on the Mac

- **Symptom:** an 8BitDo Ultimate 2 Wireless (`2DC8:6012`) over Bluetooth plays its buttons and sticks, but motion aiming does nothing, and `DM_MOTION_LOG=1` logs no motion sample.
- **Cause:** GameController takes the pad for a plain extended gamepad (product category `HID`, `GCMotion` nil): no GameController motion path exists, and GameController lies outside this repository. Firmware 1.03 and later stream a 34-byte report `0x01` whose bytes 15 to 26 hold six signed little-endian `int16` (acceleration x, y, z at 4096 counts/G, then rotation x, y, z at 2000 deg/s per 32767) in the Pro Controller's raw axes, as SDL's `SDL_hidapi_8bitdo.c` decodes them. Firmware 1.02 sends 12-byte reports with no sensor.
- **Fix:** a row of the passive reader's model table (`motion_pro_mac.h`): `2DC8:6012`, report `0x01` of at least 34 bytes, its GamePad / Joystick interfaces only, paired with GameController's controller by its `vendorName` (`8BitDo Ultimate 2 Wireless`, after the product categories); `abitdo_motion_decode` (`motion_pro.h`) turns the words into the Switch frame, one sample a report, stamped on arrival, dropping an all-zero block, learning the rest offset as the Pro Controller does and starting again after 300 ms of silence. A short report logs once and never makes the pad live. Pairing, `DM_PAD_MERGE`, focus, `DM_MOTION_HID=0` and `DM_MOTION=0` work as for the [DualShock 4](#dualshock-4-over-bluetooth-advertises-motion-but-sends-zeroes); a usable `GCMotion` would come first.
- **Check:** `t_motion_pro` (a real resting report captured upstream, PR #1934, firmware 1.02's short report, signs and scales, an all-zero block after live data, the rest offset learned from that captured report's bias, staleness) and `t_motion_pro_mac` (`vendorName` matching after the category, non-gamepad and synthetic interfaces left out, beside a Pro Controller and a DualShock 4, two pads, focus, removal).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) upstream (upstream nxnative `549324da`, issue #2997): reported on an M3 Max with macOS 26.7.1; slingshot aiming confirmed for 37 minutes on an M4 MacBook Pro (PR #1836). Not on a pad here; other `2DC8` models and the 2.4 GHz dongle (`2DC8:310B`) are not covered.

### An original Joy-Con's sensors are read by the host

- **Symptom:** on the Mac, an original (Switch 1) Joy-Con's buttons and sticks work through GameController but its motion does not: the six-axis sensor lies flat, so a game that steers or aims with it (Nintendo Switch Sports Resort: Archery, Boxing; Splatoon Raiders: motion aiming) does not follow the controller. A lone Joy-Con does not play at all, and a pair plays as one full-key controller whatever the game asks for.
- **Cause:** macOS's GameController presents a paired L + R as one `GCController` ("Nintendo Switch Joy-Con (L/R)") with no `GCMotion` object at all, a lone Joy-Con with no extended gamepad profile, and gives a controller no HID identity, so a sensor read from IOKit cannot be tied to one of its controllers ([PR #2594](https://github.com/seedds/nxnative/pull/2594) routed them by a button press seen on both, a heuristic). The HID report its driver keeps sending (0x30, about 60 Hz) has the IMU fields zeroed: the sensor is off until the host asks for it, and the OS driver never does. The Pro Controller's passive reader ([Switch Pro Controller advertises motion but sends zeroes](#switch-pro-controller-advertises-motion-but-sends-zeroes)) does not fit: it only listens, while a Joy-Con has to be told to send its samples and to give its factory calibration over SPI.
- **Fix:** the host reads each Joy-Con wholly from its own HID report, on the Mac only (`pad_jc1.h`, pure C, and `pad_jc1_mac.h`, IOKit), and `front_mac.m` leaves GameController's Joy-Con controllers unread (`jc1_gc_unread`, as identical pads' `hidpad_gc_unread`), keeping only Home and Capture away from macOS (`pad_keep_system_buttons`; Home held still opens the quit prompt, read from the report). It matches vendor 057E, products 2006 (left) and 2007 (right), opens the device nonexclusively and sends the console's handshake: device info (0x02), standard full mode (0x03 with 0x30), EnableIMU (0x40 with 0x01), the vibration on (0x48 with 0x01), SPI reads of the factory IMU calibration at 0x6020 and of the stick calibrations (factory 0x603D, user 0x8010, decoded by `pad_pro.h`: a left Joy-Con fills the left stick's block, a right one the right's), then the player lights (0x30), 60 ms apart as the console does, each step its own main-queue block. Output reports go out on a serial queue of their own, so a Bluetooth write never holds up the run loop. A report whose sensor block is all zero is the sensor off, never a reading (a real gyro is never 0 on all three axes three times running, even in free fall): it gives no samples, and a watchdog repeats the handshake for a Joy-Con with no sensor data since its last one, whether its reports stopped or come zeroed (a wake resets the mode), after 1 s and then twice as long each time up to 8 s. A report shorter than 0x30's 49 bytes is refused before any of it is read.
- **Pads and players:** a Joy-Con that connects joins a pad that holds the other side alone, else it is a pad of its own (`jc1_pair_pick`); holding SL + SR on one of a pair for 3 s makes it a pad of its own, holding L on a left one alone and R on a right one alone together for 3 s pairs them (`jc1_gesture`, the Switch 2 transport's gestures). A pad is a player from its first button press, as a raw HID pad, and its lights show the player (all four flashing while it waits). Each Joy-Con is a device of its own to the npad layer (`dm_joy_attach`, `dm_joy_set` with its rail buttons, `dm_motion_set_joy`), as the Switch 2 transport's Joy-Con 2s, so the npad layer shows a pair as one dual npad or, split by the controller applet, as two single ones (`hle_hid.c`), whatever macOS's combine setting. For a game that supports no Joy-Con style the pad is one whole controller (`jc1_pad_input`): a pair as a Pro Controller, a Joy-Con alone held sideways, its face buttons, stick and merged six-axis stream turned a quarter (`jc1_sideways_*`: the left one counterclockwise, the right one clockwise, the rail away from the player). The merged stream (`dm_motion_set_hid`) comes from the right Joy-Con of a pair (`DM_JC1_SIDE=L` for the left), the left one when the right one is not streaming. `DM_PAD_MERGE` makes every pad player 1 and holds no Joy-Cons apart. `DM_JC1=0` gives them back to GameController (buttons, no motion).
- **Report:** 49 bytes, of which three 12-byte samples sit at offset 13 (acceleration XYZ then gyro XYZ, int16 little endian, 5 ms apart, the third the newest). The chip's axes: +X runs along the controller toward its top, +Y is the short axis, and +Z leaves the face on the left Joy-Con but the back on the right one, so the map into the Switch frame is (-Y, +X, +Z) for the left and (+Y, +X, -Z) for the right, negated, because the host wants the gravity direction and not the accelerometer's specific force; the gyro takes the same rotation, in rad/s.
- **Gyro scale:** the calibration's coefficient is stored in either of two schemes (816 or 936 over coeff - origin), and the units in the wild use both: one of a pair here had 0x3BE7 (15335) where the other had the default 0x343B (13371), so with one constant the two integrate at rates 13% apart and the orientation drifts during a round. Each axis takes whichever constant puts it nearest the part's measured sensitivity (0.061 deg/s per count), which keeps a real per-unit calibration and drops the scheme. The gyro's origin is the still offset.
- **Still offset (the cause of Boxing's phantom punches):** the factory's gyro origin is close but not the unit's own: the left one here read 5/25/2 counts against a rest offset of tens of counts, and what is left over (a degree or two per second) integrates into a drift the game reads as the player's hands moving. The host learns the controller's own offset from a second of samples in which the gyro and the accelerometer hardly vary, from fresh reports with sensor data only, and takes the two together (the factory origin is kept from the calibration reply whatever the logging; a rest learned before the reply, against origin 0, starts again, and the same calibration read again after a wake keeps it), as the Switch 2 transport does for its Joy-Con 2 (`s2_rest_update`, `pad_jc1.h`'s `jc1_rest_update`): measured, the left's residual was 11/-3/-7 counts and the right's 4/2/4. On a 22 minute session the learned offsets settled at -1/-2/46 counts on the left and 9/-8/-15 on the right, the left's residual at rest was 0.06 deg/s, and Boxing, which threw punches with the player still on both builds before this one, was clean.
- **Sample times:** the newest sample is the earlier of the clock and the arrival, the clock advances 15 ms a report and slews a quarter toward the arrival, and the samples within a report are 5 ms apart; a sample at or before the last one given is skipped, so an early report brings fewer samples rather than out-of-order ones.
- **Rumble:** the game's vibration for a Joy-Con pad's player goes to the Joy-Cons (`dm_jc1_rumble`, set as the player's haptics sink), not to GameController. Every 15 ms while it buzzes, each Joy-Con gets an output report 0x10 with one HD rumble sample (`jc1_rumble_encode`, dekuNukem's rumble data table as Linux hid-nintendo and SDL encode it: a high band of 81.7..1252 Hz and a low band of 40.9..626 Hz, each frequency and amplitude on its log scale; nothing at the default frequencies is the neutral 00 01 40 40): its own side's motor in a pair, the stronger of the two in each band when it is alone. A report carries one sample where a game sets values every 5 ms, so each report plays the strongest value set since the last one (`jc1_rumble_hold`), and a buzz ends with three reports of silence. The tick runs only while there is a Joy-Con pad.
- **Found on:** Nintendo Switch Sports Resort (v65536), on a Mac (macOS 27.2) with a left and a right Joy-Con: both accept the handshake, the 49-byte reports arrive at about 60 Hz with three samples 5 ms apart, the factory calibration reads, and flat on the desk both halves report the same gravity (left +0.01 -0.06 -1.04, right +0.02 -0.06 -1.01). The normalized gyro scale reads 0.0611/0.0611/0.0610 deg/s per count on the left and 0.0610/0.0609/0.0610 on the right: the same 0.061 the part's sensitivity is, where the left's own coefficient with the 816 constant would give 0.0532, 13% slow. Archery starts and shoots, and the game's own orientation gate (the buttons facing inward) passes. A real punch reached 9.9 G and 18 rad/s. On Splatoon Raiders (v65536, a Switch 2 game, SDK 21.4.4) the same pair aimed cleanly and 1 to 1: the game reads the six-axis API every frame (30,400 `GetSixAxisSensorStates` calls to frame 26,100 in a 7 minute session) and never the npad IMU API, and the stream carried the motion (444 deg/s peak from the left half, 484 from the right, 1.27 rev/s handed to player 1).
- **Open:** reading a Joy-Con wholly from HID (buttons, sticks, rumble, lights, pairs, gestures, the sideways mapping) is checked by `t_jc1` only and has not run on hardware; until it has, buttons, sticks and rumble that worked through GameController depend on it. To check on a Mac with Joy-Cons: a pair and a lone one join at a press and light their player; sticks centred and reaching full after the SPI calibration (`DM_JC1_LOG=1` logs it); a game whose controller applet wants two players splits the pair; the rumble strength and feel, and whether a 15 ms report rate keeps up over Bluetooth with two pads; Home held quits; whether GameController's player lights on the Joy-Con fight the host's. The sideways frame derived here (left (-y, x, z), right (y, -x, z)) is the opposite of the Switch 2 transport's `s2_map_left_alone` / `s2_map_right_alone`; one of the two is wrong and only hardware can say which. A pair dropped out once mid-session (the right one's RSSI was -77; a battery is suspected). Whether a pair's two sensor frames should be common or per device is open: a flat pose agrees on both, and mirrored hand poses read mirrored x, which is physically expected and passed Archery. Boxing's phantom punches were the still offset and are fixed (above); the three samples a report (200 Hz, where the Switch 2 transport sends one) are not implicated, since Splatoon Raiders aims 1 to 1 from the same stream and a round of Boxing is clean.
- **Check:** `t_jc1` (the output report's bytes, the SPI reply in both encodings, the left and right frame signs, a short report refused unread, the repeated packet counter, a zeroed stream after a live one and the watchdog's timing, the jitter monotonicity with early and late arrivals, the calibration's origin and the rest learned on it; each Joy-Con's buttons and the charging-grip bit, the stick through its SPI calibration, the sideways stick, sensor and buttons, a pad's whole-controller state, the pairing pick, the merged-stream side, each Joy-Con's motors, the gestures, the light patterns, the rumble codes against the table and the peak hold).

### Identical controllers that GameController lists as one

- **Symptom:** two Switch Pro Controllers connected over USB to a Mac play as one player: GameController lists one controller and reads one of the two pads, the other does nothing, and a two-player game refuses to start ([issue #1218](https://github.com/seedds/nxnative/issues/1218)). Over Bluetooth both are listed.
- **Cause:** GameController lists one controller for both. Their USB serial numbers are the same, which may be why; over Bluetooth each has its own. IOKit has both devices, and each sends its report `0x30`. GameController gives a controller no HID identity, so its one controller cannot be tied to one of the two devices.
- **Fix:** one mechanism in `pad_hid_mac.h`, on its own HID manager. It keeps the devices GameController reads (`g_hidpads_gc`) instead of dropping them, to count IOKit's pads of each model (vendor and product ID) against GameController's controllers of it: a Pro Controller's by their product category, another model's by name (`vendorName` is the HID product string). Other Microsoft, Sony and Nintendo pads cannot be matched by name (a DualShock 4's HID product string is `Wireless Controller`), so they are never read this way, which would read them twice. When IOKit has at least two pads of a model and more than GameController lists (only entries that send reports count: [A HID entry that sends nothing counted as a second pad](#a-hid-entry-that-sends-nothing-counted-as-a-second-pad)), after a 3 s wait for a pad that is not listed yet (`pad_dupes_want`), every pad of that model is read there, a player each, by USB location: a Pro Controller from its report `0x30` (`pad_pro.h`) with its gyro (`motion_pro.h`), any other model from its HID elements (`pad_hid.h`). `front_mac.m` leaves GameController's controllers of that model unread (`hidpad_gc_unread`). When GameController lists them all again, they go back to it. `DM_PAD_IDENTICAL=0` turns it off, as does `DM_HID_PADS=0`; `DM_MOTION=0` and `DM_MOTION_HID=0` turn off only the gyro. `motion_pro_mac.h` is not involved: it still pairs one Pro Controller's raw motion with GameController's one controller.
- **Sticks:** a Pro Controller read this way asks for its stick calibration in SPI flash, subcommand `0x10` in output report `0x01`: the user's at `0x8010` when its magic `B2 A1` is there, else the factory's at `0x603D` ([spi_flash_notes.md](https://github.com/dekuNukem/Nintendo_Switch_Reverse_Engineering/blob/master/spi_flash_notes.md)). Alongside the macOS driver both pads answered over USB, and a pad over Bluetooth, on an M4 Pro with macOS 27. Without an answer each axis measures its own rest and reach.
- **Limits:** such pads have no rumble or player lights, and Home does not quit from them. Another model's buttons follow 8BitDo's numbering unless `DM_HID_MAP` says otherwise; only Pro Controllers were run, before the mechanism was folded into `pad_hid_mac.h` ([PR #1595](https://github.com/seedds/nxnative/pull/1595)), and the folded version awaits a run with two Pro Controllers over USB.
- **Found on:** Mario Kart World 1.8.0, two Pro Controllers over USB, 33 minutes of two-player split-screen races.

### One Pro Controller read as two players

- **Symptom:** with one Pro Controller over Bluetooth, the log shows `GameController lists 1 of 2 pads of this model` twice for the same USB location, then players 1 and 2 for that pad; a one-player game opens the controller applet every few frames (`hid controller applet: 1 to 1 players wanted, 2 connected`, focus state 2 then 1, thousands of times). A game that suspends its music while an applet has focus plays none: sound effects and positional music still play, while area and cutscene music never start.
- **Cause:** `IOHIDManager` hands a device over once per matching dictionary it meets, each time as a new `IOHIDDeviceRef` for the same I/O Registry entry. The Pro Controller meets both the GamePad usage dictionary and its own vendor / product one (added so identical pads are counted), and `hidpad_found` knew devices by reference only, so one pad counted as two pads of its model against GameController's one controller ([Identical controllers that GameController lists as one](#identical-controllers-that-gamecontroller-lists-as-one)).
- **Fix:** `pad_hid_mac.h` knows a device by its registry entry ID (`hidpad_entry`): a second reference to a known entry is ignored in every list.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md), one Pro Controller over Bluetooth on the Mac: no music in Kokiri Forest gameplay or its cutscenes, back once the pad was read once.

### A HID entry that sends nothing counted as a second pad

- **Symptom:** one Pro Controller over Bluetooth comes back from a long disconnect (20 minutes or more) as two players: `GameController lists 1 of 2 pads of this model: read here` for two USB locations, one of them `0x0`, then `controller 'Pro Controller' (HID) connected` as players 1 and 2. The location-0 entry logs `cannot ask its stick calibration (IOReturn 0x10000003)`. The `connected` then `disconnected ... is free` lines of the GameController controller just before are the host releasing it to the twin path, not a Bluetooth drop. A short drop of about 20 s reconnects as one player.
- **Cause:** the twin path ([Identical controllers that GameController lists as one](#identical-controllers-that-gamecontroller-lists-as-one)) counted every IOKit entry of the model as a pad. After the long disconnect IOKit had a second entry of the one pad: `0x10000003` is `MACH_SEND_INVALID_DEST`, so nothing receives what is sent to it, and it survived the next reconnect while the live entry was replaced. Two entries against GameController's one controller read as two identical pads that GameController merged. The raw motion pairing ([Switch Pro Controller advertises motion but sends zeroes](#switch-pro-controller-advertises-motion-but-sends-zeroes)) counted the same entries, so the dead one would also have turned the gyro off. What macOS keeps the entry for is not known: the report has no `ioreg` listing of that state.
- **Fix:** an entry counts only while a pad is behind it (`hidpad_live`, `pad_hid_mac.h`; `pro_live`, `motion_pro.h`). macOS keeps a Pro Controller in full mode, which sends report `0x30` every 15 ms whether or not anything moves, so a Pro Controller entry counts while its last `0x30` is less than a second old; another model's entry counts once it has sent any report (it may send only on change). Each entry's reports are listened to for this (`hidpad_listen`; another model's only until its first). An entry starts counting at its first report, and again at its first after a silence; one that falls silent without being removed is left out at the next change of the model's pads. Both twins and the raw motion pairing use it. When a model has two or more entries, the log names each one that starts or stops counting, with its transport and registry entry ID, and the twin line names them too, so a report shows which entries a pad has. A twin now takes its player only once it sends.
- **Open:** not run with a controller (none here), so that the reporter's location-0 entry sends nothing is inferred from its `MACH_SEND_INVALID_DEST`, not measured; if it does send report `0x30`, it still counts. The issue stays open for the reporter's retest. Two Pro Controllers over USB are read as twins as before, about 15 ms later (their first reports), checked with fake devices only. A silence of a second or more (a pad whose reports stop while it stays connected) leaves it out at the next change of its model's pads.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (v131072), one Pro Controller over Bluetooth on a MacBook Air M4 with macOS 27.2, in two runs after long disconnects ([issue #2237](https://github.com/seedds/nxnative/issues/2237)).
- **Check:** `t_pad_hid_mac` (`dm/host/tests`, fake IOKit entries and GameController controllers): one pad with a silent second entry stays with GameController, as does a reconnected pad whose old entry fell silent; two pads over USB become twins only once both send, go back when one falls silent and come back when it sends again. With every entry counted, it fails with the report's two `read here` lines. `t_motion_pro_mac`: a silent entry does not stop the pairing, and a pad whose old entry fell silent is paired on its new one. `t_motion_pro`: `pro_live`.

### A virtual controller is trusted but never published by GameController

- **Symptom:** on the Mac through Steam Link / Remote Play, a virtual `045e:028e` controller named `GamePad-N` gives a game no input and no controller-connected log line. `+[GCController supportsHIDDevice:]` answers YES, but `GCController.controllers` is empty ([issue #2465](https://github.com/seedds/nxnative/issues/2465)).
- **Cause:** `hidpad_found` trusted the Microsoft, Sony and Nintendo vendor IDs without waiting for GameController to publish a controller. A virtual HID device can reuse those IDs without being published, so neither GameController nor the raw HID reader read it. The existing two-second fallback covered other vendors only.
- **Fix:** vendor-only trust applies to physical devices: a device marked `kIOHIDVirtualHIDevice` must have a matching, usable GameController controller or take the existing two-second HID fallback, whatever its name, vendor or product. Both the name check (`hidpad_gc_listed`) and a late handoff (`hidpad_gc_connected`) require `extendedGamepad`, the profile `front_mac.m` reads. Apple's GameController synthetic devices remain excluded. Physical-controller vendor trust remains because their GameController names can differ from their HID product strings.
- **Fix, its layout:** the raw HID fallback used 8BitDo's button numbering and treated Z / Rz as the right stick. Steam Link's Xbox 360 layout uses Xbox button usages, X / Y for the left stick, Rx / Ry for the right stick and Z / Rz for the triggers. `pad_hid_layout_for` requires `045e:028e` and those six Generic Desktop axes without dedicated Brake / Accelerator usages. Nintendo's report `0x3F` takes precedence. Discovery and the value callback use the same axis mapping. The d-pad arrives as buttons 12–15, and `DM_HID_MAP` still replaces button entries.
- **Check:** `t_pad_hid_mac` drives the real discovery, value callbacks and handoff with fake IOKit devices and GameController controllers. It checks the mapped face button, triggers and right stick for the matching Xbox layout, dedicated triggers on a different layout with the same ID, and Nintendo's right-stick axes when report `0x3F` takes precedence. Unlisted virtual devices of all three trusted vendors and another vendor deliver button presses and releases through HID after the wait. Already listed and promptly published usable controllers stay with GameController. A matching controller without `extendedGamepad` cannot suppress HID or take it back, but a usable late controller does. Removal during the wait, the synthetic exclusion, physical-device trust with missing or false virtual flags, and the identical-pad and Nintendo-protocol cases are checked too.
- **Open:** live Steam Link verification of the buttons and triggers is pending. The reporter's local Steam-specific repair restored input. The button map comes from one-at-a-time presses of a GameSir G8 through Steam Link on an iPhone, captured on the Mac, and `t_pad_hid` checks each. Both sticks worked in Donkey Kong Bananza with an earlier local version. Rumble and multiple remote players remain untested.
- **Found on:** Cult of the Lamb 1.5.28 with four DLCs through Steam Link, built with engine `ccd834e0` (NX2Apple 1.4.0), reported in issue #2465.

### One pad that needs Input Monitoring left every raw HID pad unread

- **Symptom:** on the Mac no raw HID pad is read, and the log says `[RED] HID gamepads: cannot open HID (0xe00002e2); only GameController controllers are read`. Since the fix only the refused device is named, `[RED] controller '<name>' (HID, <vendor>:<product>): not read: macOS requires Input Monitoring for this device (...)`, and the other raw HID pads are read.
- **Cause:** `hidpad_start` (`pad_hid_mac.h`) opened its manager with `IOHIDManagerOpen`, which opens every matched device and fails as a whole when one fails, and the host then dropped the manager. macOS refuses `IOHIDDeviceOpen` with `kIOReturnNotPermitted` (`0xe00002e2`) on a device that also declares a keyboard or mouse unless the app has Input Monitoring (`kIOHIDRequestTypeListenEvent`), and with `kIOReturnExclusiveAccess` when another app has seized the device. An ad hoc signed app is allowed by its code hash, so a rebuilt app is refused again until it is removed from that list and allowed again.
- **Fix:** the manager is made with `kIOHIDManagerOptionIndependentDevices` and only scheduled. `hidpad_open` opens a device nonexclusively and schedules it on the main run loop when `pad_hid_mac.h` reads it (`hidpad_use`) or listens to it for twins (`hidpad_listen`), so a physical Xbox or Sony pad, which GameController reads, is not opened here. `hidpad_drop` stops its callbacks, lets its output reports queued on `g_hidpad_out` go out (as `pad_jc1_mac.h` does), unschedules and closes it. A refusal costs that device only and is logged with `IOHIDCheckAccess`'s state and where to allow the game.
- **Check:** `t_pad_hid_mac`: refusals with `kIOReturnNotPermitted` (at once, after `HIDPAD_GC_WAIT`, in `hidpad_listen`, in each `IOHIDCheckAccess` state) and `kIOReturnExclusiveAccess` beside an ordinary pad that opens, sends its button and stick and closes when removed; Xbox and Sony pads never opened; an output report in flight on `g_hidpad_out` done before `IOHIDDeviceClose`. On this Mac (macOS 27.2), a manager made this way and never opened matched its devices and read their elements unopened, the same count as opened (none for the built-in keyboard, which Input Monitoring gates).
- **Open:** not run with a refused device beside a raw HID pad, nor with any raw HID pad (none on this Mac); upstream checked the manager on a Mac with denied keyboards beside other devices. `pad_jc1_mac.h` and `motion_pro_mac.h` still use `IOHIDManagerOpen`: they match only given controller IDs, which declare no keyboard.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) upstream (upstream nxnative `1947c0df`, PR #3386): 1.1.1 (v131072) on an M1 Pro with macOS 27.2.1.

### A keyboard receiver that declares a gamepad takes player 1

- **Symptom:** on the Mac, with a keyboard and mouse receiver plugged in, the log shows `controller '<receiver>' (HID) connected: player 1` and the real controller as player 2; a one-player game takes no input from it and opens the controller applet again and again (`hid controller applet: 1 to 1 players wanted, 2 connected`).

### Raw HID pads with wrapped unsigned axes, mouse collections or Consumer AC Back

- **Symptom:** on the Mac, a raw HID pad such as the NVIDIA SHIELD Controller 2015 (USB `0955:7210`) has its sticks pinned to an end and its analog triggers held at rest, its touchpad or mouse moves the left stick, and its Back button (Consumer `0x0C:0x224`) does nothing. A keyboard and mouse receiver that declares a gamepad (as in [A keyboard receiver that declares a gamepad takes player 1](#a-keyboard-receiver-that-declares-a-gamepad-takes-player-1)) can join on a mouse click, and its mouse then moves the left stick.
- **Cause:** three gaps in `pad_hid.h` / `pad_hid_mac.h`:
  1. A descriptor that writes an unsigned Logical Maximum without a leading zero byte (`0xFFFF` on a 16-bit field) parses as signed `-1`, and IOHIDFamily swaps `(0, -1)` to `-1..0`; raw values normalized against that range land far past ±1, and a trigger at 0 reads +1.
  2. `hidpad_found` and `hidpad_value` took every element of the device, whatever its collection and whether it was relative, so a Mouse collection's relative X / Y fed `PH_X` / `PH_Y` and its button usage 1 a face button.
  3. Only Button-page usages 1..32 were read.
- **Fix:** with no vendor gate: `pad_hid_norm_bits` takes the range back from the field's width (`IOHIDElementGetReportSize`) when a multi-bit axis reports `-1..0` or `0..-1`; `hidpad_collection_flags` skips elements under a Mouse, Keyboard or Keypad collection that have no GamePad / Joystick / MultiAxisController ancestor (a Physical Pointer collection inside a gamepad still counts), and relative axes are ignored in discovery and in the callback; Consumer AC Back maps to Minus (`pad_hid.ac_back`), unless it comes from a standalone Consumer Control collection (a receiver's media keys).
- **Check:** `t_pad_hid` (wrapped 16- and 8-bit ranges both ways, the SHIELD's measured stick ends and trigger sweep, widths 0, 1 and 32, `ac_back` beside the buttons); `t_pad_hid_mac` drives discovery and callbacks on a synthetic composite pad: sticks under a Physical Pointer collection, wrapped axes, a sibling Mouse collection (relative X / Y and a click), a relative axis inside the gamepad, AC Back inside it and in a standalone Consumer Control collection, and a device with relative axes only.
- **Open:** not run with a SHIELD pad or a composite receiver (none here); upstream's retest on the SHIELD is pending, including whether its Back and Start match standard HID (`0x0C:0x224` Back, Button 12 Start).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) (v131072) with an NVIDIA SHIELD Controller 2015 on an M1 Max, found upstream ([PR #3352](https://github.com/seedds/nxnative/pull/3352), upstream nxnative `6a02debe`).

### Pro Controller clone read as raw HID

- **Symptom:** on the Mac, a Pro Controller clone that GameController does not list (a PowerA NANO pairs over Bluetooth as `Lic Pro Controller`, HID vendor and product 0) is read as a raw HID pad with its buttons in the wrong places, a full stick push reads 61 to 74% so the character does not run, and its four lights keep running in a chase.
- **Cause:** its report descriptor is Nintendo's, and until a console talks to it the pad stays in the Pro Controller's simple report `0x3F`. That report numbers its buttons unlike the default 8BitDo map and carries the sticks uncalibrated (the NANO's rest 9 and 11% off centre, its reach about 0.78 of the axis from there), and the pad chases its lights until it is given a player. The pad speaks the lights subcommand (`0x30`): it answered with `80 30` in report `0x21` ([PR #989](https://github.com/seedds/nxnative/pull/989)); that does not establish support for full input mode or device info.
- **Fix:** Nintendo's protocol is told by the descriptor, not the name or vendor (`pad_hid.h`, `pad_hid_nin_bit`). A pad read as raw HID that declares buttons in input report `0x3F`, the reply `0x21`, full input `0x30` and subcommand output `0x01` is asked for device info (`0x02`). One that answers gets the shared handshake (`jc1_handshake_report`, also used by [original Joy-Cons](#an-original-joy-cons-sensors-are-read-by-the-host)): full mode, sensor and vibration on, factory IMU calibration and factory/user stick calibration from SPI, then player lights. Its report `0x30` gives buttons and sticks through `pad_pro.h`; the buttons pass through the same `DM_HID_MAP` as `0x3F`, including Home/Capture overrides, without carrying old hat or trigger state across modes. The gyro uses `pad_jc1.h`'s calibrated sensor decoder (`jc1_unit_cal`, `jc1_input`, in the Pro Controller's frame): factory origins and per-axis sensitivity, the learned rest offset and monotonic sample times. The passive `motion_pro.h` decoder remains for identical genuine Pro Controllers. With output report `0x10`, the protocol pad gets its player's HD rumble (`dm_hidpad_rumble`, left and right actuators separately, every 15 ms while buzzing). Output reports go out on a serial queue (`g_hidpad_out`).
- **Fallback:** report `0x3F` uses its own button numbering and raw sticks measured from their rest against the reach seen so far (`pad_hid_raw_axis`, starting at 0.7: a full push read 99 to 100% on the NANO). It serves until full mode, for good after three unanswered device-info asks or no `0x30` after the handshake, and again after a return to `0x3F`, which starts another handshake. Player lights are independent of full mode and device info: a descriptor with `0x3F` buttons, reply `0x21` and output `0x01` can receive the LED command (`pad_hid_nin_lights`, `jc1_led_pattern`), even without full input `0x30`. They flash all four before joining and show the player's number after its first button press; they are also sent when device-info retries run out. A pad declaring only `0x3F` buttons receives no output. The log names the path; `DM_HID_LOG=1` logs simple-report usages.
- **Open:** the protocol path has not run on hardware: the NANO was played on the PR's `0x3F` path only (buttons in place, full tilt runs, player 1's light). Whether it accepts full mode, answers SPI reads, has a gyro or plays rumble is unknown, as is whether its descriptor declares the necessary reports. Its log names `answers Nintendo's subcommands`, `in full mode: read from its report 0x30`, the calibration received, or the fallback.
- **Found on:** a PowerA NANO over Bluetooth on macOS 27.2; not specific to a game. Played in FINAL FANTASY RESONANCE on the PR's `0x3F` path.
- **Check:** `t_pad_hid` covers the simple map, raw stick scaling, descriptor capabilities and identical button mappings in both modes, including disabled buttons, Home/Capture overrides, the d-pad and stale simple state. `t_jc1` covers the shared handshake, calibrated motion and separate rumble actuators. `t_pad_hid_mac` drives fake IOKit devices through retries, handshake, full input, calibration replies (a truncated reply is rejected; factory rest emits zero gyro, and per-axis sensitivity is applied), a custom map in full mode, player lights, rumble and return to simple mode. It checks lights without full input support and without a device-info answer, no output for buttons alone, an unchanged 8BitDo path and identical genuine Pro Controllers.

### A raw HID d-pad reads left as up-left

- **Symptom:** on the Mac, pressing left on a raw HID controller's d-pad registers up-left, and pressing up-left registers no direction.
- **Cause:** `b396df3a` removed `DM_BTN_LEFT` from the eight-slot hat table in `pad_hid_buttons()` (`pad_hid.h`). Value 6 then read the entry for up-left, and value 7 read the zero-initialized last slot.
- **Fix:** restore left at index 6 and up-left at index 7 in the shared decoder. It handles 8BitDo D-input hats and Nintendo's simple report `0x3F`. GameController and Nintendo's full report `0x30` decode the d-pad independently.
- **Found on:** synthetic raw HID hat inputs on macOS 27.2.1. A compiled probe decoded all eight directions before `b396df3a`, six after it, and all eight with the fix. [PR #2933](https://github.com/seedds/nxnative/pull/2933)
- **Check:** `t_pad_hid` checks the button mask for all eight directions. Only values 6 and 7 fail with the broken table. `t_pad_hid_mac` checks the Mac raw HID path with virtual controllers.

### Switch 2 hid calls that open the hid service

- **Symptom:** at boot, `game called nn::diag abort: Result 0xe15` at `sdk+0x6d6948` (under `hid::InitializeSensorFusion`, with `[RED] sf: the game connects to service hid itself`). Later, motion controls that go through the SDK's sensor fusion (`hid::UpdateSensorFusion`) do nothing: the controller's orientation stays still.
- **Cause:** these Switch 2 SDK calls ask the hid service or read its shared memory, neither of which the host provides, and the SDK aborts on the answer.
- **Fix:** the host answers them in `hle_hid.c`, checking six-axis handles as the SDK does (npads No1 to No8, Other and Handheld, else `0x58aca`; devices 0 to 2, else `0xd6ca`; a refused handle gets a red line):
  - Npad IMU (`EnableNpadImu`, `DisableNpadImu`, `IsNpadImuEnabled`, `GetNpadImuSamples`): the layer the SDK's own sensor fusion reads (`Enable` / `UpdateSensorFusion` → `GetNpadImuSamples` → `nn::imu::FullSensorState`). These four are the only users of the SDK's IMU state (`sdk+0x1056c48`), so the host keeps that state: on with the game's buffer, which no service writes; enabling twice answers `0x2908ca` as the SDK does.
  - IMU samples: `GetNpadImuSamples` writes 0x28-byte `NpadImuSample`s (`sdk+0x6ca8b8`) from the host's six-axis state ([Six-axis sensors](#six-axis-sensors), [live motion](#live-controller-motion)) at each 5 ms tick on the guest clock, in the layout and units of [The Npad IMU sample holds the acceleration first](#the-npad-imu-sample-holds-the-acceleration-first). The handle is the six-axis handle, which the fusion passes as the IMU handle ([The SDK's IMU handles are the console's six-axis handles](#the-sdks-imu-handles-are-the-consoles-six-axis-handles)). Like the console's ring in shared memory, the answer keeps no state per reader: each call returns the newest ticks up to the current one, at most the count asked for and the 16 the SDK's ring holds, oldest first, numbered by absolute tick + 1, and never below the last tick answered for that handle (a high-water mark per handle, so the numbers never go back). The fusion skips a number it has already taken and bridges or resets on a gap (`sdk+0x6d7198`), so several readers, a fusion created again, or an IMU switched off and on each get every tick. A handle whose controller is not connected has no samples.
  - `GetSixAxisSensorIcInformation`: the fusion's initialization (`sdk+0x6d7db0`) asks it through the hid service and, when it fails, never reads a sample (`sdk+0x6d7e40`). The 0xc8 bytes are, per sensor, its range, zero-offset bounds and sensitivity bounds (read at `+0x00`, `+0x10`, `+0x40`, `+0x44`, `+0x64`, `+0x74`, `+0xa4`, `+0xa8` into `nn::imu::SixAxisSensorInformation`, `sdk+0x6fed30`); a sample past twice the range resets the fusion. The host answers yuzu's values for this layout: 2000 deg/s and 8 G (the Switch six-axis IC's full scale), offsets within ±10 deg/s and ±0.0612 G, sensitivity 0.95 to 1.05 with ±0.003 cross-axis.
  - `IsSixAxisSensorDeviceNewlyAssigned` (from hid shared memory, `sdk+0x6c1330`): no, so the fusion is not reset each update; `ResetIsSixAxisSensorDeviceNewlyAssigned`: nothing to clear. `StoreSixAxisSensorCalibrationParameter` keeps the fusion's 0x744-byte gyro bias calibration per device for the run and `LoadSixAxisSensorCalibrationParameter` gives it back ([The SDK's sensor fusion needs sensor noise and a stored calibration](#the-sdks-sensor-fusion-needs-sensor-noise-and-a-stored-calibration) for a device with nothing stored). Six-axis handles are checked as the SDK's `VerifyValidSixAxisSensorHandle` does (`sdk+0x6d8440`: also device index 0 to 2, else `0xd6ca`).
- **Note:** unconfirmed against a console: which Joy-Con a pair's device index 0 and 1 are (the host takes 0 as the left, as for six-axis handles), the IC bounds besides the ranges (not read from a Switch 2 controller), and the Result a console gives for a device with no stored calibration (the only caller tests for 0).
- **Found on:** Nintendo Switch Sports Resort (`04008E001F098000`, v65536). `t_hid.c` covers each call, the sample window and numbering, unit conversion, sign switches and concurrent readers.

### The SDK's IMU handles are the console's six-axis handles

- **Symptom:** a Switch 2 game's motion controls stay still and its motion calibration fails: Nintendo Switch Sports Resort's "Calibrar los sensores de movimiento de los mandos Joy-Con" ("place the Joy-Con on a flat surface") ends after 30 s with "No se ha podido completar la calibracion" every time, though `GetNpadImuSamples` is called thousands of times; `StoreSixAxisSensorCalibrationParameter` is never called (`DM_HLECOUNT`).
- **Cause:** the sensor fusion's handle is made by the SDK itself (`GetSensorFusionHandles` → `GetNpadImuHandles`, `sdk+0x6ca570` → `nn::hid::utility::GetSixAxisSensorHandle`, `sdk+0x6d8490`; the SDK's own `GetSixAxisSensorHandles` calls the same utility). That is the console's `SixAxisSensorHandle`: byte 0 the `NpadStyleIndex` (3 full key, 4 handheld, 5 Joy-Con pair, 6 left, 7 right), byte 1 the npad id, byte 2 the device (0 left and 1 right of two sensors; SDK 22 gives full key and handheld one sensor, device 2). The host's `GetSixAxisSensorHandles` put the style's bit number in byte 0 instead, and `GetNpadImuSamples` read the SDK's handle that way: a pair on No1 (`0x5`, `0x10005`) was style bit 5, never connected, so every call answered 0 samples and the fusion left at `sdk+0x6d777c` without feeding anything.
- **Fix:** the host's six-axis handles use the console's numbering too (`six_style_index`, `six_style_bit` in `hle_hid.c`; devices 0 to 2 for every style, as SDKs differ in the device they give; a style set of several styles gets the one the npad is shown in; the stored calibration of device 2 is device 0's), so the SDK's handles and the host's read the same everywhere; `t_hid.c` checks both kinds, player 2's npad and a split pair's left and right Joy-Cons.
- **Found on:** Nintendo Switch Sports Resort (`04008E001F098000`, v65536).

### The Npad IMU sample holds the acceleration first

- **Symptom:** a Switch 2 game's motion calibration never completes and, with a real controller, what it moves turns by itself in circles while the controller lies still: Nintendo Switch Sports Resort's "place the Joy-Con on a flat surface" ends after 30 s with "No se ha podido completar la calibración" every time, and its paddle spins. A probe on the fusion's output sample (`DM_PROBE=sdk:6d7118@x22+0x40`: `GetUnbiasedAcceleration` z, then `GetUnbiasedAngularVelocity` in deg/s) reads an acceleration of 0 G and an angular velocity of about +560 deg/s about z with a flat sensor and no controller.
- **Cause:** `NpadImuSample` (0x28 bytes, `sdk+0x6ca8b8`) is the sampling number, the ns since the previous sample, the acceleration in m/s² at +0x10 and the angular velocity in rad/s at +0x1c. `UpdateSensorFusion` copies +0x10 negated (`sdk+0x6d7334`) to nn::imu's sample +0x24, which nerd's `FeedSixAxisSensorValues` (`sdk+0x6ffac0`) and `GyroPointing::FeedImuSampleNoUpdate` (`sdk+0x700e90`, `sdk+0x700f84`) take as the acceleration, and +0x1c as it is to +0x18, the angular velocity. The host wrote the angular velocity first and both negated, so the fusion took gravity (9.8 m/s²) for a 9.8 rad/s turn about the vertical (562 deg/s), its stable orientation turned at that rate and `GyroPointingCore::Recover` (`sdk+0x712aa0`) ran about once a second.
- **Fix:** `GetNpadImuSamples` writes the acceleration (G × 9.80665, −9.8 m/s² on z lying face up) at +0x10 and the angular velocity (revolutions/s × 2π) at +0x1c, in the six-axis state's own signs: the fusion negates the acceleration into a specific force and reports it as −m/s² / 9.80665 G (`sdk+0x6d74a0`), so its outputs read as the six-axis state does. The time step is the sample timestamps' (`(t − t_prev) / 1e9`, `sdk+0x700ff0`, from the samples' `delta_ns`). `DM_IMU_ACC_SIGN` / `DM_IMU_GYRO_SIGN` (`-1`) negate either and `DM_IMU_AXES` permutes the axes, for a test.
- **Check:** the same synthetic run then read an angular velocity of −0.004 deg/s (5 to 95% within ±0.17), −1.000 G on z, a stable orientation turning 0.16 deg/s, the fusion's ready flag (bit 1 of the orientation's flags word, `sdk+0x6d78f8`) set, no `Recover`, and the game's calibration passed. With a right Joy-Con 2 and with a DualSense the calibration passes and the paddle follows the controller in matches. `t_hid` (`t_imu_conversion`: a known pose through the whole conversion to the bytes the fusion reads).
- **Found on:** Nintendo Switch Sports Resort (`04008E001F098000`, v65536).

### The SDK's sensor fusion needs sensor noise and a stored calibration

- **Symptom:** with IMU samples flowing from the host's own flat sensor, the fusion reset itself several times a second (its initialization, which asks `GetSixAxisSensorIcInformation`, ran 612 times in one Nintendo Switch Sports Resort session) and never took the controller for still; `StoreSixAxisSensorCalibrationParameter` was never called. With a DualSense its orientation drifted.
- **Cause:** samples that never change. The fusion's stillness detector (`GyroPointingStateDetector::UpdateMovingDetection`, `sdk+0x736260`) calls the controller moving when the lag-1 autocovariance of the last 64 accelerations on x and z (m/s²) is beyond 1e-6, and its bias calibration needs the Kalman filter's bias deviation under 0.01 rad/s (`GyroPointingKalmanFilter::GetCalibrationState`, thresholds at `sdk+0xbb85b8` / `+0xbb7df8`), which an exactly constant input does not give it. On a console the fusion rarely has to learn the bias: `LoadSixAxisSensorCalibrationParameter` gives it the controller's stored calibration, which it takes as its initial bias (`sdk+0x6d7f7c`) and counts as calibrated (`+0x538`); the host answered none (`0xd8ca`). A GameController (DualSense: 0.34, 0.20, −0.66 deg/s at rest) reports its gyro with its rest offset, which a zero bias would then leave in.
- **Fix:** `GetNpadImuSamples` adds fixed Gaussian noise to the host's own samples (gyro 0.1 deg/s, acceleration 0.05 mG, a hash of the tick, device and axis, so a tick read again reads the same; `DM_IMU_NOISE=0` removes it, `=<deg/s>,<mG>` sets other spreads, also through `DM_CTL`'s `env`). A live controller carries its own noise: its interpolated ticks are left as they are, and only a tick with no change of its own (a held sample, or between two that read alike) gets a tenth of the host's noise. `LoadSixAxisSensorCalibrationParameter` answers a device with nothing stored this run with the ideal sensor's calibration (zeros, a zero bias) when the sensor's gyro offset is taken off (`six_offset_known`: the host's own sensor, a HID or Joy-Con 2 stream, a GameController once its offset is learned), else `0xd8ca` as before. The host learns a GameController's rest offset and takes it off (`motion_rest`, `motion_fusion.h`: a first offset from two agreeing still seconds, at most 2 deg/s so a slow steady turn is not taken for one, later ones only within 1.25 deg/s of it, ramped in over 0.75 s; forgotten when the stream goes stale or another controller takes the player), and drops a stream's first all-zero sample (a Joy-Con 2's first report; later zeros can be a free fall).
- **Check:** `t_hid` (`t_imu_noise`: spread, whiteness and the stillness criterion; `t_live_rest`, `t_live_still_dither`, `t_six_ic_info`, the calibration load and store) and `t_motion` (`rest_checks`). With a DualSense, over 1,876 still answers the game got a mean gyro of 0.00, −0.04, −0.00 deg/s after its offset (0.6, 0.1, −0.7 deg/s) was learned.
- **Found on:** Nintendo Switch Sports Resort (`04008E001F098000`, v65536).

### Whether a vibration device is mounted

- **Symptom:** with rumble on, `[RED] sf: the game connects to service hid itself`, then `CRASH sig=11 addr=0` in the SDK's mounted check (`hid::detail::IsVibrationDeviceMounted`, `sdk+0x24254c` in SDK 7, under `hid::IsVibrationDeviceMounted`; a Switch 2 SDK's form is `hid::IsOunceVibrationDeviceMounted`). With rumble off in the host's settings the game never asks.
- **Cause:** the SDK's own call opens the hid service, which sm refuses (0xe15), and reads the null service object. With rumble off the affected game did not ask; current channel handles do not depend on the rumble setting.
- **Fix:** `hle_hid.c` answers the Switch 2's form, `IsOunceVibrationDeviceMounted` (the Switch 1 form is no longer taken over in this fork). On Horizon a device is mounted when the npad's connected controller has the handle's style and an actuator on that side; the host reports it mounted when the handle names a channel of the npad's controller (`vib_valid`), whether or not a haptics output is routed yet ([A vibration device before its controller connects](#a-vibration-device-before-its-controller-connects)).
- **Found on:** Super Mario Odyssey 1.4.1, entering a Sand Kingdom pipe (`main+0x5d3150` asks the Switch 1 form for each handle of a controller whether any is mounted; GitHub issue #715). Kirby Air Riders calls the Switch 2's form for its handles soon after boot. It crashed a run with a window, and no headless run; why only that one was not checked.

### Vibration handles before a controller is reported

- **Symptom:** `DM_RUMBLE_LOG=1` shows the game's startup handle request answered with none, then every vibration value sent to handle 0 and reaching no output for the whole session, although a controller with haptics (a DualSense on the Mac) is connected. A game that rumbles would stay silent.
- **Cause:** `hid::GetVibrationDeviceHandles` answered 0 handles until a controller's haptics were routed. Games ask once at startup, before GameController reports the pad, and keep the answer. On Horizon the handles are computed from the npad id and style alone (libnx `_hidGetVibrationDeviceHandles`).
- **Fix (resolved):** the handles no longer wait for a routed output: with an output sink installed (`dm_haptics_has_output`), a connected npad style gets its handles even with rumble off; `vib_send` checks for a permitted, routed output at each send (`hle_hid.c`). A missing sink or a disconnected npad still yields no handles. `DM_RUMBLE_LOG=1` logs the handle requests and, once a second, the values sent, those with no routed output and the peak amplitude. Each input value is counted separately, including mixed batches; a mutex protects the diagnostic totals across game threads. `t_hid` covers cached startup handles delivering a nonzero value after routing, mixed-batch diagnostics and concurrent sends; `t_hid_tsan` checks those sends for data races.
- **Found on:** Unicorn Overlord (the Asian release, `010054B01AD92000`), in the log only: the game has no rumble of its own (it sends amplitude 0 throughout), so nothing could be felt before or after. A later Echoes of Wisdom test checks startup handles and device-info answers on a game that rumbles.

### A vibration device before its controller connects

- **Symptom:** with rumble on, a game asks for vibration handles at boot and gets two, then sends one idle value and none for the rest of the session; nothing vibrates although a controller connects a few seconds later. `DM_RUMBLE_LOG=1` shows `GetVibrationDeviceInfo` answering mounted 0 (and the mounted check, when asked, false) before the pad connects.
- **Cause:** the mounted check ([Whether a vibration device is mounted](#whether-a-vibration-device-is-mounted)) and `GetVibrationDeviceInfo` answered from `vib_targets`, which keeps only the players with a routed haptics output. A game that asks once at boot, before a Bluetooth pad has connected (the Switch 2 transport connects on a button press while the game runs), keeps "not mounted" for the session and never sends rumble. On Horizon the controller is there before the game boots.
- **Fix:** `hle_hid.c`'s `vib_valid` is the handle and npad-style check behind `vib_targets` without the routed-output mask; `IsOunceVibrationDeviceMounted` and `GetVibrationDeviceInfo` answer from it regardless of the rumble setting. `vib_targets` keeps the mask, so values sent before the pad connects are still dropped rather than played later.
- **Found on:** The Legend of Zelda: Echoes of Wisdom; its game note records the before/after traffic and physical controller validation from [PR #2859](https://github.com/seedds/nxnative/pull/2859).
- **Check:** `t_hid` (`t_vibration`: the mounted and actuator answers before a route and with rumble off, values still dropped until rumble is on and the output routed); `t_hid_tsan` also queries them concurrently with sends. Diagnostic counters are atomic across game threads.

### Controller haptic engines without advanced players

- **Symptom:** a controller (an Xbox Wireless Controller, a GameSir Super Nova, a GameSir Cyclone) never vibrates in a game; the log repeats `[RED] haptics: controller left handle create player: Couldn’t communicate with a helper application. (NSCocoaErrorDomain 4097)`. The engine itself starts.
- **Cause:** the engines that `GCDeviceHaptics` makes are served by `gamecontrollerd`, which tells CoreHaptics whether it offers advanced pattern players (`HapticServerConfig.supportsAdvancedPatternPlayers`; its log: `Server returned: supports audio: 0 adv players: 0`). `-[CHHapticEngine createAdvancedPlayerWithPattern:error:]` does not check that; the request reaches the server, which refuses it, and the XPC reply comes back as NSCocoaErrorDomain 4097, on every locality (All, Default, Handles, Left Handle, Right Handle). The output made only advanced players (a looping 30 s event driven by dynamic parameters), and a player failure is retried on the same handle, so the fallback to the default locality could not help either. On the Mac the refusal also leaves that engine unusable: a plain player or a restart on it fails with -4810. A plain `CHHapticPatternPlayer` on a new engine plays and takes dynamic intensity and sharpness controls.
- **Fix (resolved):** when the advanced player cannot be made, the channel drops that engine, makes a new one and keeps using plain players (`haptics_apple.m`, log line `has no advanced players … plain players`). A plain player cannot loop, and one stopped in the middle of an event left the Xbox controller's motors running at its level after the engine and the process were gone, until the controller was switched off. So plain players play pulses of 0.5 s that end on their own: the next one is scheduled where the last ends while the effect lasts, each starts at the current level (its pattern's initial control) and takes later levels as controls, and a stop sends level 0 to the playing pulses and stops the engine only after the last one has ended. Checked on an Xbox controller through the host's own `haptics_apple.m`: low and high levels are told apart, full level feels like a plain pattern at intensity 1, and the motors stop after the effect. `t_haptics_apple` covers a server without advanced players: the new engine, the pulses following each other, no pulse cut by a stop.
- **Left and right handle engines override each other (current).** Without advanced players, the engines of `LeftHandle` and `RightHandle` playing at once were not felt on the Xbox controller, while one engine on `Handles` (or on `All`) at the same intensity was; a trigger engine playing beside them likewise drowned them out. So a split route whose first advanced player is refused becomes one engine on `Handles` (`Default` when the controller does not list it) that plays both motors mixed (`merge`, log line `plays both motors on one engine`): the rumble is the same on both sides. A DualSense (`GCProductCategoryDualSense`) is not merged: with plain players on its left and right handle engines, each side alone, both at different levels and silence were felt as sent (PR #986: a standalone probe and Super Mario Odyssey's buried Power Moons, over Bluetooth on macOS 26.7.1, with plain players set at connection). So its handles keep their engines, each moves to plain players when its advanced player is refused (log line `has no advanced players … plain players`, once per handle), and left and right keep their own levels. Why the Xbox controller's handle engines override each other is not known (its rotating motors, or its driver in `gamecontrollerd`), so other controllers with both handle localities stay merged until one is tried. Not run: a DualSense over USB, a DualSense Edge, and the refusal on both handles of a real DualSense (the left handle's is what main already met). `t_haptics_apple` covers the merge and the DualSense's handles, with and without advanced players.
- **Low levels on rotating motors (open).** Controller motors and the Switch's resonant actuators disagree at low amplitudes, in two directions. The Xbox controller's motors showed nothing at intensity 0.05, a faint buzz from about 0.1 and a soft one at 0.3, so Breath of the Wild's charged attack (0.07 for about 3 s, `DM_RUMBLE_LOG=1`) was not felt even at `DM_RUMBLE_GAIN=2.5`. Mario Kart 8 Deluxe holds its low band at 0.1–0.4 all race long (about 30 changes a second, 0.84 peaks every few seconds): a texture on a Joy-Con, rumble that never lets up on a DualShock 4's motors. A floor with a square-root rise (0.15 + 0.85·√x) fixed the first and would make the second much worse, so the mapping stays linear. `DM_RUMBLE_MIN=0..0.9` (default 0) silences controller levels below it and stretches the rest over the full range, on every controller route; 0.45 leaves Mario Kart 8 Deluxe's crashes and drifts, as an emulator gives them on that controller. `t_haptics_apple` covers the cutoff.
- **Found on:** The Legend of Zelda: Breath of the Wild (1.9.0), on macOS 27.0.1 with an Xbox Wireless Controller over Bluetooth and an Xbox 360 USB receiver; NieR:Automata The End of YoRHa Edition (the Asian release, `0100B8E016F76000`) on an iPhone with a GameSir Super Nova in DualShock 4 mode, which plain players fixed; Mario Kart 8 Deluxe (4.0.1) on macOS 27.0.1 with a GameSir Cyclone; the same error in issue #219 (Sifu, provisional profile), controller unnamed.

### Paired Joy-Cons rumble both halves on one channel

- **Symptom:** a paired Bluetooth `Joy-Con (L/R)` rumbles both Joy-Cons together for every effect—including when a game splits the pair into sideways `JoyLeft` and `JoyRight` npads so player 1's rumble shakes player 2's Joy-Con too—and logs `localities All, Default, JoyCon (L), JoyCon (R), 1 channels`.
- **Cause:** `GameController` reports the per-half actuator localities of a combined `Nintendo Switch Joy-Con (L/R)` as `"JoyCon (L)"` and `"JoyCon (R)"` rather than `GCHapticsLocalityLeftHandle` and `GCHapticsLocalityRightHandle`. `haptics_apple.m` checked only the handle localities and fell back to `Default` (one mixed channel), and on a server without advanced players `c.merge` would also collapse a two-channel route back to `Default`.
- **Fix:** when `supportedLocalities` contains both `"JoyCon (L)"` and `"JoyCon (R)"`, `configure` creates motor 0 on `"JoyCon (L)"` and motor 1 on `"JoyCon (R)"`. These localities keep separate engines with plain players too. A failed factory or engine start uses the channel's existing backoff and retries its own locality: neither `merge` nor the handle route's `Default` fallback is installed, since mixing can cross npads. Ordinary handle localities retain their fallback.
- **Current reach:** original Joy-Cons normally use the Mac's [raw HID transport](#an-original-joy-cons-sensors-are-read-by-the-host), including its per-device rumble, so they bypass this adapter's engine route. This fix serves the remaining Core Haptics route (the Mac's GameController fallback, `DM_JC1=0`); it does not add split Joy-Con input support to GameController front ends.
- **Verification:** `t_haptics_apple` covers each side's factory and start failures with advanced and plain players, locality-preserving recovery, and active controller-object replacement through split, rejoin, disconnect and reconnect. Old callbacks, snapshots, pulse renewals and delayed stops cannot affect the replacement route. `t_hid` (`t_joycon_vibration_lifetime`) checks active vibration through single / dual assignment and rejection of stale single handles after rejoin. These are synthetic boundary tests; post-fix physical split / join validation remains open.
- **Found on:** Super Mario Party (`010036B0034E4000`, provisional profile), paired Bluetooth Joy-Cons on an Apple M1 Pro with macOS 26 (PR #2472's original diagnosis log).

### A haptic engine that stops under a call raises, and ended the app

- **Symptom:** the app dies with `*** Terminating app due to uncaught exception 'com.apple.CoreHaptics', reason: '-[CHHapticEngine(CHHapticEngineInternal) checkEngineRunning:]: self.running'`, then `[dm] CRASH sig=6` in `__pthread_kill`; no `[RED] haptics` line comes first. Seen after about 85 s of a Mario Kart World race on an iPhone, a few seconds after the log's `oe focus state` changed twice (2, then 1).
- **Cause:** Core Haptics reports a player or parameter call on an engine that is not running by raising an `NSException`, not by returning an `NSError`, and offers no running state to ask first. The engine stops on its own at any time (an audio interruption, the haptics helper's exit) while its stopped handler is only queued onto the adapter's serial queue, and the adapter's own stop is asynchronous, so any queued work that calls a player (a level change, a pulse renewal, the idle release, a stop on focus loss or reconfiguration) can reach an engine that is no longer running. Every `error:` path in `haptics_apple.m` was already covered; this one is not an error return. The log has no backtrace, so which call raised in the crash is not known; it came a few seconds after a focus loss and its return, which stop and restart the engines.
- **Fix (resolved):** every entry into a rumble channel (`apply:`, `stop`, the queued pulse renewal and delayed engine stop) runs its Core Haptics calls inside `guarded:work:`. A caught exception is handled as a failed engine (`stoppedEngine:stage:`) that is never called again: the channel drops its engine and players without stopping or silencing them (a stop sends a plain player zero, which raises once more; nothing plays from an engine that is not running), backs off like a failed start, clears the queued output and logs `[RED] haptics: <target> <stage> on a stopped engine`; the next effect builds a new engine. `t_haptics_apple` raises from a player's `sendParameters` on the advanced-player route and on the plain-player route, from a level change and from the idle release, and checks the channel clears and recovers; without the guard the first case ends in the same uncaught `NSException`, and with a recovery that stops the channel the plain-player case does.
- **Found on:** Mario Kart World (1.8.0, a physical iPhone, run of 2026-11-07).

### DualShock 4 rumble through its effects report

- **Symptom:** on the Mac, a DualShock 4 or a controller that presents itself as one (a GameSir Cyclone over Bluetooth: HID vendor `054C`, product `05C4`, `productCategory` "DualShock 4") does not rumble; Core Haptics failed on every locality with NSCocoaErrorDomain 4097 (issue #363, also in a minimal Swift app), while the same controller rumbles in an SDL-based emulator.
- **Cause:** the Core Haptics route was the only one. SDL's hidapi driver does not use it for a DualShock 4: it writes the controller's effects report, which needs no haptics server and keeps the strong and weak motors apart, where a server without advanced players merges them (above).
- **Fix (resolved):** on the Mac, a controller GameController calls a DualShock 4 is driven through that report when a free HID device of vendor `054C`, product `05C4` / `09CC` / `0BA0` is there ([asked of the registry at each connect](#a-dualshock-4-that-connects-after-the-first-stays-on-core-haptics); `ds4_route`, log line `rumble through the DualShock 4 effects report`): report `0x11` over Bluetooth (78 bytes, flags `0xC4`, rumble-only flag `0x01` so the light bar is left alone, CRC32 over `0xA2` and the first 74 bytes), `0x05` over USB (32 bytes), sent only when a motor byte changes. As the emulators feed SDL, the strong motor follows the low band and the weak one the high band (0.85 / 0.15 left / right), linearly, with `DM_RUMBLE_GAIN` and `DM_RUMBLE_MIN`. Without the HID device the controller keeps the Core Haptics route. GameController does not name a controller's HID device, so two DualShock 4s each get one, possibly swapped. `t_haptics_apple` covers the CRC, the fallback without the device and the report's bytes on fake devices.
- **Found on:** Mario Kart 8 Deluxe (4.0.1) and The Legend of Zelda: Breath of the Wild (1.9.0) with a GameSir Cyclone over Bluetooth on an M5 Pro, macOS 27.0.1: rumble on crashes and drifts (with `DM_RUMBLE_MIN=0.45`), on hits and chopping, stopping after each. Not checked: a genuine Sony DualShock 4, the USB report.

### A DualShock 4 that connects after the first stays on Core Haptics

- **Symptom:** with two controllers that present themselves as DualShock 4s on the Mac, the one turned on first rumbles normally and the one turned on later is barely felt. The first logs `rumble through the DualShock 4 effects report`; the later one logs `haptics: player 2 controller …, localities …`, then `has no advanced players (NSCocoaErrorDomain 4097): plain players` and `plays both motors on one engine (Handles)`.
- **Cause:** `ds4_route` kept one `IOHIDManager` for the session and never scheduled it. A manager adds devices once when its matching is set; later arrivals and removals reach it only through a notification port, which needs a run loop or a dispatch queue (Apple's `IOHIDManager.c` in IOKitUser). So `IOHIDManagerCopyDevices` went on answering with the devices of the first DualShock 4's connect: a later controller found none free and fell back to Core Haptics, whose plain pulses on `Handles` the reporter barely felt. From the same code, a controller that disconnected and came back would get its dead device back and no rumble; that was not reported.
- **Fix (resolved):** `ds4_take` asks the registry at each connect (`IOServiceGetMatchingServices` on vendor `054C`) and each player owns the device it opens, closed when the controller goes. A device in use is told by its registry entry ID, since two handles on one device are not `CFEqual`. Scheduling the manager was not chosen: the lookup would then depend on the arrival callback running before GameController's connect, and a missed one would leave the controller on Core Haptics for good. `t_haptics_apple` covers a controller connecting later and one coming back, on fake devices; the same lookup finds the same devices as a manager on this Mac's own HID devices. How weak Core Haptics is on this controller was not measured: a controller with no effects report stays [as it was](#controller-haptic-engines-without-advanced-players).
- **Found on:** Mario Kart World (1.0), issue #1165, two GameSir Cyclones over Bluetooth on an M5 Pro, macOS 27.2: from the reporter's log. Not yet run on two real controllers.

### Mac menu bar over the fullscreen game

### Pro Controller rumble through its rumble report

- **Symptom:** on the Mac, a Switch Pro Controller or a controller that presents itself as one (an 8BitDo pad, GameSir Nova, or Xtreme XTRE041 in Switch mode: HID vendor `057E`, product `2009`, `productCategory` "Switch Pro Controller") does not rumble through Core Haptics, or on a genuine Switch Pro Controller feels thin and loses stereo and dual-band texture. The log shows no error: `haptics: player 1 controller Pro Controller, localities All, Default, Handles, Left Handle, Right Handle`, then `has no advanced players (NSCocoaErrorDomain 4097): plain players` and `plays both motors on one engine (Handles)`, and the plain players start and play.
- **Cause:** the Core Haptics route was the only one for GameController-listed Pro Controllers. Without advanced players `haptics_apple.m` merges both handles onto one engine and collapses the game's two bands per actuator into one intensity and sharpness, so a genuine Pro Controller loses stereo and dual-band HD rumble ([issue #2804](https://github.com/seedds/nxnative/issues/2804)). On Switch-mode clones `gamecontrollerd`'s Core Haptics output produced no felt vibration at all; on a GameSir Nova, Core Haptics fired only at `hapticSharpness = 0` and stayed silent at `0.5` or `1.0`, while the host sends about `0.5` ([PR #2607](https://github.com/seedds/nxnative/pull/2607)). `gamecontrollerd` lies outside this repository.
- **Fix (resolved):** on the Mac, a controller GameController calls a Switch Pro Controller is driven through Nintendo's HD rumble output report `0x10` when a free, non-synthetic HID device of vendor `057E`, product `2009` accepts subcommand `0x48 0x01` (enable vibration; `pro_route` in `haptics_apple.m`, log line `rumble through the Pro Controller rumble report`). The registry lookup (`hid_take`) is shared with the [DualShock 4](#a-dualshock-4-that-connects-after-the-first-stays-on-core-haptics) and skips GameController's synthetic HID devices (`kIOHIDGCSyntheticDeviceKey`); accepting `0x48 0x01` also passes over the dead second entry IOKit can keep after a long Bluetooth disconnect ([issue #2237](https://github.com/seedds/nxnative/issues/2237)). Reports are padded to 49 bytes over Bluetooth (`JC1_REPORT_LEN`) and 64 bytes over USB, as SDL and `pad_jc1_mac.h` / `pad_hid_mac.h` send them. Each actuator keeps its own low and high band at the game's frequencies via `pad_jc1.h`'s exact HD rumble encoder (`jc1_rumble_encode`, `jc1_rumble_report`), with `DM_RUMBLE_GAIN` and `DM_RUMBLE_MIN` applied as on every other route. Changes are paced to 15 ms with peak-hold (`jc1_rumble_hold`) so 5 ms pulses are not dropped and Bluetooth is not flooded at 200 Hz, an active level refreshes every 30 ms, and stop, focus loss, sink switch or disconnect sends neutral (`00 01 40 40`) and cancels timers. Without a free live device, the controller stays on Core Haptics.
- **Check:** `t_haptics_apple` covers synthetic and dead-entry skipping, `0x48 0x01` enable, 49-byte Bluetooth and 64-byte USB report encoding, stereo L/R and exact log-table bands, 15 ms pacing with peak-hold, 30 ms refresh, idle timer stop, `DM_RUMBLE_GAIN` / `DM_RUMBLE_MIN`, focus suspend, sink handover, disconnect cleanup, failed-silence non-spinning, Core Haptics fallback, and two Pro Controllers.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (v131072): an 8BitDo pad over Bluetooth, USB and 2.4 GHz receiver on macOS 27.2 ([PR #2607](https://github.com/seedds/nxnative/pull/2607), reproduced on an M3 Pro), a GameSir Nova over Bluetooth and 2.4 GHz receiver on macOS 27.2, a genuine Nintendo Switch Pro Controller over Bluetooth on an M3 Pro with macOS 26.6.2 ([issue #2804](https://github.com/seedds/nxnative/issues/2804)), and an Xtreme XTRE041 over Bluetooth and USB on an M1 Pro ([PR #2787](https://github.com/seedds/nxnative/pull/2787)).
- **Open:** hardware retest of this unified route on a genuine Nintendo Switch Pro Controller over Bluetooth and USB, on 8BitDo / GameSir Nova with 49/64-byte padded reports, on an XTRE041 over USB without the `0x80 0x02` / `0x80 0x04` USB handshake, and with two Pro Controllers connected at once (GameController names no HID device, so two connecting together may swap their rumble, as for the DualShock 4).

### An 8BitDo Ultimate 2 Wireless with no rumble on the Mac

- **Symptom:** an 8BitDo Ultimate 2 Wireless (`2DC8:6012`, firmware 1.03 or later) over Bluetooth LE plays its buttons and sticks but never rumbles. The log says `haptics: player 1 controller 8BitDo Ultimate 2 Wireless, localities none, 0 channels`.

- **Fix:** `haptics_apple.m`'s `abitdo_route`, for a controller with no localities whose `vendorName` contains `8BitDo`, when a free, non-synthetic `2DC8:6012` gamepad or joystick HID device takes a zero report `0x05` (which skips dead Bluetooth entries and firmware without the report); the log says `rumble through the 8BitDo output report 0x05`. - **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game) upstream (upstream nxnative `3e8f1ce5`, PR #2763: an M5 MacBook Air, macOS 27.2; the report also confirmed in PR #1934). Open: the revised route on the pad itself, firmware 1.02, two pads (they may swap their rumble, as two DualShock 4s), the USB and 2.4 GHz dongle (`2DC8:310B`) modes. Not on a pad here.

### Scripted presses on a path of their own

- **Symptom:** with a controller connected (a DualShock 4 here), `DM_KEYS` and `DM_CTL` presses are logged (`DM_KEYS: … press …`) but the game does not react to them, or only now and then; without the controller the same script works.
- **Cause:** scripted presses went through player 1's controller path (`dm_pad_set`). A connected controller publishes its whole state there on every change, replacing scripted holds and sticks; the press latch preserves only the first read. Script release also cleared the physical controller's state.
- **Fix (resolved):** `DM_KEYS` and `DM_CTL` set buttons, a press latch and sticks of their own (`script_set` in `hle_hid.c`), ORed with the keyboard path and player 1's controller when the game reads player 1; for the sticks, the one deflected more wins. Shake includes the scripted path too.
- **Check:** `dm/host/tests/t_hid.c` (`t_script`) runs the scripted publisher with a controller update during the hold: buttons survive repeated reads after the latch is consumed, the scripted stick wins over drift, shake continues, and release preserves physical input. Short presses are latched once, all four axes reach the handheld npad, and player 2 stays separate.
- **Found on:** Batman: Arkham Knight (`0100ACD0163D0000`), reported in [PR #326](https://github.com/seedds/nxnative/pull/326) while driving the opening route with `DM_KEYS` and a DualShock 4. Reproduced independently in the host HID test without game files; its game profile is not in this checkout.

### Mac pointer stays over the game

- **Symptom:** on the Mac, the mouse pointer stays over the game picture while playing with a controller or the keyboard, in a window and in fullscreen ([issue #675](https://github.com/seedds/nxnative/issues/675)).
- **Cause:** AppKit hides the pointer only for an app that asks, and `front_mac.m` never asked.
- **Fix:** a key the game takes, a controller button or a stick past 15% (GameController and raw HID pads alike, `pad_set`) calls `[NSCursor setHiddenUntilMouseMoves:YES]` (`cursor_hide_for_input`), only while the game window is key, the app is active and the pointer is over the content view. AppKit shows the pointer again on the next mouse movement, and `input_release` shows it when the window loses focus.
- **Check:** with the pointer over the game, a controller button or the keyboard hides it; moving the mouse shows it; over the title bar, or with another app active, it stays.
- **Found on:** every game on the Mac (general); [PR #584](https://github.com/seedds/nxnative/pull/584).

### Mac display sleep during controller play

- **Symptom:** the Mac dims or turns off its display and can reach the lock screen while the player is using a controller, in a window or in fullscreen.
- **Cause:** macOS counts keyboard and mouse input as user activity, not a controller's, so its display-idle timer keeps running. The host's `NSActivityUserInitiated | NSActivityLatencyCritical` activity (`front_run`) prevents idle system sleep, not display sleep.
- **Fix:** while the game window is key, `front_mac.m` holds a second activity with `NSActivityIdleDisplaySleepDisabled` (`display_awake`; `pmset -g assertions` shows `PreventUserIdleDisplaySleep` "NativeNavi active game window"). `input_release` lets go of it when the window loses focus or is minimized, `input_resume` takes it again, and startup takes it if the window became key before the focus observers were installed. Windowless runs never hold it. An explicit lock or sleep still works, and no input is synthesized.
- **Found on:** Mario Kart 8 Deluxe on the Mac, controller play; every game on the Mac (general); [PR #741](https://github.com/seedds/nxnative/pull/741).

### Mouse and keyboard

- **Symptom:** the first boot aborted in `hid::GetMouseState` (the SDK's mouse resource was never initialized).
- **Fix:** the mouse and the keyboard answer as not connected (`hle_hid.c`): `hid::InitializeMouse` and `hid::InitializeKeyboard` do nothing, `hid::GetMouseStates` returns 0 entries and `hid::GetKeyboardState` a zeroed state with the next sampling number. The single-state `GetMouseState` and the `GetKeyboardStates` history that the games below call are not taken over in this fork.
- **Found on:** 13 Sentinels: Aegis Rim (SDK 11, `GetMouseState`); Monster Hunter Rise (SDK 11, `GetKeyboardStates`).

## Applets

### System applets opened by `Show…` calls

- **Symptom:** null read in `sdk` under `nn::applet::CreateLibraryApplet` when a game calls a `Show…` function that opens a system applet (Engage: title menu → DLC, its shop page); `Show…` overloads found in the imports before they were met.
- **Cause:** every `Show…` call that opens a system applet (eShop, friend lists, web pages, error screens) goes through the applet proxy that `oe::Initialize` would have set up, and the host has none.
- **Fix:** hook each `Show…` overload the game imports: list `main`'s undefined symbols containing `Show` / `Applet` and grep the host sources for each mangled name; one overload missing is enough to crash. The host has `web::ShowWebPage`, which is logged and returns failure (`hle_offline.c`), and `err::ShowError` with a `Result` (`hle_misc.c`) or an `ErrorCode` (`hle_offline.c`), which logs the error and shows nothing. The controller applets are in `hle_hid.c` ([The controller applet waits for players](#the-controller-applet-waits-for-players)).
- **Found on:** Fire Emblem Engage (its shop pages, whose stand-ins are not in this fork).

### Library applets take the application's focus

- **Symptom:** entering 2P stops the game on its 2P screen: the same frame repeats, the music plays, no controller does anything, until the window loses and regains focus (Mario Kart 8 Deluxe, every launch). With one controller, once that was fixed: the 2P character select ignores input while the log shows the controller applet opened again every few frames.
- **Cause:** on Horizon a library applet takes the application's focus. am sends message 15 with OutOfFocus when it opens and 15 with InFocus when it closes, and the `Show…` call returns once it has closed. The host's stand-ins answered at once with no focus change. Mario Kart applies the controller applet's answer only after that InFocus notification: its notification thread (`main+0x8ea560`, blocking `PopNotificationMessage`) sets a flag on 15 with state 1, and the per-frame `main+0x87b5d0` takes the flag before it applies the answer (`main+0x87b300`). Second: with fewer controllers than the game's minimum, the host answered success with the connected count. A Switch never gives that answer (its applet waits for controllers until the player closes it), and the game, which asks for two in 2P, opened the applet again.
- **Fix:** `hle_oe.c` counts open applets apart from the front end's focus. The game sees the front end's state, or 2 while an applet is open over a game in focus; each change of what it sees is one 15 (under focus modes 1 and 2, [Focus handling mode decides whether focus changes are notified](#focus-handling-mode-decides-whether-focus-changes-are-notified)). `DM_APPLET("name");` (`hle.h`) at the top of a stand-in holds the game out of focus until the stand-in returns: the controller applet, the controller firmware update and the error applet (`err::ShowError`, both overloads). A stand-in that reports the applet could not start (`web::ShowWebPage`) opens none. An instant open and close merges into one pending 15 that reads 1, which is all Mario Kart needs; a game that must see the 2 would need more. `ShowControllerSupport` with fewer players than the minimum (`ControllerSupportArg` +0) returns `ResultControllerSupportCanceled` (2202-3101), what the SDK's `ShowControllerSupportCore` (SDK 4.4.0 `sdk+0x24eeb0`) returns when the player closes the applet; Mario Kart goes back to its engine class menu, as on a Switch. `DM_OE_SCRIPT` now also starts for a game that only uses the blocking `PopNotificationMessage`.
- **Found on:** Mario Kart 8 Deluxe (4.0.0 and 4.0.1; GitHub issue #550).
- **Check:** `t_oe` and `t_hid` (`dm/host/tests`). On the Mac, from a save past the Mii pick: L+R at the title, Down, A (2P), A (Grand Prix), A (50cc). The log shows `oe library applet: controller support`, then `oe focus state → 2 (library applet open)` and `→ 1 (library applet closed)`, and the character select takes input. With one controller and no window (or under `DM_CTL`) the applet logs `too few, closed as the player would (canceled)` once and the engine class menu comes back; with a window its prompt waits for a second player ([The controller applet waits for players](#the-controller-applet-waits-for-players)).

### The controller applet waits for players

- **Symptom:** with [Press a button to join](../settings.md#press-a-button-to-join) on, a game's player screen closes when the game asks for more players than have pressed a button. The log shows `hid controller applet: 2 to 2 players wanted, 1 connected: too few, closed as the player would (canceled)` (Mario Kart World 1.8.0, pull request #1596).
- **Cause:** the controller applet's stand-in (`ctrl_support`, `hle_hid.c`) answered at once, and below the game's minimum (`ControllerSupportArg` +0) it answered as the player closing the applet. A Switch's applet stays open until enough controllers are there or the player closes it. Before Press a button to join the host had nothing to wait for; with it, connected controllers that are no player yet are what the applet waits for.
- **Fix:** with a window and no scripted input, `ctrl_support` asks the front end (`front_ctrl_support`, `front.h`). Its prompt is up over the game, holding the game's thread, while controllers join: a first button press with Press a button to join, a connection without it. The rules are in `ctrl_prompt.h`: B or Escape closes it (canceled); with at least the minimum in, it is done when a player presses A or Return, when the game's maximum has joined, or when no connected controller is left to join; the press that makes a controller join counts for neither; no time limit and no close on a focus loss, as on a Switch. The game gets no controller or keyboard input while it is up, nor until the A or B that closed it is let go. The host counts the players again once it closes (`dm_players_reported`) and answers canceled below the minimum. The Mac draws it on the Home prompt's card (`front_mac.m`, `home_quit_mac.h` `hq_card_view`). A front end passes the texts in the player's language as `DM_CTRL_PROMPT_TEXT` ([Starting a game](../frontends.md#starting-a-game)). Without a window, or with `DM_KEYS` or `DM_CTL` (nobody at the controllers), the host answers at once as before.
- **Found on:** Mario Kart World (1.8.0, pull request #1596; GitHub issue #1640).
- **Check:** `t_ctrl_prompt` and `t_hid` (`dm/host/tests`). On the Mac with a window, two controllers and Press a button to join on, Mario Kart 8 Deluxe from a save past the Mii pick: press a button on one controller, then L+R at the title, Down, A (2P), A (Grand Prix), A (50cc). The log shows `front end: controller prompt open: 2 to 2 players wanted, 1 in, 1 controllers waiting to join`; a press on the second controller closes it (`controller prompt closed: 2 players (done)`, then `the prompt waited, 2 now (OK)`) and the character select has two players. B instead closes it as canceled and the engine class menu comes back.

### The controller applet leaves out the players past the maximum

- **Symptom:** with more controllers than a game takes, the game gets no input and the log repeats `oe library applet: controller support`, `hid controller applet: 1 to 1 players wanted, 2 connected` and `focus state → 1 (library applet closed)` every few frames (1,671 times in one run). A game that suspends its music while an applet has focus plays none.
- **Cause:** above the game's maximum (`ControllerSupportArg` +1) the stand-in (`ctrl_support`, `hle_hid.c`) answered with the count capped and left every npad connected. On a Switch the applet leaves no more controllers connected than the game takes, so the game saw the second npad again on its next frame and opened the applet again. Any second player caused it: a second controller, a receiver read as a pad ([A keyboard receiver that declares a gamepad takes player 1](#a-keyboard-receiver-that-declares-a-gamepad-takes-player-1)), or one controller listed twice ([One Pro Controller read as two players](#one-pro-controller-read-as-two-players)).
- **Fix:** the players past the maximum, the highest first, are left out (`g_benched`): their npads read as not connected and their style events are signalled, as for a player on an npad the game does not support. With a maximum of one their controllers feed player 1 (`merged_players`), so whichever controller the player holds plays, and a device that never sends input does no harm. With a higher maximum they are not used. They count again when the applet opens for more players (the lowest first), when the game sets its supported npads again (`SetSupportedNpadIdType`), or when their controller goes away; a controller that connects later is a player until the applet opens again. The log names each one: `hid: player 2's controller feeds player 1: the controller applet left it out`. No prompt asks which controllers stay, as a Switch's applet does: with a maximum above one the lowest players stay.
- **Open:** not run on a game (no second controller here): the tests cover the host's side, and that Ocarina of Time stops asking once No2 reads as not connected follows from its request for one player, not from a run. A game that opens the applet for one player and later expects a second controller without opening it again would not see that controller until it reconnects; none is known. The second HID entry behind the report no longer counts as a pad: [A HID entry that sends nothing counted as a second pad](#a-hid-entry-that-sends-nothing-counted-as-a-second-pad).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (v131072, one Pro Controller over Bluetooth on the Mac, read as players 1 and 2 after it reconnected; GitHub issue #2237).
- **Check:** `t_hid` (`dm/host/tests`): one wanted with two and three players, the lowest players kept with a maximum of two, the applet opened for more, a controller that goes and comes back, the supported npads set again.

### `nn::ngc::ProfanityFilter` overloads taken over by name

- **Symptom:** crash in `lmem::AllocateFromExpHeap` under `ngc::ProfanityFilter::MaskProfanityWordsInText` right after the character name is entered (DARK SOULS: REMASTERED); filter methods among the undefined imports with no hook, found from the import list before they were met (The Great Ace Attorney Chronicles).
- **Cause:** the SDK's filter reads its word list from system data, which the host never mounts, and allocates from a heap the host never set up. Games call the methods by name, each in the overloads of its SDK: DARK SOULS: REMASTERED calls the UTF-16 mask (`EPiPtj`) and The Great Ace Attorney Chronicles `MaskProfanityWordsInText(int *, char *, uint32_t)`; an overload the host has not taken over runs the SDK's version.
- **Fix:** the methods are taken over by name: the destructor, `GetContentVersion` (0), `CheckProfanityWords` with `char` words and the `char`, `unsigned short` and `char16_t` overloads of `MaskProfanityWordsInText` (`hle_misc.c`); `Initialize(void *, size_t, bool)` and `CheckProfanityWords` with `char16_t` words (`hle_offline.c`). Nothing is masked or reported.
- **Found on:** DARK SOULS: REMASTERED (SDK 4.5.0; one boot: the UTF-16 overload by name); The Great Ace Attorney Chronicles (SDK 10.4.1: the `char` overload).

### The graphics scale does not follow the operation mode

- **Symptom:** a Switch 2 game renders smaller docked than handheld, or smaller than console footage: Star Fox's scene was 768x432 docked (DLSS network resized to it at boot, its window 1920x1080) and 960x540 handheld; Ocarina of Time drew 2048x1152 docked, its 3D at no more than 1536x864; Donkey Kong Bananza's docked frame buffer was 2304x1296 on a 2880x1620 swap chain.
- **Cause:** the host answered `oe::GetCurrentGraphicsScale` (am's graphics scaling parameters: 10 / 20 / 30 → tier 0 / 1 / 2) by the operation mode: 0 handheld, 1 docked. Games size their picture and their GPU budget by the tier, full at 0: Star Fox keeps only "tier 0" (byte +0xa of its mode event, `main+0xba69970`) and renders 0.8 times smaller below it; Bananza scales its frame buffer by {1.0, 0.8, 2/3}[tier] (`main+0x30f840`) and adds 0, 9 or 13 to the GPU time its dynamic resolution counts; Ocarina of Time's output is 0.8 times smaller at tier 1. So the tier reads as how much of the GPU the game may use, which a system would lower while it needs the GPU itself (GameChat's video): an inference from the games' code, not a measurement. A docked picture smaller than the handheld one, on a GPU about twice as fast, is not what the console does, and Star Fox's console footage is nearer tier 0: Peppy's close-up 65 s into it has a mean gradient of 5.8 (x1000, luminance at 1080p), tier 0 here 5.3, tier 1 4.6.
- **Fix:** tier 0 in both modes (`hle_oe.c`; check: `t_oe`). `DM_GFX_SCALE=1` or `2` answers a reduced tier, to see what a game does with it. Open: which tier a console reports in which mode is not measured.
- **Found on:** Star Fox (docked: scene 960x540 to its 1920x1080 window, as handheld; measured on a build of the PR author's fork, MetalFX temporal, `HOST_OPT -O3`, not on `main`). Donkey Kong Bananza: docked in the mining tunnel, frame buffer 2304x1296 → 2880x1620 and main passes 1676x943 → 2095x1179, GPU p50 about 7.0 → 8.6 ms, 60 fps held with both (M6, 16 GB, a host of chain `cfcc3a82c78b` with only this answer changed). [Ocarina of Time](../../dm/games/0400486024DEC000/README.md): output 2048x1152 → 2560x1440, 3D 1536x864 → 1920x1080, GPU p50 12.9-14.0 → 15.0 ms at about 59 fps (M4 Pro, two contributors' runs on `main` with only this answer changed).

### Focus handling mode decides whether focus changes are notified

## Accounts, network, shop and parental controls

### Account and friends calls found in the imports

- **Symptom:** undefined `nn::account::` / `nn::friends::` imports with no hook, found from the import list ([Listing a game's unhooked imports before they are met](#listing-a-games-unhooked-imports-before-they-are-met)) before they were met.
- **Fix:** hooked: `account::ListAllUsers` (`hle_account.c`: the registered local users, [Local users, sessions and separate saves](#local-users-sessions-and-separate-saves)); `friends::GetBlockedUserList` (`hle_friends.c`: none, and the call fails as the other calls that need the friends service do).
- **Found on:** Super Mario 3D World + Bowser's Fury (SDK 10, `ListAllUsers`); DRAGON QUEST XI S (the friends calls).

### `account::GetUserId` copies the Uid of any handle

- **Symptom:** a second controller ends the game with `FATAL account::GetUserId: the handle was not issued by the host (0x2)`, at boot with both connected or when the second joins during play (EA SPORTS FC 27 1.8d.6523; the FC 26 patch reports `(0x8)`).
- **Cause:** the host checked the handle's third word against the marker its own open calls write. The SDK's accessor never reads that word: FC 27's `nn::account::GetUserId` (`sdk+0x1c0040`) calls `detail::GetUserId` (`sdk+0x1bede0`, `ldp x8, x1, [x0]; mov x0, x8; ret`), stores the 16 bytes and returns 0. For a second controller's player FC 27 passes a handle it built and never filled (`main+0x1f638b0`; words `0x7012222b20 0x400000001 0x2`), so on a console the call succeeds and returns those bytes.
- **Fix:** `GetUserId` copies the Uid and returns 0 for any handle, as the SDK does (`hle_account.c`); the open calls issue session tokens for closing their own sessions, but the accessor still does not inspect that word. `t_account` covers the host's handle and built handles with third words 2, 8, 0 and all ones.
- **Found on:** EA SPORTS FC 27 (PR #1129; two DualSense controllers on a Mac and an iPad Air M4, reported in its review thread); first found on EA SPORTS FC 26 by the [FC 26 120 fps patch](https://github.com/imnotsharingmyname/nxnative-fc26-120fps) (MIT).

### Local users, sessions and separate saves

- **Symptom:** Minecraft Dungeons II's second local player repeatedly receives player 1's user and cannot join (PR #2846).
- **Cause:** the host always returned its one fixed UID. The PR's carried implementation demonstrated about 40 seconds of two-player play, but listed closed users as open and forgot registered users at the next boot.
- **Fix:** `hle_account.c` keeps up to eight local users, each with an identity of its own, and keeps registration apart from open sessions. This fork has no user selector and creates no users: `TryOpenPreselectedUser` opens user 1, and other users exist only in a save store that carries a registry of them.
- **Identity and sessions:** user 1 retains its original UID and `DM_NICK`; users 2–8 use PR #2846's deterministic slots and `Player N` nicknames. `hle_account_users.c` reads the registry `<DM_SAVE>.users` (`nxnative-users-1` and a hexadecimal slot mask) and never writes it; a store without one has user 1. An unreadable or corrupt registry registers nobody, is logged in red and is left intact. `ListAllUsers`, `ListQualifiedUsers`, `GetUserCount`, `GetUserExistence` and `GetNickname` answer from the registry, closed profiles included. Each open (`OpenUser`, `TryOpenPreselectedUser`) owns a unique session token and `ListOpenUsers` lists only users with live sessions. Closing a copied/stale token cannot close another session. A fresh process has registered profiles but no live sessions; the launch user remains user 1.
- **Saves:** `hle_fs.c` retains `<DM_SAVE>` for user 1 and uses `<DM_SAVE>_userN` for each additional user. Unknown UIDs fail instead of falling back to user 1. Reusing an occupied mount name for a different backing directory fails. The existing transaction engine handles each directory independently; no transaction rewrite. See the [front-end contract](../frontends.md#local-users) for backup/move requirements.
- **Checked:** `t_account` covers a store without a registry, a registry read by a fresh process, a corrupt registry, two sessions for one UID, stale closes and concurrent opens/closes. `t_account_save` opens two registered users, mounts distinct saves with identical filenames, commits independently (including an alias), injects a failure in each direction, and starts two fresh processes to verify registered identities and committed bytes survive while pending writes do not.
- **Found on:** Minecraft Dungeons II, reported by papertradooor in PR #2846; save/session contracts reproduced with synthetic inputs. Borderlands: Game of the Year Edition also needs an empty open-user list at first gamepad mapping to take its synchronous preselected-user fallback.

### An account AsyncContext needs its SDK constructor

- **Symptom:** `CRASH sig=11` at `main+0x5b64f8`, `lr=main+0x3f1b8cc` (`nn.account.AsyncContext$$Finalize`), on an IL2CPP thread-pool worker a few seconds after the player confirms a name and birthday (Pokémon Friends 1.1.5). The object's first word, its vtable, holds stray bytes (`0xffffd256` in one run, `0x15600000128` in another). The game had started `account::EnsureNetworkServiceAccountIdTokenCacheAsync`.
- **Cause:** `nn::account::AsyncContext` is polymorphic. The SDK's constructor (SDK 19.3.11: `sdk+0x1ad6c8`) writes the class's vtable and nulls the three words after it, the IPC object pointer at +0x18 among them, and sends nothing. The host took the constructor over with one that wrote no memory, so the vtable word kept what the allocator left there. The game's C# binding deletes the native context from the managed finalizer through the virtual deleting destructor, inlined in main (`main+0x5b64f0`: `if (p) p->vtable[1](p)`), which the host's `AsyncContextD1Ev` takeover never sees, and jumped through those bytes.
- **Fix:** the constructor is no longer taken over (`hle_account.c`): the SDK's own runs. No host interface sets the IPC pointer, so the SDK's destructor, reached through the vtable, finds no session to close and frees the object. `account::NintendoAccountAuthorizationRequestContext` has no vtable (its SDK constructor writes none) and holds no host state, so its destructor's takeover stays.
- **Found on:** Pokémon Friends (`010008C01E742000`, update 1.1.5, SDK 19.3.11; no profile in the repository yet). The managed names come from Il2CppDumper's table.

### The network account check is cancelled offline

- **Symptom:** a "Transmitting" loading screen with a hint stays for ever before the main menu while the game keeps drawing at 60 fps and its music plays (Taiko no Tatsujin: Rhythm Festival). No red line, no crash; `DM_SF_TRACE=1` shows nothing after `nsd:u`. `DM_HLECOUNT` shows `account::EnsureNetworkServiceAccountAvailable` called thousands of times (4,647 in under three minutes, about once per frame).
- **Cause:** the host's `EnsureNetworkServiceAccountAvailable` returned `RES_FAIL`. The SDK opens the account applet for account errors that require user interaction. Cancelling it returns `ResultCancelledByUser` (2124-0001, `0x27c`), as confirmed by replaying the SDK 13.3.0 path with a cancelled applet exit. Taiko takes that result as "continue offline" (`main+0x16ee0f4`: `and x8, x0, #0x3fffff; cmp x8, #0x27c`) and retries on anything else.
- **Fix:** the call returns that result, `RES_ACC_CANCELED` (`hle_account.c`). The other network-account calls (`GetNetworkServiceAccountId`, `LoadNetworkServiceAccountIdTokenCache`) still fail.
- **Check:** `make -C dm/host/tests run` runs `t_account`.
- **Found on:** Taiko no Tatsujin: Rhythm Festival (`01006B0016AD6000`, update 6.2.0, Unity 2020.3.26f1 IL2CPP, SDK 13.3.2; no profile in the repository yet). Before the fix, a cheat that rewrote main's import stub for the call (`main+0x1845440`, build `7150D78C454E7C55`) to return `0x27c` got it to the main hub.

### Creating an ssl context needs no network

- **Symptom:** the game ends right after `nnMain`, with a crash in its own cleanup on an object it had not created yet (DRAGON QUEST BUILDERS 2: `CRASH sig=11 addr=0x60db0` at `main+0x2676c8`, x0 = 0, the callers `main+0x85210` and `main+0x7fabf8`). No red line.
- **Cause:** `ssl::Context::Create` failed in the host's offline stubs. A context is a session of the console's own ssl service, so it succeeds on Horizon with no network; only a connection needs one. The game's online library treats the failure as fatal, and its startup (`main+0x84a60`) returns false.
- **Fix:** `Context::Create` and `Context::Destroy` succeed and connect to nothing (`hle_net.c`). `Connection::Create` and the rest still fail, as they do with no network.
- **Found on:** DRAGON QUEST BUILDERS 2 (SDK 5.4.0). 53 of 82 games surveyed import the call.

### `EventFd` needs no network

- **Symptom:** `abort` under `grpc_init` at startup, with no red line: `game called nn::diag abort: Result 0, call site sdk+0xb8fe8`, backtrace `sdk+0xba138 sdk+0x7bd670 sdk+0x777f30 main+0x21f0c80`, just after `fs mount _npln:` (Ocarina of Time).
- **Cause:** gRPC, which `nn::npln` links, wakes its pollers with `nn::socket::EventFd`. The host failed that with ENETDOWN, so gRPC found no wakeup descriptor, its poll engine's factory (`main+0x21f1280`) returned null and the engine selection called `abort` (`main+0x21f0c7c`). An event descriptor is local to the bsd service, so on Horizon it works with no network; only a connection needs one.
- **Fix:** `EventFd`, `EventFdRead` and `EventFdWrite` are host counters, `Poll` waits on them with a condition variable and `Close` frees them (`hle_net.c`). They share the BSD descriptor table with [local UDP sockets](#udp-loopback-works-offline). An endless wait comes back with 0 after 100 ms, as it does with nothing to wait on.
- **Check:** `make -C dm/host/tests run` runs `t_net_eventfd`.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (SDK 22.2.8).

### Event descriptors in an `fd_set`

- **Symptom:** `CRASH sig=10` (SIGBUS) in a network thread right after start (Minecraft's `NetherNet Network`, `main+0x18b2ae8`, `x0=0x4000`), at a load from its own stack.
- **Cause:** the host numbered its event descriptors from `0x4000`. The bsd service gives out the lowest free number from 0, and games size their tables for such small numbers: NetherNet puts its event descriptor in a 1024-bit `fd_set` on the stack for `Select`, and `FD_SET(0x4000)` reads and writes 2 KB past the set. `Select` also failed whenever a descriptor was set, so it could never wait on one.
- **Fix:** the event descriptors are numbered as the service numbers them, the lowest free one from 0 (`hle_net.c`). `Select` (`dm_sk_select`, both overloads) is `Poll` over the descriptors in its sets: it waits on the host's event descriptors, a descriptor the host never made has nothing to say, the sets come back with the ready ones, and a descriptor closed during the wait fails with EBADF. As a game's own stale or never-valid descriptors now fall in the same range, `Poll` reports a closed descriptor (`POLLNVAL`) only for one that was open when the wait began.
- **Check:** `t_net_eventfd` (`make -C dm/host/tests run`).
- **Found on:** Minecraft (Bedrock Edition, 1.21.120).

### UDP loopback works offline

- **Symptom:** New Game stays on the loading artwork with an empty progress bar while rendering and loading tips continue (Divinity: Original Sin 2). Both `nn::socket::Socket(AF_INET, SOCK_DGRAM, 0)` calls fail, so RakNet never completes initialization.
- **Cause:** the host treated every socket as remote networking and returned ENETDOWN. RakNet's startup tests a local UDP endpoint by sending a four-byte datagram to itself at `127.0.0.1`; this works on an offline console. The missing test leaves the game's single-player client and server waiting. The same cause was independently documented in [DroidPlay Core's Divinity note](https://github.com/enjoyerofslop/droidplay-core/blob/main/dm/games/010027400CDC6000/README.md).
- **Fix:** `hle_net.c` serves IPv4 UDP endpoints inside the process, with BSD sockaddr/flags/errors, local binding and ephemeral ports, datagram queues, connected send/receive, nonblocking calls and `Poll` / `Select`. The enum, plain-argument and C entry points share this service with EventFd. Queues are bounded; close wakes blocked readers and pollers, and descriptor generations prevent waits from attaching to a reused slot. Remote traffic and name resolution remain unavailable. No game key or fixed address is involved: this is host binding, its loosest correct binding.
- **Check:** `t_net_loopback` exercises the four-byte startup test, two-endpoint exchange, connected filtering, peek/truncation, nonblocking and timed receive, remote rejection, mixed EventFd readiness, and close/reuse during waits; `t_net_eventfd` retains the existing event-descriptor checks.
- **Found on:** Divinity: Original Sin 2 - Definitive Edition (update 1.0.12, SDK 9.3.0).

### A console's own Mii database

- **Symptom:** `[RED] sf: the game connects to service mii:e … mii:u itself`, then an abort, from `nn::mii::Database`; once the host answers it, a game finds none of the console's Miis.
- **Cause:** `nn::mii::Database` keeps an `IDatabaseService` of the mii service at +0 (`Database::Initialize`, `sdk+0x1c5664`), and the host has no mii service. The Miis live on the console, in the mii service's system save, which the host does not ship.
- **Fix:** `hle_mii.c` takes over `Database::Initialize`, `Finalize` and `GetIndex` and answers from a database of its own: empty, or the console's when the player supplies it under `DM_SYSTEM_DIR` (the Mac launcher sets `~/Library/Application Support/NativeNavi/system`; elsewhere `$DM_ROOT/run/platform/system`) as `save/8000000000000030/MiiDatabase.dat`. The Switch 2's service (program `0400000000000039`) mounts system save `8000000000000030` as `mii` and reads `mii:/MiiDatabase.dat`, as the Switch does. The file is 0x1a98 bytes: `NFDB`, 100 StoreData of 0x44 bytes, the version (1) at +0x1a94, the count at +0x1a95, and a CRC-16/CCITT (polynomial 0x1021, initial 0) of the bytes before it at +0x1a96, big-endian. `hle_mii.c` reads it once at `Database::Initialize`. Each StoreData's seven words of bit fields, nickname and create ID become a CharInfo (`mii_from_store`; the stored eyebrow y is 3 below the CharInfo's). `GetIndex` finds a Mii by its create ID and fails for one that is not there. A file of another size, magic, version or CRC is logged in red and leaves the database empty. The file is never written. The default Mii the host builds for an amiibo's owner (`dm_mii_default_charinfo`) is in no database.
- **Found on:** Mario Kart 8 Deluxe (4.0.0, SDK 4.4.0: the service connection); Nintendo Switch Sports Resort (v65536: the console's database). The save's ID, mount name and file checks were read from the Switch 2's system program `0400000000000039`.
- **Check:** `make -C dm/host/tests run` runs `t_mii`: a database with known fields unpacks into them; a wrong CRC, size or version is refused; `GetIndex` answers from it; the default Mii is not in it.

### Shop service accessors

- **Symptom:** shop service accessor calls among a game's imports; the first one met was an abort with no message (`SVC 0x15` / `0x1f` / `0x21` placeholders, then `Break` with `sm::Finalize` under `ShopServiceAccessServer::Proxy::Initialize`) at the start of `nnMain`.

### Socket and play report calls found in the imports

### SDK 21 socket overloads

- **Symptom:** `nn::socket` imports in forms the host had not taken over, at a game's first socket calls (Star Fox).
- **Cause:** SDK 21's socket functions also come in overloads with plain `sockaddr` (`GetPeerName`), a `ShutdownMethod`, `Read` / `Write` and a `GetHostEntByName(const char *)` without options.
- **Fix:** the overloads use the shared offline BSD service (`hle_net.c`); `GetHostEntByName` resolves nothing. `Poll` does not fail on a descriptor the host never made, which only a garbage value can be: it reports nothing ready at the timeout, as a console's does for a socket with nothing to say. Local descriptors work through [EventFd](#eventfd-needs-no-network) and [UDP loopback](#udp-loopback-works-offline).
- **Found on:** Star Fox.

### Server environment queries without nsd

- **Symptom:** `[RED] sf: the game connects to service nsd:a itself, which the host does not serve` (also `nsd:u`), then `game called nn::diag abort: Result 0xe8d` and exit 134 during startup.
- **Cause:** `nn::nsd::GetApplicationServerEnvironmentType` asks the nsd services for the console's server environment (`nsd::detail::ipc::GetApplicationServerEnvironmentType`) and aborts when the request fails; the host serves no nsd service. `nn::oe::GetServerEnvironmentType` is a single branch through the `sdk` module's PLT to it, in all 18 `sdk` modules on hand (Switch 1 and Switch 2 titles, Mario Golf: Super Rush and EA SPORTS FC 27 among them), so a game reaches it either way. The query asks for a fixed property of the console, not for a network connection.
- **Fix:** `hle_offline.c` takes over `nsd::GetApplicationServerEnvironmentType` and returns `oe::ServerEnvironmentType` 1, retail `lp1`, as the existing `nsd::GetEnvironmentIdentifier` answer does (the game's table maps `0 dd1`, `1 lp1`, `2 sd1`, `3 sp1`, `4 dp1`). The forced takeover binds the `sdk` module's own PLT entry too, so `oe::GetServerEnvironmentType` needs no takeover of its own. Other nsd operations are not implemented. `t_server_environment` looks up the real registrations by name and checks the answer against the identifier.
- **Found on:** Hogwarts Legacy (`0100F7E00C70E000`, SDK 17, no profile), in a contributor's bring-up ([PR #1199](https://github.com/seedds/nxnative/pull/1199); also [NX2Apple issue #475](https://github.com/LNPANDY/NX2Apple/issues/475)): with the takeover the game passed the call and went on rendering. No local game references either function. Hogwarts on the current host and PATAPON 1+2 REPLAY ([NX2Apple issue #426](https://github.com/LNPANDY/NX2Apple/issues/426)) are not checked (open).

### Socket `Poll` and `Select` with nothing to wait on

- **Symptom:** one thread at 100% CPU from boot, with one SVC in 99 s (`NexusRevolution Socket`, `main+0x92c7c4`, the game's network thread).
- **Cause:** it calls `nn::socket::Poll(fds, 0, 33)`: no descriptors and a 33 ms timeout, which on hardware is a 33 ms sleep. The host failed every socket call at once, so the thread spun 11,000 times a second (88,000 hits of a probe in 8 s).
- **Fix:** `Poll` and `Select` with nothing to wait on (no descriptors, or only negative ones, which POSIX ignores) now wait out their timeout and return 0, in every mangling the host takes over, including SDK 4's `Select(int, fd_set*, …, timeval*)`; an endless timeout returns 0 after 100 ms, since a thread inside a host hook pauses for IL2CPP's collector only once the hook returns (`hle_net.c`, `dm_guest_sleep_ns` in `hle_thread.c`).
- **Found on:** DARK SOULS: REMASTERED (SDK 4.5.0; one boot). Guest CPU fell from 1,030 to 60 ms per second.

## Settings, languages and fonts

### Polish and Thai, and a Switch 2 SDK's own language list

- **Symptom:** a game that ships Polish or Thai text could not be given either language: the packing script stopped at `unknown game language 'pl'`, and the Game language row did not offer them.
- **Cause:** `nacp.LANGUAGES` covered only the first 16 bits of `SupportedLanguageFlag`. The controls for Wonder Switch 2 Edition 1.2.1 use bits 16 and 17 for Polish and Thai. Breath of the Wild 1.9.0 sets bit 17 in its Switch control data. In `nn::settings::Language` order the two codes are `pl` at 18 and `th` at 19. A Switch 2 SDK can provide a separate list with no settings service call. Its list omits `zh-CN` and `zh-TW`, so Simplified Chinese is at index 13 instead of 15. Where the SDK lists Polish and Thai they are at indices 16 and 17.
- **Fix:** the tools read the two control bits and offer the codes in the packer and launcher (`dm/tools/nacp.py`). The game's `sdk` (22.2.8) answers `GetAvailableLanguageCodes` and `GetAvailableLanguageCodeCount` from its own table of 18 codes, so the host takes over neither: the forced take-over for SDKs without a list of their own, and the loader's choice between the two, were removed with the fork, as were the `LanguageCode` hooks. `oe::GetDesiredLanguage` passes through the `DM_LANG` code.
- **Found on:** Super Mario Bros. Wonder (1.2.1, SDK 16.2.12, Polish and Thai title-screen boots on the Mac with `DM_LANG`). The list and count exports read a local table of 16 codes in Donkey Kong Bananza (20.5.19) and Pokémon Pokopia (20.5.25), and 18 in Mario Kart World (21.4.0), Wonder Switch 2 Edition (21.4.1), [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (22.2.8), and Nintendo Switch Sports Resort (22.2.10).

### Shared font address: BFTTF header or bare TTF

- **Symptom:** the font engine runs on garbage; crash after the shared fonts load, looking up the "?" glyph (`main+0x6c73c0`, a font cache lookup returning null), with SDK 10's `ScalableFontEngine::LoadFont` failing with error 403 and `SetFont` with 301 on both stand-in fonts; or Japanese, Korean or Chinese text draws nothing in a Unity game while Latin text is fine (Patrick's Parabox's language menu showed three blank lines).
- **Cause:** consumers read the shared font differently.
  - The SDK's font engine calls `ScalableFontEngineHelper::Decode(ptr, size)`, which XOR-decodes in place unless the first word is the "already decoded" marker (LE `0x18029a7f`). So for a game that decodes it the system shared font must look like BFTTF: serve `marker + bswap(size ^ 0x49621806) + TTF` (`hle_sdk16.c`). Mario decodes the pointer and needs the 8-byte BFTTF header in front.
  - 3D World records shared fonts as type 0 (`main+0x975658`), calls no `ScalableFontEngineHelper::Decode` and hands the `GetSharedFontAddress` pointer straight to `LoadFont`, so the pointer must be the plain TTF. SDK 10 and older games all take the plain TTF.
  - Unity's Switch player hands the shared fonts straight to FreeType. In Patrick's Parabox (SDK 13) the game's one font (Jost, a Unity dynamic font) falls back to the OS fonts for those glyphs, and the player loads them from the shared fonts: `main+0x2390b0` maps the names `Switch_Font_STD`, `Switch_Font_CN_Simplified`, `Switch_Font_CN_Extended`, `Switch_Font_CN_Traditional`, `Switch_Font_KR` and `Switch_Font_NIN_Extended` to types 0–5 and hands `GetSharedFontAddress` / `GetSharedFontSize` straight to FreeType's `FT_New_Memory_Face` (`main+0x23b2e0`), as libnx homebrew does with the same pl offsets. The host gave every SDK 11+ game the 8-byte BFTTF header in front, so every face failed to open.
  - The SDK's `GetSharedFontAddress` is the shared memory base plus the pl service's offset, with no adjustment, and that offset points past the header (yuzu's pl service: "font offset and size do not account for the header"); Captain Toad (SDK 8) records its shared fonts as plain TTFs and calls `Decode` only for its BFTTF formats.
  - A game on a newer SDK can import `Decode` (and so get the header) yet hand the address straight to `LoadFont` the same way (The Legend of Zelda: Echoes of Wisdom 1.1.0, SDK 20.5.1: `main+0x8b37c` crashed at address 0x38).
- **Fix:** the host first decided by the SDK version alone (SDK 10 and older the TTF, SDK 11+ the header). Now the address is the header (marker form above) only for a game whose `main` imports `nn::fontll::ScalableFontEngineHelper::Decode` (Wonder, Breath of the Wild, Tears of the Kingdom, Pokémon Legends: Z-A); every other game gets the TTF itself (`font_skip` in `hle_sdk16.c`, `dm_game_imports` in `loader.c`). `GetSharedFontSize` and the built-in font calls give the same form. The profile key `shared_font`, which overrode the choice, and the host's `LoadFont` take-over were removed with the fork.
- **Check:** 3D World's case was found by probing the engine's error code after each call (`DM_PROBE` on the instruction after `GetError`).
- **Note:** of the games on hand, the ones that call `GetSharedFontAddress` without importing `Decode` are all Unity players (Engage, Ace Attorney Investigations Collection, Brain Memory Training Academy, Patrick's Parabox). To see which fonts a Unity game asks for, probe its name mapper's entry (`DM_PROBE=main:2390b0` on Patrick's Parabox 1.0.1; the function is the one `main` caller of `GetSharedFontLoadState`).
- **Found on:** Super Mario 3D World + Bowser's Fury (SDK 10, the plain TTF); Super Mario Bros. Wonder, The Legend of Zelda: Breath of the Wild, The Legend of Zelda: Tears of the Kingdom, Pokémon Legends: Z-A (the `Decode` importers); Patrick's Parabox (the blank CJK text, 1.0.1); Captain Toad: Treasure Tracker (SDK 8, plain TTFs); Fire Emblem Engage, Ace Attorney Investigations Collection, Brain Memory Training Academy (the other Unity players); The Legend of Zelda: Echoes of Wisdom 1.1.0 (no profile).

### Every undrawn extension code point is a ring

- **Symptom:** a crash in the font engine at boot with the null glyph, from a code point no message uses (`main+0x62d20` on 1.0.0, `main+0x63780` on 1.1.4); `?` in text for an icon the stand-in does not draw.
- **Cause:** the stand-in extension font drew only the icons games were seen to use, so a lookup of any other code point found no glyph.
- **Fix:** every code point of U+E000–E1FF the stand-in does not draw maps to a plain ring (`make_ext_font.py`), so a lookup always finds a glyph.
- **Found on:** Super Mario 3D All-Stars (the launcher looks up U+E06B at boot).

### Nintendo-extension glyphs for button icons

- **Symptom:** controller-button icons in text show as `?`.
- **Cause:** those glyphs come from the system shared font's Nintendo-extension set (private-use code points; Mario's `GameMsg/Key.msbt` uses U+E0E0–E0F0 for A/B/X/Y/L/R/ZL/ZR/SL/SR/D-pad/+/−, U+E0AB–E0AE for D-pad directions, U+E090–E097 for stick arrows, U+E100/E101 for sticks).
- **Fix:** `dm/tools/make_ext_font.py` generates a stand-in `nintendo_ext.ttf` with those icons (`make_shared_fonts.py` makes it with the other stand-ins); the host serves it for shared-font type 5 (`DM_FONT_DIR` or `DM_SHARED_FONT_EXT`).
- **Note:** to find which code points a title uses, scan the `TXT2` sections of its MSBT files for U+E000–F8FF.
- **Found on:** Super Mario Bros. Wonder.

### Shared font stand-ins sized for the game's font engines

- **Symptom:** a crash after the shared fonts load, looking up the "?" glyph (`nro0+0xaef8a8`, a null pointer from nn::font's texture cache), with `ScalableFontEngine::LoadFont` returning 201 on one engine and 0 on another, and `SetFont` 301.
- **Cause:** a game sizes each `nn::fontll` engine's work memory for Nintendo's font of the type it loads there, and the host served macOS's Arial Unicode as it is for types 0-4. Mario Tennis Fever gives its first engine 512 KB and its second, the one its glyph thread uses, 50 KB (`0xc800`), and `FSS_load_font` needs 56-60 KB for Arial Unicode there: 201, ignored by the game, so the name stays unknown to that engine, `SetFont` fails and every lookup misses. What it needs grows with the font's hinting program (Arial Unicode: a 4,139-element interpreter stack, a 9 KB `prep`) and its outlines and layout tables, hardly with its glyph count. Measured on that engine (its buffer shrunk by a test take-over, a boot each): Arial Unicode as it is 56-60 KB, unhinted 44-48 KB, a hinted 7,430-glyph Japanese cut 44-48 KB, the same cut unhinted at most 32 KB.
- **Fix:** `dm/tools/make_shared_fonts.py` makes one stand-in per type, unhinted, with the layout tables but kerning dropped, holding its type's characters (standard: Latin, Greek, Cyrillic and cp932's Japanese; GB 2312; the other GBK hanzi; Big5; every modern Hangul syllable with KS X 1001) and a name of its own, as a game can load several types into one engine; the host serves each type its own file from `DM_FONT_DIR` (`hle_sdk16.c`, `font_file`), a type without one the standard font. `build_app.py` makes them into `<id>_build/font`, and the Mac app holds them in `Resources/dm/font`. On that 50 KB engine standard, both Simplified Chinese fonts and Traditional Chinese need 24-32 KB, Korean 32-40 KB; every engine runs on the game's own buffer, as on the console. Before this the host gave every engine under 512 KB that much host memory in a take-over of `ScalableFontEngine::Initialize`, `Finalize` and `GetPointerToWorkBuffer` (PR #2707's registry of them), removed with the cause.
- **Checked:** Super Mario Party (`010036B0034E4000`, SDK 5) loads all six types into each of its four shared-font engines (512 KB and 768 KB): every load returns 0, each under its own name. The old stand-in gave all five of types 0-4 the one name `Arial Unicode MS`.
- **Open:** engine sizes are measured on one game. A game that loads several types into a small engine needs their sum there, and one whose engines are smaller than a font needs fails with 201 as above. Type 0 now holds no Chinese or Korean, as on the console, so a game that draws those from type 0 alone shows `?`. The fonts are drawn unhinted.
- **Found on:** Mario Tennis Fever (SDK 20.5.17). [Kirby's Dream Buffet, issue #1569](https://github.com/seedds/nxnative/issues/1569), logged the old take-over's `[RED] more than 16 font engines with a small work buffer`; its later crash is not shown to follow from it.

## C library, time and random numbers

### Time zone rules, calendar conversion and the network clock

- **Symptom:** saves dated 18:00:02 31/12/1969 (`ToCalendarTime: first conversion 2 → 1969-12-31 18:00`), and Continue, which takes the newest save, loads an older one.
- **Cause:** the host failed `time::StandardNetworkSystemClock::GetCurrentTime`, and the game kept the PosixTime it had (2). A Switch keeps its network clock from its last time sync, so one that has ever been online reads it offline too. The SDK's `StandardNetworkSystemClock::now()` never calls `GetCurrentTime`: it reads the time service once its own initialized flag is set, which the host's `Initialize` take-over never sets, and returns 0 (1970) otherwise ([Ocarina of Time](../../dm/games/0400486024DEC000/README.md)'s `sdk+0x5d8490`).
- **Fix:** the network clock is the host's clock, as the user clock (`DM_FIXED_TIME` included), since the host's clock is set from the network: `GetCurrentTime`, `now()`, and the network fields of the host's clock snapshots ([below](#steady-clock-clock-snapshots-and-user-clocks)). `t_time` checks all three. Also hooked: `time::ToPosixTime` (host `mktime`), `ToPosixTimeFromUtc` (host `timegm`), `ToCalendarTime` (the host's zone) and `ToCalendarTimeInUtc`. The contexts of the network clock and of the adjustable clocks follow the same rule ([below](#the-adjustable-network-clock-aborts-in-adjust)).
- **Reach:** `main` calls the network clock in Breath of the Wild, Tears of the Kingdom, Mario Kart World, Minecraft Dungeons II, PRAGMATA, Super Mario Party and [Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (`now()` too); Pokémon Sword and Shield, Brilliant Diamond and Animal Crossing: New Horizons import it.
- **Found on:** Divinity: Original Sin 2 (SDK 8.2.0; first brought up in DroidPlay Core, an Android fork that shares this host, from [PR #2359](https://github.com/seedds/nxnative/pull/2359): the network clock); 13 Sentinels: Aegis Rim (SDK 11, `ToPosixTime`); Super Mario Odyssey (`ToPosixTimeFromUtc`).

### The C library's local time is UTC, as on a Switch

- **Symptom:** times a game shows through the C library are off by the host's UTC offset: Hades II's load screen dated a save made at 01:44 KST (UTC+9) 16:44 the day before, its UTC time. The save file itself holds the right time.
- **Cause:** the host took over `localtime`, `localtime_r` and `mktime` with its own local-time functions, on the belief that the SDK converts by the system time zone. It does not: the SDK's musl time zone helper (`__secs_to_zone`) is a fixed stub (offset 0, no daylight saving, name `"UTC"`) in every `sdk` checked, SDK 3.5.0 to 22.2.10 (Xenoblade Chronicles 2 to EA SPORTS FC 27, the Switch 2 builds included). Local time on a Switch comes only from `nn::time`. Hades II turns its save header's time into a UTC `struct tm` with `gmtime_r`, back into seconds with `mktime`, then into a calendar with `time::ToCalendarTime`. The host's `mktime` read the UTC `tm` as local time, 32,400 s early in KST, and `ToCalendarTime` added the offset back once. The take-over came from the D2R port, whose chronicle times (`localtime` + `strftime`) differed from the wall clock by the zone's offset. They do on a Switch too.
- **Fix:** the take-overs are gone, so the SDK's own functions run. The pass-through table (`hle_table.c`), used only when no module defines them, maps `mktime` to the host's `timegm` and `localtime_r` to `gmtime_r`. `nn::time` keeps converting in the host's zone ([above](#time-zone-rules-calendar-conversion-and-the-network-clock)). `t_time` checks both with `TZ=Asia/Seoul`.
- **Found on:** Hades II 1.0.141667 (SDK 20.5.15; [issue #2784](https://github.com/seedds/nxnative/issues/2784): `gmtime_r` from `main+0x4301bc`, `mktime` from `main+0x430a4c`, `ToCalendarTime` from `main+0x430d18`).

### Steady clock, clock snapshots and user clocks

- **Symptom:** SDK calls that reach the time service, each aborting in `sm::Initialize` (or found in the imports before they were met).
- **Fix:**
  - `time::GetStandardSteadyClockCurrentTimePoint`, the free-function form of the steady clock (SDK 20): host monotonic seconds, fixed source ID; `GetSpanBetween` runs in `sdk` (Animal Crossing: New Horizons SDK 20.5.4, found in `main`'s imports before the first boot).
  - `time::ClockSnapshot::CreateWithStandardSystemClock`: 0xD0 bytes, filled on the host from the steady clock, the user clock and the calendar; the network fields are the user clock's, as the network clock is ([Time zone rules, calendar conversion and the network clock](#time-zone-rules-calendar-conversion-and-the-network-clock)), so two host snapshots take their span from their steady time points and one made on a Switch from the network times. The type byte at `+0xcd` is 1 for a standard snapshot (0 means uninitialized), as verified in Tears of the Kingdom's SDK. `t_time` checks the registration, a guarded buffer, the calendar and location, and snapshot arithmetic.
  - `time::StandardSteadyClock::now()`, the C++ clock form: a time point of seconds in `x0`. The SDK asks the steady-clock session `time::Initialize` opens and returns 0 without one (SDK 3.7.0, `sdk+0x16edf4` in Mega Man Legacy Collection, which calls it from six sites in `main`); the host takes over `Initialize` and opens none, so the clock never moved. It is the host's monotonic seconds, as the free function's. Reported in [PR #2729](https://github.com/seedds/nxnative/pull/2729).
  - The take-overs of the steady clock's `GetCurrentTimePoint` method, of the adjustable snapshot and of the adjustable user clock's `GetCurrentTime` were removed with the fork.
- **Found on:** The Legend of Zelda: Breath of the Wild, The Legend of Zelda: Tears of the Kingdom, Animal Crossing: New Horizons, Mega Man Legacy Collection.

### The adjustable network clock aborts in `Adjust`

- **Symptom:** `game called nn::diag abort: Result 0x74, call site sdk+…` within the first frames, the backtrace's first `sdk` frame right past `time::AdjustableNetworkSystemClock::Adjust` (its last instruction is the call of `diag::detail::AbortImpl`, so the return address names the next function, `GetSystemClockContext` of the same class). Any other reader of an adjustable network clock, or the adjustable user clock's `now()`, aborts in `diag::detail::AbortImpl` under `time::detail::MonotonicSystemClock`.
- **Cause:** `Adjust` copies `StandardNetworkSystemClock::GetSystemClockContext` into the SDK's `detail::MonotonicSystemClock` and aborts on its failure; the SDK asks the time service, which the host never opens, and gets 0x74. Past that, every adjustable reader goes through `MonotonicSystemClock::IsAdjusted`, `GetCurrentTime` or `GetCurrentTimespec`, which turn the stored context into a time through the time service's shared memory, which the host never maps, and abort without it (Nintendo Switch Sports Resort's `sdk+0x5d96e0`..`+0x5d985c`). The adjustable network clock's `GetCurrentTime`, `now()` and `GetSystemClockContext` each call `IsAdjusted` first; the adjustable user clock's `now()` calls `GetCurrentTime`. `GetStandardNetworkSystemClockCurrentTimespec` (SDK 17) reads the shared memory too and returns 0x74.
- **Fix:** on the host the network clock is the user clock ([Time zone rules, calendar conversion and the network clock](#time-zone-rules-calendar-conversion-and-the-network-clock)) and each adjustable clock is its standard clock. `hle_time.c` answers `StandardNetworkSystemClock::GetSystemClockContext`, `AdjustableUserSystemClock::GetSystemClockContext` and `AdjustableNetworkSystemClock::GetSystemClockContext` with the user clock's context (the one the host's snapshots carry at `+0x00` and `+0x20`). `Adjust` runs as is and only sets the SDK's copy. `t_time` checks each context against a snapshot, within its 0x20 bytes. The take-overs of the adjustable clocks' `GetCurrentTime` and `now()` and of the two network `…CurrentTimespec` getters were removed with the fork, so those readers reach the SDK's own code again.
- **Found on:** METAL GEAR SOLID: Peace Walker - Master Collection Version (`0100C6F01C4F8000`, 1.3.1, SDK 19, not in the games table), program 1, which its launcher starts: it aborted in `Adjust` (`sdk+0x42c514` on that build) right after its first frames. Found and diagnosed by varyform in [PR #1875](https://github.com/seedds/nxnative/pull/1875), whose first fix (a zero network context) ran it on for 90 seconds (2100 frames) with sound on an M3 Max; the fix as landed has not been run on that game here (no game files).

### A periodic benefit claim without the time service session

- **Symptom:** `Break#1 reason=0 Result=0 svc at sdk+0x370f24` right after the first save at the title, with `bt: sdk+0x175f00 sdk+0x175fc4 sdk+0x176060 sdk+0x375b88 main+0x6ea74 …` (`diag::detail::OnAssertionFailure` called from `time::ClaimPeriodicBenefitWithUserSystemClock`).
- **Cause:** the public `time::ClaimPeriodicBenefitWithUserSystemClock` (a once-a-day reward) asserts that `time::g_pStaticService`, the time service session `time::Initialize` opens, is set; the host takes over `Initialize` and opens none. The work is in `time::detail::ClaimPeriodicBenefitWithUserSystemClock`, which only compares the snapshots' fields through `CalculateSpanBetween` and `CalculateStandardUserSystemClockDifferenceByUser` (both host take-overs) and asks the service two things: when automatic correction was last switched, if the context's snapshot and this one differ in it (`+0xcc`), and the device's location and when it was set, if they differ in location name. Host snapshots never have automatic correction and always carry the host's zone name, but a claim context saved on a Switch (a location such as `Asia/Tokyo`) or a Mac whose zone changed reaches both, again with no session.
- **Fix:** the two service questions are taken over (`hle_time.c`): `detail::GetDeviceLocationNameAndUpdatedTime` answers the host's zone name, as its snapshots carry, and both it and `detail::GetStandardUserSystemClockAutomaticCorrectionUpdatedTime` answer a cleared time point. The host does not know either moment, and the claim uses such a time point only when its source ID is the current snapshot's steady clock's, which a cleared one never is (`t_time`). The `HLE_FORCE` on the public entry, which called the SDK's `detail::` implementation past its session check, was removed with the fork.
- **Found on:** Tetris 99 (010040600C5CE000) 2.5.0, SDK 6.4 (the same `sdk` module as ASTRAL CHAIN), from a provisional profile: the claim returned 0, then 1 on the next check, and the title screen kept running for three minutes at about 56 fps.

### Hooks whose return type did not match the SDK

- **Symptom:** a call the host answers reads as failed when it succeeded, or reads leftover register bits. Super Smash Bros. Ultimate refills the Spirit Board at every visit, since the elapsed time between two snapshots never reads as known.
- **Cause:** take-overs declared another return type than the SDK's own function: `time::CalculateSpanBetween` returns bool (true when the span is stored), and the host returned a Result 0; `nifm::HandleNetworkRequestErrorResult` returns bool, and the host returned a Result whose low bit happened to be 0. Checked in the `sdk` of SDK 12 to 20 (Metroid Dread `sdk+0x3ab540`, `+0x336210`).
- **Fix:** each returns what the SDK does: the span call 1 or 0; the network call 0 (not resolved, offline). `t_time` checks the span call's values.
- **Found on:** reported by MacNativeGames on Super Smash Bros. Ultimate (the Spirit Board); the Spirit Board was not replayed here.

### `clock_gettime(CLOCK_REALTIME)` through the time source pointer

- **Symptom:** `std::terminate` (`Break` from `sdk+0x5bfa48`) at the first real-time read (right after the first-boot dialog, `main+0x3f3f68` → `system_clock::now()`).
- **Cause:** `clock_gettime(CLOCK_REALTIME)` calls through a source pointer (`sdk+0xb05010`) that `nntimeStartup` sets once `time::Initialize` succeeds: 1 = `nn::time::GetStandardUserSystemClockCurrentTimespec`, 2 = the adjustable clock's (`sdk+0x8e414`). Both asked the time service.
- **Fix:** they are host take-overs now (`hle_time.c`), and `system_clock::now()` works on any build.
- **Found on:** Ace Attorney Investigations Collection (1.0.0.2, SDK 17.5.3).

### Guest clock reads wait while the app is in the background

- **Symptom:** after switching apps and back, one guest thread at 100% in a tight loop (`main+0x9abd0`, `x10 = 0`); the game freezes, picture still, sound on. Mac repro `DM_OE_SCRIPT=bg=1@20,bg=0@25`.
- **Cause:** the frame pacing measured a frame period of 0 (`main+0x5926a8`: the clock difference between two frames). The host freezes the guest clock in the background but its threads went on, so two frames read the same time.
- **Fix:** guest reads of the system counter (the `cntpct` gate, `svc GetSystemTick`) now wait while the app is in the background (`hle_os.c` `guest_clock_read_wait`); host work and the keyboard freeze (The software keyboard blocks only its caller) keep the frozen clock.
- **Found on:** Super Mario Galaxy 2 (one of two causes; the other is [Focus handling mode decides whether focus changes are notified](#focus-handling-mode-decides-whether-focus-changes-are-notified)).

### Cryptographically random bytes

- **Symptom:** abort in `sm::Initialize` under `nn::crypto::GenerateCryptographicallyRandomBytes` (Unicorn Overlord: `std::random_device` → the `sdk`'s own `getentropy` → `InitializeCsrng`; Z-A: the first call in `nnMain`, `main+0x1734b4`).
- **Cause:** the bytes come from the csrng service. The `sdk` defines `getentropy`, so the host's `getentropy` hook never sees the call, but the call into `nn::crypto` goes through the `sdk`'s PLT.
- **Fix:** an `HLE_FORCE` on it fills from the host's entropy stream, the same stream as `getentropy` (`hle_os.c`).
- **Found on:** Unicorn Overlord (SDK 16.2.4; one boot), Pokémon Legends: Z-A (19.3.11; one boot).

### `clock_gettime` is `nn::time`'s steady clock (SDK 22)

- **Symptom:** `libc++abi: terminating due to uncaught exception of type std::__1::system_error` (the arguments came out as rubbish, the format named the failure) once the game's own code ran, with `sdk+0x5f2e60` (`std::terminate`) and `sdk+0x66ad2c`/`sdk+0x66acc8` (`get_terminate`/`terminate`) in the backtrace.
- **Cause:** SDK 22's exported `clock_gettime` (`sdk+0xa1430`) accepts `CLOCK_REALTIME` and `CLOCK_MONOTONIC` and returns `ENOTSUP` for ids 2–11; both accepted ids jump through musl ifunc slots in the SDK's data (`sdk+0xba5018`, `sdk+0xba5020`) whose `R_AARCH64_GLOB_DAT` relocations bind `nn::time::GetAdjustableUserSystemClockCurrentTimespec`, `_ZN2nn4time41GetStandardUserSystemClockCurrentTimespecEP8timespec` and **`_ZN2nn4time37GetStandardSteadyClockCurrentTimespecEP8timespec`** (`sdk+0xb92298`). The first two were answered from [the CLOCK_REALTIME entry](#clock_gettimeclock_realtime-through-the-time-source-pointer); the steady one was not, so the SDK's shared-memory client ran, could not read the time service's page, and returned an error, which `std::chrono::steady_clock::now()` (`sdk+0x5f2e10`: `mov w0,#1; bl clock_gettime; cbnz w0` → `std::__1::__throw_system_error`) turned into the exception.
- **Fix:** `hle_time.c` answers `GetStandardSteadyClockCurrentTimespec` with the host's monotonic clock (`struct timespec` from `clock_gettime(CLOCK_MONOTONIC)`). To name such a failure, `hle_sdk16.c` takes `nn::diag::detail::VAbortImpl` (an assert, an uncaught C++ exception or an SDK check with a message): it logs `[diag] abort at <function>: <expression> (<file>:<line>) message format <format>` and then aborts as `AbortImpl` does. Only the format is printed: the host cannot expand a `va_list` the guest built.
- **Check:** with `DM_AUDIO=1`, a run to the first room has no `[diag]` line and the frame counter keeps advancing.
- **Found on:** Well Dweller (SDK 22.2.0), in `std::chrono::steady_clock::now()` called from GameMaker's frame-timing helper.

## Modules and symbols

### Host symbol indexes avoid repeated name scans

- **Symptom:** relocation repeatedly scans all HLE and forced-takeover entries, and named-stub reuse becomes quadratic as more imports are missing.
- **Cause:** module exports already had a name index, but `resolve_import`, `hle_implements`, `force_lookup` and stub reuse still searched their tables linearly.
- **Fix:** open-addressed name indexes store entry numbers. HLE duplicates retain the first entry; forced-takeover duplicates still abort. Stub insertion grows its index above half capacity and retains existing stub numbers. Resolution happens at startup only: the fork loads no modules at run time.
- **Found on:** The Legend of Zelda: Breath of the Wild, reported in [PR #261](https://github.com/seedds/nxnative/pull/261).
- **Check:** `make -C dm/host/tests symbols` (`t_symbols`) covers collisions that wrap around the table, duplicate precedence/rejection, absent sections and names, counting-wrapper selection, and the stubs through growth and reuse at capacity. The symbol test also passes AddressSanitizer and UBSan. A local arm64 Mac synthetic 270-entry HLE table with 25% misses, Apple clang 21 at `-O1`, took 375–442 ns per linear lookup versus 15 ns indexed (25–29x; three runs of 360,000 lookups). This measures lookup cost, not overall game loading time; no new gameplay run here.

### Global symbol resolution in load order

- **Symptom:** a library's `free` rejects a pointer (`CentralHeap::Free` → `NotNMallocPtrError`).
- **Cause:** the game's `main` defines its own `operator new` / `delete` (Unity's memory manager) and `sdk` has a copy forwarding to `malloc` / `free`.
- **Fix:** symbols are resolved globally in load order (the first module's definition wins, also for a module's references to its own exports); only local / non-default-visibility symbols bind to the module itself (`loader.c`). The loader logs how many references bind to an earlier module.

### Module initializers run dependencies first

- **Symptom:** a crash during `main`'s static initializers, before `nnMain`: `CRASH sig=11 addr=0xffffffffffffffe8 pc=sdk+0x46d880 lr=main+0x164410` — a null-vptr read inside the sdk module's `std::ostream::write`, called from a game log helper that `std::cout.write`s its first line.
- **Cause:** `run_module_inits` called each module's DT_INIT in forward order of the load list (main, subsdk0, sdk). The list puts dependents first and dependencies last: `main`'s initializers already write to `std::cout`, which the sdk module's DT_INIT (libc++'s `ios_base::Init`) constructs, so the game wrote to a not-yet-constructed `cout`.
- **Fix:** the DT_INITs run in reverse load order (`loader.c`), so a module's dependencies initialize before it; the timing is unchanged (after `nninitStartup` and `_init_libc2`, before `nnMain`).
- **Found on:** Little Busters! Converted Edition (`0100943010310000`, 1.0.0, SDK 8.3.2), a provisional profile, no note (not in the games table). With the fix the game passes all module inits and boots; If My Heart Had Wings (`01001AC00ED72000`) boots unchanged with the same host.

### Undefined weak imports bind to 0

- **Symptom:** a weakly imported function the game calls although nothing defines it: an `UNIMPL` line, then an abort.
- **Cause:** the loader bound every undefined import to a named stub, so the address test the compiler emits for a weak symbol saw a function.
- **Fix:** an undefined weak symbol that no module defines and the host does not implement is now 0, as Horizon's rtld binds it (`loader.c`, logged as `undefined weak … bound to 0`).
- **Found on:** Octopath Traveler 0 (the `thread_local` init function `_ZTHN13LowLevelTasks5FTask10ActiveTaskE`).

### `ro::ProtectRelro` runs natively

- `nn::ro::ProtectRelro` (called from `main`'s DSO init), a new import of SDK 20, needs nothing: it runs natively on the host's no-op `SetMemoryPermission` / `SetMemoryAttribute`. Found on The Legend of Zelda: Breath of the Wild (1.9.0, SDK 20.5.22).

### Built-in fonts and the audio device notification of SDK 21

- **Symptom:** an abort connecting to `pl:u` at boot; a failed `nn::audio` call at boot.
- **Cause:** SDK 21 has new names: `nn::pl::GetBuiltInFontData` (the Switch 2 overload fills type, address and size, and returns whether the font is loaded), `nn::pl::GetBuiltInFontDataSet` (the same for a list of types: at most 6, one byte each, `*count` entries of 0x18 bytes in order, returning whether the fonts are loaded) and `nn::audio::AcquireAudioOutputDeviceNotification`. Unhooked, they reach the services the host does not have.
- **Fix:** the Switch 2 overloads are hooked (`hle_sdk16.c`) with the stand-in fonts of the shared font calls; the font set fills each type as `GetBuiltInFontData` does, in the order asked, and leaves out a type with no stand-in font (`t_shared_font`). The notification (`hle_audren.c`) binds the game's event, which follows the host's output route. The Switch 1 overloads and the older notification name were removed with the fork.
- **Found on:** Splatoon Raiders; `GetBuiltInFontDataSet` on Kirby and the Forgotten Land's Nintendo Switch 2 Edition (program `04004D300C5AE001`, at boot).

### The Joy-Con mouse pointer

- **Symptom:** an abort in `nn::hid` at boot, in a Switch 2 game that sets up the Joy-Con's mouse mode.
- **Cause:** the SDK's Joy-Con 2 mouse sensor (Jcms) and pointer (Nmouse) calls open the hid service, and the host has neither the service nor the sensor.
- **Fix:** the calls this game references answer as a console with no such sensor (`hle_hid.c`): `GetNmouseHandles` gives no handles and `GetNmouseTypeSet` no types (a game skips its mouse code on those answers), `GetJcmsHandle` makes the handle as the SDK does (the npad id in byte 0, the JcmsType in byte 1), and `StartJcms`, `StopJcms`, `FinalizeJcms` and `FinalizeNmouse` do nothing. `InitializeJcms` and `InitializeNmouse` have no hook: the game references neither. The fork removed the sensor itself: a front end's sensor reports, the state rings, the pointer's states, the transport's feature bit and the log switch. A Joy-Con 2 pad still says it is one (`dm_joy_attach` with `DM_JOY_2`, `dm_input.h`), and its npad shows the Joy-Con 2 style beside the plain one to a game that supports it (style bits 12, 13 and 14 for JoyDual, JoyLeft and JoyRight, inferred from Nintendo Switch 2 Welcome Tour; `t_hid`).
- **Found on:** Fire Emblem Fortune's Weave, Pokémon Pokopia (the pointer's calls); Nintendo Switch 2 Welcome Tour (the sensor and the styles).

### The graphics system check

- **Symptom:** `nn::diag abort` in `gs::sdk::CheckGraphicsSystemInitialized` at boot.
- **Cause:** the SDK's check that its graphics system is booted reads a flag only the SDK's own graphics boot sets, and the host never runs that boot.
- **Fix:** `CheckGraphicsSystemInitialized` passes (`hle_nv.c`): the host's graphics layer is up from the start. The camera session that went through the same graphics system was removed with the fork.
- **Found on:** Mario Kart World 1.8.0, from pull request #1116 (that build is not run here).

### Application GPU scheduling time

- **Symptom:** a null read in `nn::os::SdkMutexType::Lock`, at `sdk+0x151fb0`, called from `nn::gs::sdk::QueryApplicationGpuTimeSpan` after the first rendered frame.
- **Cause:** the query asks the graphics server's session (command 27), which the host never opens, how much of an interval the GPU was given to the application rather than to another of the console GPU's clients (the system's own rendering). Its two times are nanoseconds on the system tick clock; callers pass intervals bracketed by their own GPU counter timestamps.
- **Fix:** `hle_nv.c` answers the whole interval (`end - begin`, 0 if `end` is not later) with success. The host's counter timestamps are its model of the console GPU's timeline ([GPU timestamps per submission segment](frame-rate.md#gpu-timestamps-per-submission-segment)), on which the application is the only client. It is not the GPU's busy time: Welcome Tour's Bezel profiler queries each render pass's GPU region (`main+0x30a8f4`) and the whole frame's (`main+0x30a808`), and the frame load its dynamic resolution reads is the frame's scheduled time, plus the time the application was not scheduled since the previous frame, plus 0.36 ms. With busy time the GPU's idle time between frames would count as taken, and every frame would read as full. The earlier stub returned `0xaf3` (not even the SDK's own unavailable-session result, `0x30af3` at `sdk+0x41200c`); Bezel then took each region's length and left out the 0.36 ms margin.
- **Found on:** Nintendo Switch 2 Welcome Tour, update v262144 (`sdk+0x411dc0`, called from `main+0x30a840`).

### The target frame rate (graphics frame length)

- **Symptom:** a null read at boot in `nn::os::SdkMutexType` under `nn::gs::sdk::SetGraphicsFrameLengthMode`, called from `nn::oe::SetGraphicsTargetFrameRate`.
- **Cause:** `SetGraphicsTargetFrameRate` maps up to 59 fps to mode 1, up to 119 to mode 2 and above to mode 3 (`SetGraphicsTargetFrameRateAuto` to mode 0) and calls `SetGraphicsFrameLengthMode`, which locks the gs graphics server's context and sends it the mode. The host has no graphics server, so the context is null.
- **Fix:** `SetGraphicsFrameLengthMode` is hooked and logs the mode once per change; both `oe` paths reach it. The host paces by the window's present interval (`hle_oe.c`).
- **Found on:** Hyrule Warriors: Age of Imprisonment: 60 / its present interval at boot.

### Mods made for emulators do nothing, or only half of them does

- **Symptom:** a mod folder as Ryujinx, the yuzu family or Atmosphère take it (`romfs/`, `exefs/`) had no place to go: only `DM_ROMFS_OVERLAY` replaced RomFS files, by hand. With the mods folder: `[RED] mods: … is not applied` for a code patch, `mods: warning: … differ only in case` for a file a Switch would not have matched.
- **Cause:** the host had no notion of a mod: no folder, no order, no way to turn one off, and no patching of a module after the rewriter.
- **Fix:** `dm/host/hle_mods.c` reads a mods folder (`DM_MODS`, default `<DM_ROOT>/mods`), one folder per mod in any of the layouts mods ship in, ordered and switched by `order.txt` ([Mods](../development.md#mods)):
  - `romfs/` folders join the RomFS overlay and follow the Mods menu while the game runs; a `<name>.dm-delete` marker hides a game file or directory, and a name that differs from the game's only in case is taken with a warning;
  - `.pchtxt` and `.ips` patches are written into a module as it is mapped, before its code is sealed, each file whole or not at all, and never over what the rewriter changed ([the launch-time rewrite](rewriter.md#mod-code-patches-the-host-cannot-make-at-load-time) takes those).
- **Open:** code modules of a mod (ExLaunch, Skyline) are not loaded ([what one would need](../development.md#what-an-exlaunch-mod-would-need-open)).
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game), with two RomFS mods (a controller UI, a pack of tunic recolours) and synthetic patches.

### An add-on module calls SDK functions the game never makes

- **Symptom:** the practice tools' `subsdk9` read no controller (its `nn::hid::detail::GetNpadStates` ran the SDK's own reader, whose HID client the host never sets up) and could not keep its settings (`nn::fs::MountSdCard` needs fsp-srv, which the host does not serve).
- **Cause:** the host takes over the SDK calls the game makes. An add-on module makes others, and a forced takeover of them would also rebind the game's own modules (the sdk reaches the detail readers through its own PLT) and be reported in red on every run without the add-on, since no game module references it.
- **Fix:** `HLE_ADDON` takeovers (`hle.h`, the `swaddon` section) bind for the imports of an add-on module only (`loader.c` `bind_sym`, `module_t` `addon`): the three detail readers answer as the public ones (`hle_hid.c`), and `MountSdCard` / `MountSdCardForDebug` mount a host folder, `DM_SDCARD` or `<DM_ROOT>/sdcard` (`hle_fs.c`). An add-on module loads from a folder of its own (`load_modules`' `dirs`, `hle_practice.c`). Without the add-on the game's modules load as before: their `DM_LOADHASH` is unchanged.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game): sloperinaGZ 0.0.9, 5 of its 36 imports.

### A mod's code written past the end of the text was not checked

- **Symptom:** none seen: a patch that writes an `svc`, an `x18` instruction or a timer register read into the padding between a module's text and its read-only data would have been applied, and run raw against Apple's kernel.
- **Cause:** `hle_mods.c` `rec_refusal` checked the instructions a patch writes only below `TEXT_END`. The padding after it, up to the read-only data, is on the pages the loader seals executable with the text, and mods use it as a code cave: sloperinaGZ's IPS puts its stubs at main+0x3c46400, past `TEXT_END` 0x3c461d0.
- **Fix:** the check covers the text and that padding (up to `RO_OFF`). The rewriter never writes the padding, so there only the instruction check applies, not the moved-words list. Data patches past it are not checked as code.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game): sloperinaGZ's IPS of main (11 patches, applied), and a synthetic `svc` in a cave (`t_mods`, refused).

### A game that asks for an amiibo never finds one

- **Symptom:** a game's amiibo screen waits for a figure forever; nothing in the host can put one on the reader.
- **Cause:** `nn::nfp` was answered with one NFC device whose detection never finds a tag, as a console with no figure at hand.
- **Fix:** the host's NFC device (`dm/host/hle_sdk16.c`) finds an amiibo from a raw dump of the figure's tag: **Amiibo › Scan Amiibo…** in the Mac window, `DM_AMIIBO=<file>`, or `DM_CTL`'s `amiibo <file>` ([Amiibo](../development.md#amiibo)). The UID, the model block and the write counter come from the dump; the owner, nickname and application area, which the tag holds encrypted, are the host's own.
- **Open:** reading a dump's own encrypted data with the player's key file.
- **Found on:** [Ocarina of Time](../../dm/games/0400486024DEC000/README.md#found-on-this-game).
