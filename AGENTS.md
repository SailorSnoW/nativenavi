# Notes for agents

- This repository runs one game natively on Apple silicon Macs: The Legend of Zelda: Ocarina of Time for the Nintendo Switch 2 (title ID `0400486024DEC000`, SDK 22, NVN2, Nintendo EPD's sead / agl engine). The game's own code runs, rewritten only where Apple's kernel requires it (`dm/tools/patch_nso.py`), on a host that answers Horizon's SVCs and the SDK's services (`dm/host`) and implements NVN on Metal (`dm/gfx/nvn`). It is a hard fork of nxnative, which runs many Switch games on Macs and iPhones: everything that did not serve this game on a Mac was removed (other profiles, iOS, Vulkan, OpenGL, other engines' code, NSP input), and what remains is aimed at this game. The game's note, [dm/games/0400486024DEC000/README.md](dm/games/0400486024DEC000/README.md), says what its profile needs and why, what was measured, how to drive it on the Mac and what is open. [README.md](README.md) is the player-facing page; [docs/development.md](docs/development.md) has the internals, the packing script's options, building by hand, prewarm lists and power.

- The aim is this game running as well as possible on a Mac: frame pacing, power, load times and picture quality count as much as correctness. A change that only serves Ocarina of Time is welcome; it does not have to hold for other games. Still give each thing one place: the game's constants and shader tables in its profile (`dm/games/0400486024DEC000/`: `game.tsv`, the tables, `patches.py`), not in host code (`dm/tools/tests/test_architecture.py`); a mechanism in the host or the tools. The tools and Makefiles take this profile by default (`game.DEFAULT`; `GAME ?=`); `DM_GAME` / `GAME` name another only for a derived profile.
- Do not bring back what the fork removed (another game's profile, iOS, Vulkan or OpenGL, NSP input, the cheat engine, iCloud save sync) unless the user asks. Before removing more, show that the game does not use it: `DM_IMPORTS=1` lists the SDK entries its modules reference, `DM_HLECOUNT=<file>` counts those it calls. A host entry the game references but never calls on the routes tested is removed only with evidence from the game's files, and then leaves a `[RED]` refusal behind, not a call into a service that is not there.
- Find a bug's root cause and fix it there; do not just work around it. Before changing code, find why it happens: the faulting instruction and its decompilation, the value that went wrong and who wrote it, the Horizon / NVN / Metal semantics the host or the translator gets wrong. Then fix that place. A change that only hides the symptom (a stub, a skipped call, a clamp, a retry, a sleep or a longer timeout, a cache flush, a profile key that turns a feature off) is a workaround: use one only when the cause is known and lies where it cannot be fixed (the game's own code, which a rewriter cut changes deliberately, or a platform limit), or when the user asks for a stopgap. Then say so in the code comment and in the game note or reference entry: the cause, or what is still unknown, marked open.
- Where a new finding goes, once: a fact about the game (its passes, shader keys, measurements, why its profile needs a key or a cut, its status) in the game's note, in the section it belongs to and marked current or resolved; a mechanism of the host or the tools as an entry in its `docs/reference/<subsystem>.md` section (Symptom, Cause, Fix, Found on), then `python3 dm/tools/docs_symptoms.py` to update the symptom index, and a line under the note's "Found on this game". Link to a finding instead of repeating it. The reference keeps entries found on other games by nxnative where the code they explain is still here; those games are named in plain text. This file changes only when a rule does. `dm/tools/tests/test_docs.py` checks the links and anchors, the note and its table row, the symptom index, and the length of this file (1,500 words) and of each guide in `docs/agents` (6,000).
- Per-build knowledge is keyed by the NSO build ID: rewriter cuts, observation gates and frame-step stubs in the profile's `patches.py` (the game's own modules) or `dm/tools/sdk_patches.py` (Nintendo's `sdk` module), which `dm/tools/patch_nso.py` loads; the profile's `build` rows (the builds the game was brought up on, and their display versions; the packing script packs any other version from a derived profile, without those builds' fixes); and host behaviour that uses fixed module addresses checks `module_t.build_id` (`dm_main_build()`). When a new build of the game appears, carry addresses over with `dm/tools/nso_fnmap.py` and check them by disassembly; never let fixed addresses run on a build they were not found in. For automatic cuts across updates, opt individual patches into `MATCH_CUTS` only after verifying their function fingerprints and assumptions; follow [Function-matched cuts](docs/reference/rewriter.md#function-matched-cuts-for-unregistered-builds).
- The game is packed from its NUP container by `scripts/build_app.py` (`--platform mac-app`: a Mac app; `--platform mac`: a development build and the command that runs it). Scripts the user runs live in `scripts/` at the repository root; each one runs from a terminal (non-zero exit on error). Tools that only agents or other scripts call stay under `dm/`.
- Game files and anything extracted from them live in the game's build folder (`<NUP folder>/0400486024DEC000_build`, or the `--work-dir` given), never in this repository: unpacked files, rewritten modules, shader libraries, runs, dumps and analysis. Put other large scratch data there too, and ask before deleting anything in it that you did not write. Do not sign or install builds on the user's devices.
- Language: everything is in English. Red log lines (something unimplemented or wrong) start with `[RED] `. Text that must match the game's own non-ASCII data is written as escapes (`"\xE8\xB5\xB7"`), never as characters.
- The shader translation chain has one version, `DMSH_CHAIN` in `dm/gfx/nvn/dmsh_chain.h`, which the host is compiled with and loads only libraries of. It covers the chain's tools (`dm/gfx/tools/dmsh_chain.py` `FILES` is the list: the `dmsh_*` tools, `shader_split.py`, the translator's sources, `dm/gfx/nvn/dmsh_abi.h`, `dmsh_chain.lock`). The profile's own inputs (`shader_map.tsv`, `shader_facts.tsv`, `shader_pairs.tsv`, its `shader_*` / `nvn_*` keys) are not part of it: they are in each shader's cache key, and their digest stamps the libraries (`b-<V>/inputs.tsv`). The procedure:
  1. After changing a chain tool, run `dmsh_chain.py --header` once and commit `dm/gfx/nvn/dmsh_chain.h` with the change (`dm/tools/tests/test_nsp_chain.py` fails on a stale one).
  2. After that, or after changing the profile's inputs, rebuild the shaders: a full `dmsh_build.py` run (the packing script does it) stamps the libraries and writes the profile's `c1_full.tsv` and `cb_extent.tsv` from its Mac outputs (the host takes them only beside the stamp they name). A chain change retranslates every shader of the game (about 42,850), which is the longest step of a build: group such changes.
  3. Rebuild the host.

  The translator is the native `dm/gfx/tools/dmsh_xlate_bin/dmsh_xlate`, which matches `dmsh_chain.lock`; a rebuild (`dm/tools/native_tools.sh`) does not until the lock is updated.
- A change to the chain, host or tools is checked before it is committed ([06-dev-loop.md](docs/agents/06-dev-loop.md)): the host build, the host, graphics and Python tests, and a run of the game (headless with `DM_KEYS`, or `scripts/regress.py check`). Report what failed or could not be run; a path that this Mac cannot exercise (VideoToolbox AV1 needs an M3 or later) is named as untested.
- Commit only when asked, with the checkout's own git identity, and do not push unless asked. The message opens with `area/component: summary` ([Commit messages](docs/agents/06-dev-loop.md#7-commit-messages)), and a change a front end must act on takes a `Front-ends:` line ([docs/frontends.md](docs/frontends.md)).
